## 0. 全景定位

`agentic loop` 不是一个像 TCP、Transformer、CAP 定理那样边界极清楚的标准术语，它更像是近几年 AI agent 工程和研究社区逐渐收敛出来的一种核心运行范式。它描述的不是“模型是什么”，而是“模型怎样在任务过程中持续行动、接收反馈、调整策略并最终收敛”。

如果从大领域定位，它属于 `LLM-based agents`、`agent systems`、`autonomous systems` 这一大类；如果从系统层级定位，它处在“推理能力”和“外部执行能力”之间，是两者真正接上电路的那一层。很多人谈 agent，实际上谈的是工具调用、规划、多代理、记忆、验证、浏览器操作、代码执行，但这些东西之所以能形成一个真正像 agent 的系统，靠的就是一个循环：`goal -> plan -> act -> observe -> update -> verify -> continue/stop`。

从知识图谱上看，`agentic loop` 不等于某一个框架，也不等于某一篇论文。它更像一个“母结构”，很多后来流行的名字都可以看作是这个母结构的不同强化版本：

- `prompting / chain-of-thought / tool use / function calling / state` -> `agentic loop` -> `ReAct / Reflexion / Voyager / AutoGen / LATS / multi-agent systems / computer-use agents`

如果你要真正理解它，最好先搞清两个前置概念：

- `工具调用`：模型怎样从“输出文本”走向“触发外部动作”，例如发请求、读文件、调用浏览器、执行代码。
- `环境反馈`：为什么一个任务不能只靠内部推理完成，而必须让外部世界返回观察结果，参与下一步决策。

没有这两个前置概念，`agentic loop` 很容易被误解成“多轮对话”或者“连续问模型几次”。但它真正强调的是：系统不再把任务当成一次生成，而是当成一个不断更新的闭环过程。

---

## 1. 一句话定义

- 大白话定义：`agentic loop` 是一种让模型边做、边看、边改、边验证的任务闭环。
- 日常类比：像修水管，不是看一眼就直接宣布修好，而是 `先判断漏点 -> 动手修 -> 通水测试 -> 看还漏不漏 -> 再调一轮`。

如果再压缩成一句更工程化的话，可以说：

- `agentic loop = 目标驱动 + 外部行动 + 环境反馈 + 状态更新 + 验证收敛`

这个定义有两个关键词不能丢：

- `loop`：说明它不是单次生成，而是多轮迭代。
- `agentic`：说明每一轮不是被人手工写死，而是系统自己根据目标和反馈决定下一步。

## 2. 为什么会出现

### 2.1 它要解决的根本问题是什么

很多现实任务并不是“知道问题就能直接写出答案”。它们更像探索问题：

- 需要先找信息，再决定下一步问什么
- 需要先调用工具，再根据结果判断路线
- 需要边执行边发现约束
- 需要检查输出是否满足目标
- 需要在失败后修正策略

这类任务的共性是：**中间状态本身会改变后续决策**。也就是说，任务不是静态映射，而是动态过程。

单轮问答模型最擅长的是：

- 输入比较清晰
- 输出是文本
- 中间不必看环境反馈
- 正确路径大致已隐含在参数知识里

但现实世界里一旦进入下面这些场景，单轮模式就会明显失效：

- 需要浏览网页或文档
- 需要跨多个来源交叉验证
- 需要写代码并运行测试
- 需要操作外部系统或 GUI
- 需要长任务状态保持
- 需要知道“什么时候应该停”

所以 `agentic loop` 的出现，本质上不是因为大家想追新词，而是因为单次生成范式碰到了硬边界。

### 2.2 之前人们怎么处理

在 agentic loop 走红之前，主流做法大致有四类：

1. `单轮 prompt`
   - 给模型尽量长的上下文，然后让它一次性答完。
   - 问题是：一旦中途需要新信息或外部动作，这种方式就会卡住。

2. `固定 workflow`
   - 人预先写好 `step1 -> step2 -> step3`。
   - 问题是：只要真实路径跟预设不一样，系统就会僵住。

3. `RAG + 生成`
   - 先召回文档，再让模型总结。
   - 问题是：RAG 更擅长“取回后回答”，不擅长“边探索边决定下一个动作”。

4. `工具调用但无循环`
   - 模型可以调用函数，但系统仍把每次调用当成局部动作，没有完整状态和验证闭环。
   - 问题是：有行动能力，不代表有任务闭环能力。

### 2.3 旧方法的根本缺陷在哪里

旧方法的根本缺陷不只是“模型不够聪明”，而是它们大多缺失以下某一项：

- 缺少显式状态
- 缺少环境观察
- 缺少失败后更新策略的机制
- 缺少停止条件
- 缺少验证与纠偏

换句话说，问题不是“没有工具”，而是“没有闭环”；不是“不会调用函数”，而是“调用后不知道怎样根据结果继续推进任务”。

### 2.4 谁、在什么情境下、基于什么洞察提出了它

严格说，`agentic loop` 没有单一发明人。它是多条研究和工程线汇流后的结果。

可以粗略地看成三条线交汇：

1. `reasoning` 线
   - 典型代表是 chain-of-thought 和 ReAct
   - 贡献是把“内部推理过程”显式化

2. `tool use` 线
   - 典型代表是 Toolformer、函数调用生态
   - 贡献是把模型接到外部能力上

3. `autonomous agents / systems` 线
   - 典型代表是 Reflexion、Voyager、AutoGen、LATS、各类 agent SDK
   - 贡献是把推理、行动、记忆、验证和多代理组织起来

真正的洞察是：**任务完成不应被看成一次采样，而应被看成一个可持续修正的控制回路**。

### 2.5 关键决策逻辑

形成这个概念时，有几个非常关键的“为什么选 A 而不是 B”。

#### 决策 1：为什么要迭代，而不是一次性生成

- 因为很多任务的关键信息根本不在初始输入里。
- 你只有先行动，才能拿到下一步需要的上下文。
- 因此系统必须允许 `act -> observe -> revise`，不能指望模型在零观察的情况下直接给出完整答案。

#### 决策 2：为什么工具调用要成为核心，而不是辅助

- 因为外部世界变化太快。
- 最新网页、内部文件、编译器错误、浏览器状态、API 返回值，这些都不在训练参数里。
- 模型如果不能操作工具，就只能幻想世界，不是真正与世界交互。

#### 决策 3：为什么验证要显式化，而不是默认模型自检

- 因为“看起来合理”不等于“真的正确”。
- 真实系统里最怕的是 agent 在错误路径上越走越远。
- 所以必须把 `verify` 做成独立机制，而不是寄希望于模型自发谨慎。

#### 决策 4：为什么后来会走向多代理

- 因为单代理的最大瓶颈往往不是一轮推理能力，而是上下文容量、并行度和任务分工。
- 当问题可拆成多条相对独立的探索线时，多代理能提高 token 使用效率和并行探索能力。

#### 决策 5：为什么又会回到“并不是所有任务都该多代理”

- 因为并行并不总是带来收益。
- 如果子任务强耦合、共享上下文密度高、实时协调成本大，多代理反而会把问题复杂化。
- 这就是为什么现在最成熟的观点不是“永远多代理”，而是“只在合适的地方并行”。

### 2.6 当时的约束条件是什么

`agentic loop` 的出现与成熟，还受到几个现实约束推动：

- 模型上下文有限，无法一次装下所有信息
- 早期工具接口非常不统一
- 运行成本高，多轮调用代价明显
- 测试和评估体系不成熟
- prompt injection、越权调用、错误扩散等安全风险开始显现

所以今天你看到的 agentic loop，其实是能力、成本、可控性、安全性四个维度之间不断折中的结果。

## 3. 核心机制

### 3.1 用 `input -> process -> output` 解释

最基础的 agentic loop 可以抽象成：

`goal + context + tools + constraints -> iterative decision loop -> answer / artifact / action / escalation`

展开后通常是：

`goal -> plan -> act -> observe -> update state -> verify -> continue or stop`

再写得更细一点：

1. `receive goal`
   - 系统接收用户目标、规则、上下文和可用工具。

2. `construct current state`
   - 把当前任务、已知信息、预算、约束、历史轨迹整理成可继续计算的状态。

3. `select next action`
   - 决定这一轮是搜索、阅读、比较、调用 API、运行代码、浏览页面、委派子代理，还是直接回答。

4. `execute action`
   - 真正去做动作，而不是只在脑中模拟。

5. `observe environment response`
   - 收到网页结果、文件内容、报错日志、测试结果、用户反馈、工具返回值等外部观察。

6. `update state and policy`
   - 把观察写回状态，必要时更新计划、收缩范围、改变策略。

7. `verify`
   - 判断这轮结果是否足够、是否可信、是否需要额外验证。

8. `stop or continue`
   - 若满足停止条件则结束；否则进入下一轮。

### 3.2 关键子概念

#### 1. State

状态是 agent loop 的核心容器。没有状态，系统每轮都像重开新对话。

状态通常包括：

- 当前目标
- 已完成步骤
- 已知事实
- 未解决问题
- 工具调用历史
- 错误记录
- 预算和停止条件

#### 2. Tool Use

工具调用让模型从“语言系统”变成“任务系统”。

常见工具包括：

- web search
- file system
- shell
- code execution
- browser automation
- business APIs
- MCP servers

没有工具调用，agent loop 仍然可能存在，但能力会被强烈限制，基本只能在文本世界内循环。

#### 3. Observation

观察是外部世界对系统动作的反馈。

重要的是：观察不是装饰，而是下一轮决策的依据。

例如：

- 测试失败 -> 说明 patch 还没收敛
- 搜索结果空 -> 说明 query 太窄
- 页面结构变化 -> 说明浏览器策略要改
- 发现权威来源冲突 -> 说明要提高验证层

#### 4. Memory

记忆不是可选品，而是长任务性能的决定因素之一。

记忆可以分成：

- `working memory`：当前任务局部上下文
- `episodic memory`：本次尝试中发生过什么
- `long-term memory`：跨任务可复用经验

Reflexion 之所以重要，就是因为它把“失败后的语言化反思”写入 episodic memory，让下一轮不再盲目重复。

#### 5. Verification

验证是 agent loop 从“会跑”变成“可信”的关键。

验证的常见方式有：

- 单元测试
- 集成测试
- 规则检查
- 结构化 rubric
- source attribution
- visual feedback
- LLM judge
- 人类审批

没有验证，loop 只会更快地产生幻觉，而不是更可靠地完成任务。

### 3.3 第一性原理追问

#### 如果去掉状态，会怎样

系统会不断重复劳动：

- 重复搜索
- 重复问同样问题
- 重复犯同样错误
- 无法判断自己已经做到哪一步

这说明状态不是“缓存优化”，而是 loop 的骨架。

#### 如果去掉观察，会怎样

系统会退化成内部幻想机：

- 做了动作，但不真的看结果
- 或者根本不做动作，只脑补动作后果

这说明观察不是“补充信息”，而是 loop 的现实锚点。

#### 如果去掉验证，会怎样

系统会持续积累未被发现的错误，直到最后输出一个形式完整但本质不可用的结果。

这说明验证不是锦上添花，而是防止错误级联的保险丝。

#### 如果去掉停止条件，会怎样

系统要么：

- 过早停止，交付半成品
- 要么无限继续，成本失控

所以停止条件和预算控制，本质上是 loop 的经济学部分。

### 3.4 一个最小 agentic loop 长什么样

可以写成极简伪代码：

```text
state = initialize(goal, tools, constraints)

while not done(state):
    action = choose_next_action(state)
    observation = execute(action)
    state = update(state, observation)
    verdict = verify(state)
    if verdict == "stop":
        break

return finalize(state)
```

这段结构非常普通，但几乎所有现代 agent 系统，无论是 ReAct 风格、code agent、browser agent、multi-agent orchestrator，最后都能映射回这个骨架。

## 4. 生态位：它和谁像？和谁争？

### 4.1 易混辨析

| 概念 | 相似点 | 本质区别 |
|---|---|---|
| workflow | 都是多步 | workflow 更像预设路径；agentic loop 更强调根据中间观察动态改路线 |
| RAG | 都会接外部信息 | RAG 核心是 retrieve -> generate；agentic loop 核心是 act -> observe -> revise |
| ReAct | 都强调 reasoning + acting | ReAct 是经典模板之一；agentic loop 是更宽的总称 |
| multi-agent | 都属于 agent 系统 | multi-agent 是组织形式；agentic loop 是运行机制 |
| chain-of-thought | 都涉及中间推理 | CoT 是内部思维链；agentic loop 包含外部动作和反馈 |

### 4.2 上下游关系

从系统分层看：

- 上游：用户目标、权限、工具定义、系统规则、可用上下文
- 中游：agentic loop 本身
- 下游：结果输出、日志、回执、评估、人工接管、长期记忆

从任务生命周期看：

`goal definition -> task decomposition -> agentic loop -> verification -> delivery -> evaluation`

agentic loop 最特别的地方在于，它不是某个步骤，而是中间那段持续运行的“工作引擎”。

### 4.3 它通常和哪些概念搭配使用

- `tool calling`
- `state management`
- `memory`
- `guardrails`
- `tracing / observability`
- `human-in-the-loop`
- `multi-agent orchestration`
- `protocols like MCP / A2A`

这些概念和它的关系不是“可有可无的配件”，而是它在工程中落地时的自然外延。

### 4.4 竞争与互补

#### 固定 pipeline

优点：

- 可控
- 成本低
- 可预测

缺点：

- 遇到路径依赖和例外情况时脆弱

适用：

- 规则固定、风险高、变化少的业务流程

#### RAG + 一次生成

优点：

- 简单
- 快
- 适合问答和总结

缺点：

- 不擅长探索型任务和多步行动任务

适用：

- 问答、摘要、轻分析

#### Agent + Workflow

这是当前最现实的组合。

- 把高不确定性部分交给 agentic loop
- 把高确定性部分交给固定 pipeline

这往往比“全 agent”更稳，也比“全 workflow”更灵活。

## 5. 发展脉络与前沿

### 5.1 发展脉络

#### 阶段一：把推理和行动接起来

2022 年 ReAct 的意义，不在于简单加了一个动作字段，而在于它第一次清楚展示：推理与行动可以交错进行，且两者会互相增强。

此前很多工作默认认为：

- 要么让模型好好想
- 要么让系统好好做

ReAct 说的是：

- 不，应该 `think -> act -> observe -> think again`

这个变化看似只是模板变化，实际上直接改变了后续整个 agent 领域的建模方式。

#### 阶段二：把工具调用从技巧升级成机制

2023 年 Toolformer 代表了第二阶段。它不再满足于手写 prompt 让模型“勉强学会”调用工具，而是试图让模型自己学会：

- 什么时候该调工具
- 调什么工具
- 参数怎么写
- 返回结果怎么整合进后续 token 预测

这一步的重要性在于：agent loop 的“行动”开始从启发式过渡到可学习对象。

#### 阶段三：把反思、记忆和长期迭代接进来

同样在 2023 年，Reflexion 和 Voyager 分别从两个方向把 loop 推进了一大步。

Reflexion 的关键贡献是：

- 不改模型权重
- 直接让 agent 在失败后写下语言化反思
- 再把这些反思带入下一轮

Voyager 的关键贡献是：

- 在开放环境中做长期探索
- 把技能写成可执行代码并沉淀为技能库
- 结合自动课程、环境反馈和自我验证，让系统具备某种“持续进化”的味道

这时的 loop 已经不只是 `action loop`，而开始带有 `learning loop` 的结构。

#### 阶段四：从单代理走向组织系统

2023 年 AutoGen、CAMEL 等工作让大家看到一个新问题：

- 不是所有复杂任务都该由单个 agent 一口气完成

于是问题从“怎样让一个 agent 循环起来”，转向“怎样组织多个 agent 的循环关系”。也就是：

- 谁负责规划
- 谁负责搜索
- 谁负责验证
- 谁负责综合
- 谁负责把最终结果交付

此时 `agentic loop` 的单位不再只是单代理回路，还可以上升为团队级回路。

#### 阶段五：从回路走向系统工程

2024 到 2026 年，Agent SDK、LangGraph、OpenAI Agents SDK、Anthropic Research system、MCP、A2A 等方向的共同特征是：

- 不再把 agent 当作一次 demo
- 而是当作长期运行、需要观测、需要协议、需要治理的系统

这意味着 agentic loop 已从“prompt 模板”变成“系统架构核心”。

### 5.2 当前前沿方向

#### 方向 1：可观测的 loop

以前很多 agent 失败时，开发者只能说“它看起来乱了”。现在更成熟的体系会要求：

- 每步可追踪
- 每步可解释
- 每步可回放
- 每步可评估

这也是为什么 tracing、receipts、run history、trajectory eval 越来越重要。

#### 方向 2：协议化互操作

MCP 的价值在于：

- 标准化 agent 接工具和上下文的方式

A2A 的价值在于：

- 标准化 agent 和 agent 之间的协作方式

这两者一起推动 agentic loop 进入协议层，而不再只是每个团队手写 glue code。

#### 方向 3：更强的 planning

从线性 loop 到 tree search，再到更复杂的 deliberation 结构，说明下一阶段的竞争点不只是“能不能调工具”，而是：

- 如何选择更优路径
- 如何平衡 breadth 和 depth
- 如何在有限预算下搜索更有价值的路线

#### 方向 4：computer use

当 agent 的动作空间从 API 扩展到真实 GUI，loop 会变得更像机器人控制问题：

- 观察更脏
- 状态更不稳定
- 验证更难
- 安全风险更高

但这也意味着它离真实世界更近。

### 5.3 尚未解决的核心争议

1. 什么才算合格停止条件
2. 多代理收益什么时候为正
3. 如何评价非唯一正确路径
4. 如何在开放工具环境下做权限和安全控制
5. 如何控制成本不让 loop 变成 token 黑洞

### 5.4 驱动力判断

推动这条演进线的底层力量不是某家公司的营销，而是三件事同时发生：

- 模型本身足够强，能支撑多步推理
- 工具和协议生态成熟，外部行动变便宜
- 企业和开发者对“帮我完成任务”而不只是“帮我回答问题”的需求快速上升

## 6. 怎么用

### 6.1 场景一：深度研究

最典型的 agentic loop 场景就是 research。

为什么 research 特别适合它：

- 问题路径依赖强
- 新发现会改变下一步方向
- 很多线索彼此并行
- 输出前必须验证来源质量

一个好的研究 loop 通常会是：

`question -> split subquestions -> search -> read -> compare -> identify gaps -> search again -> synthesize -> cite -> stop`

### 6.2 场景二：编码和调试

编码任务其实也是天然循环任务。

典型路径：

`read code -> form hypothesis -> patch -> run tests -> read failures -> refine patch -> rerun -> stop`

为什么很多“AI 写代码” demo 看起来会翻车：

- 因为它们只有 `generate patch`
- 没有完整的 `verify and revise`

一旦进入真实工程环境，缺少验证环的代码代理很难长期可靠。

### 6.3 场景三：浏览器和 GUI 操作

当 agent 要真正操作页面时，它必须：

- 观察页面
- 判断当前状态
- 采取动作
- 看动作是否生效
- 修正策略

这使得 agentic loop 与传统脚本自动化的区别变得很明显：

- 脚本自动化依赖固定路径
- agentic loop 依赖反馈自适应

### 6.4 场景四：企业后台流程

例如：

- 客服升级单
- 法务材料整理
- 财务核对
- 销售情报研究

这些任务的特点是：

- 半结构化
- 高频
- 多系统
- 需要留痕

agentic loop 在这里最有价值的，不是替代所有审批，而是把“收集、整理、初步判断、准备交付”自动化。

### 6.5 实战切入方式

如果你要自己实践，不建议一开始就做“大而全自治 agent”。更靠谱的起点是：

`single goal + 1 or 2 tools + explicit state + explicit verify + explicit stop`

一个最小工作流示例：

```text
你现在以 agentic loop 方式工作。

任务：研究“为什么很多 AI agent 在长任务里会失控”。

约束：
1. 先拆成 4 个待验证子问题。
2. 每轮只做一个动作：search / read / compare / summarize。
3. 每轮输出：
   - current_goal
   - chosen_action
   - observation
   - impact_on_hypothesis
   - next_action
   - stop_or_continue
4. 如果证据不足，继续循环。
5. 如果已经足够回答，停止并给出最终结论和证据链。
6. 优先一手来源，不确定内容标注为推测。
```

这个 prompt 的价值不在于“词写得高级”，而在于它把 loop 的几个关键部件都钉住了：

- 当前目标
- 当前动作
- 观察结果
- 状态更新
- 停止判断

## 7. 深度调研：学术、实践与开源

### 7a. 关键论文

这一层我按“奠基 -> 扩展 -> 强化 -> 组织化 -> 规划化 -> 综述化”的顺序来讲，而不是做孤立论文卡片。

#### 1. ReAct: Synergizing Reasoning and Acting in Language Models

- 作者、年份与出处：Shunyu Yao 等，2022 提交，ICLR 2023
- 论文要解决的问题：
  - 当时关于 LLM 的两类能力往往被分开研究：
    - 一类是 `reasoning`，例如 chain-of-thought
    - 一类是 `acting`，例如在环境中执行动作
  - 作者认为两者分离会带来明显问题：
    - 只推理容易幻觉
    - 只行动又缺少中间计划和可解释性
- 核心贡献：
  - 提出一种交错式轨迹，让模型在同一个任务过程中反复输出 reasoning trace 和 action。
  - reasoning 不再只是“给人看的中间话”，而是用来诱导、追踪和更新行动计划。
  - action 则负责从外部环境中取回新信息，反过来修正推理。
- 方法论摘要：
  - 用 few-shot 提示构造轨迹模板
  - 在问答任务中，action 可调用 Wikipedia API
  - 在交互任务中，action 可作用于环境
  - 环境返回 observation，再进入下一轮 reasoning
- 为什么这个设计重要：
  - 它第一次把 `think -> act -> observe -> think` 写成一个统一结构。
  - 这实际上等于给后来的 agentic loop 奠定了最小工作骨架。
- 关键实验与结论：
  - 在 HotpotQA 和 FEVER 上，ReAct 能通过外部检索减少 chain-of-thought 常见的幻觉和错误传播。
  - 在 ALFWorld 和 WebShop 等交互决策基准上，它在极少示例的情况下就能超过模仿学习和强化学习基线。
  - 论文特别强调生成的人类可读轨迹更容易解释和审计。
- 局限性：
  - 强依赖 prompt 设计
  - 仍然是单条线性轨迹
  - 没有显式长期记忆
  - 没有系统化处理停止条件和预算
- 影响力判断：
  - ReAct 不是唯一源头，但它几乎是最清晰的奠基工作之一。
  - 今天很多 agent framework 虽然不显式叫 ReAct，但在轨迹设计上都能看见它的影子。

#### 2. Toolformer: Language Models Can Teach Themselves to Use Tools

- 作者、年份与出处：Timo Schick 等，2023，NeurIPS 2023
- 论文要解决的问题：
  - 大模型在语言任务上很强，但在算术、事实查询、日期推理等方面常常不如更简单的专用工具。
  - 问题不只是“模型没知识”，而是“模型不知道什么时候该把任务交给工具”。
- 核心贡献：
  - 提出 Toolformer，让模型以自监督方式学习：
    - 是否需要调用某个 API
    - 什么时候调
    - 调用参数是什么
    - 工具返回值如何进入后续 token 预测
- 方法论摘要：
  - 先给少量 API 使用演示
  - 再让模型在大语料上自生成潜在工具调用位置
  - 用过滤策略保留真正有帮助的调用样本
  - 最后继续训练模型
- 为什么这个设计重要：
  - 它把工具调用从纯 prompt 技巧推进到“可学习行为”。
  - 这对 agentic loop 非常关键，因为 loop 的行动层不能永远依赖人手搓模板。
- 实验与结论：
  - 论文引入了计算器、问答系统、搜索引擎、翻译系统和日历等工具。
  - 结果显示，在零样本任务中，Toolformer 能显著优于未接工具的语言模型，而且不损害原有语言建模能力。
- 局限性：
  - 工具集合相对有限
  - 更接近“学会工具使用”而不是完整长链任务闭环
  - 对开放工具生态和复杂环境反馈的讨论还不充分
- 影响力判断：
  - Toolformer 很重要，因为它把 `act` 这件事变成了模型本体应掌握的能力，而不只是外部 orchestration 的补丁。

#### 3. Reflexion: Language Agents with Verbal Reinforcement Learning

- 作者、年份与出处：Noah Shinn 等，2023，arXiv
- 论文要解决的问题：
  - 很多语言 agent 会在 trial-and-error 中重复犯错。
  - 传统 RL 需要大量样本和昂贵微调，不适合快速迭代的语言 agent 场景。
- 核心贡献：
  - 不通过更新参数来学习，而是通过“语言化反馈”学习。
  - 让 agent 在失败后写下 verbal reflection，并保存进 episodic memory，用于下一轮决策。
- 方法论摘要：
  - agent 完成一次尝试
  - 从环境或内部模拟得到反馈
  - 生成自然语言反思
  - 把反思写入记忆缓冲区
  - 下一次任务时读取这段反思
- 为什么这个设计重要：
  - 它把 `failure -> reflection -> better retry` 正式结构化。
  - 这比单纯重复 loop 更进一步，因为系统开始显式吸收经验。
- 关键结论：
  - 在顺序决策、编程、语言推理等任务中都有明显改进。
  - 论文报告在 HumanEval 上取得比当时 GPT-4 更强的 pass@1。
- 更值得注意的地方：
  - 论文做了反馈信号类型、反馈接入方法和 agent 类型的消融分析。
  - 这说明作者并不是只证明“有效”，还在研究“为什么有效、什么条件下有效”。
- 局限性：
  - 反思本身可能带噪声
  - 如果反馈质量差，反思会把误导写进记忆
  - 还缺少对长期记忆污染和错误固化的充分讨论
- 影响力判断：
  - Reflexion 把 agentic loop 从“执行闭环”推进成“反思闭环”，是后续很多 self-improving agent 思路的关键前驱。

#### 4. Voyager: An Open-Ended Embodied Agent with Large Language Models

- 作者、年份与出处：Guanzhi Wang 等，2023，arXiv
- 论文要解决的问题：
  - 许多 agent 能解决局部任务，但难以在开放世界中长期探索、积累技能并迁移到新任务。
- 核心贡献：
  - 构建一个 Minecraft 中的开放世界 lifelong learning agent。
  - 引入三大核心部件：
    - automatic curriculum
    - ever-growing skill library
    - iterative prompting with environment feedback, execution errors, and self-verification
- 方法论摘要：
  - 自动课程负责决定下一步探索目标
  - 每次成功行为被沉淀为可执行代码技能
  - 新任务优先检索并复用技能库，而不是从头开始
  - 失败时根据环境反馈和执行错误改程序
- 为什么这个设计重要：
  - 它展示了 agentic loop 不必局限于文本任务，可以进入开放环境。
  - 更重要的是，它把“循环”从单任务层拓展到了长期技能积累层。
- 实验与结论：
  - 与 prior SOTA 相比，Voyager 拿到更多独特物品、更远探索距离，并更快解锁科技树。
  - 它还能把技能库迁移到新世界中解决新任务，而许多基线方法泛化较差。
- 局限性：
  - 环境特定性强
  - 依赖高质量模型
  - 技能库管理本身可能越来越复杂
  - 真实业务系统比 Minecraft 环境脏得多，迁移不直接
- 影响力判断：
  - Voyager 让大家真正看到“loop + memory + executable skills”可以形成长期复利，而不是一次次孤立试错。

#### 5. AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation

- 作者、年份与出处：Qingyun Wu 等，2023，arXiv
- 论文要解决的问题：
  - 随着 agent 任务变复杂，单个 agent 往往难以同时承担规划、执行、审阅、工具操作和人类交互。
  - 开发者需要一种更通用的方式组织多个 agent 协同完成任务。
- 核心贡献：
  - 提出一个多代理会话式框架，让多个可定制 agent 通过自然语言或代码定义的交互模式完成任务。
- 方法论摘要：
  - agent 可由 LLM、工具、人类输入等组成
  - 交互模式可以被编程
  - 开发者可构造 assistant、user proxy、tool executor 等不同角色
- 为什么这个设计重要：
  - 它把单代理 loop 扩展成“多代理 loop 的编排问题”。
  - 从此以后，社区开始广泛讨论 orchestrator、worker、critic、reviewer 等角色。
- 关键结论：
  - 论文展示了数学、编码、问答、运筹、在线决策等多种应用。
  - 更重要的是，它降低了开发者实验多代理模式的门槛。
- 局限性：
  - 很多结果来自框架示例，而不是统一严格 benchmark
  - 多代理带来的 coordination overhead 后来被证明不可忽视
- 影响力判断：
  - AutoGen 对社区影响非常大。即使今天官方仓库已进入 maintenance mode，它依旧是多代理工程化历史中的关键节点。

#### 6. Language Agent Tree Search Unifies Reasoning Acting and Planning in Language Models

- 作者、年份与出处：Andy Zhou 等，2023，ICML 2024
- 论文要解决的问题：
  - 许多语言 agent 仍采用较简单的 act loop，缺乏系统化规划。
  - 单轨迹 agent 容易走进局部最优或早期错误路径。
- 核心贡献：
  - 提出 LATS，把 Monte Carlo Tree Search、LM-powered value function、自反思和环境反馈统一进一个通用框架。
  - 不只是行动，更强调 deliberative planning。
- 方法论摘要：
  - 每个节点代表某种中间状态或思路
  - 模型生成候选动作和后续 reasoning
  - 环境和 value function 共同给出质量反馈
  - 树搜索决定继续扩哪条路径
- 为什么这个设计重要：
  - 它证明 agentic loop 不一定只能线性推进。
  - 当任务空间复杂时，树搜索式 loop 能显著提升探索质量。
- 关键结论：
  - 在编程、交互问答、web navigation、数学等多域表现强。
  - 论文报告在 HumanEval 上获得 92.7% pass@1，并在 WebShop 上达到接近梯度微调系统的表现。
- 局限性：
  - 成本高
  - 设计复杂
  - 并不是每个业务任务都值得上树搜索
- 影响力判断：
  - LATS 代表了 agentic loop 的一个重要前沿：从“会循环”升级到“会搜索路径空间”。

#### 7. A Survey on Large Language Model based Autonomous Agents

- 作者、年份与出处：Lei Wang 等，2023 首版，2025 仍在更新
- 论文要解决的问题：
  - 领域快速爆炸式增长，缺乏统一视角整理 agent 构件、应用与评估方法。
- 核心贡献：
  - 给出一个统一框架，总结大多数 LLM autonomous agents 的构造方式。
  - 系统整理应用领域与评估策略。
- 为什么这篇综述重要：
  - 它让“agentic loop”不再只是零散案例，而有了更清楚的模块化视角：
    - profile
    - memory
    - planning
    - action
  - 同时也把评估问题提升到一等公民位置。
- 局限性：
  - 综述必然滞后于最新工程实践
  - 很难覆盖所有新框架和产品系统
- 影响力判断：
  - 对学习者来说，它的价值不在于单个结论，而在于帮助建立稳定视角：agent 研究究竟由哪些可组合部分构成。

#### 论文脉络总结

如果把这些论文串起来看，`agentic loop` 的演化链大致是：

- ReAct：证明 `reasoning + acting` 可以交错
- Toolformer：让工具使用变成可学习行为
- Reflexion：把失败经验写回 loop
- Voyager：把 loop 扩展到长期技能积累
- AutoGen：把 loop 组织成多代理系统
- LATS：把 loop 从线性推进升级到带搜索规划
- Survey：把整个领域模块化总结

这条脉络说明一个很重要的事实：`agentic loop` 并不是一个单点发明，而是一整条能力链逐步闭合后的结果。

### 7b. 最佳实践

#### 1. Anthropic：把 loop 明确定义成 `gather context -> take action -> verify work -> repeat`

- 来源：Anthropic《Building agents with the Claude Agent SDK》
- 实践内容：
  - 先把 agent 看成一个反馈回路，而不是一个超级 prompt。
  - 上下文获取、行动能力、校验方式分别设计。
  - 明确强调 subagents、compaction、tool design、visual feedback、LLM judge。
- 为什么它算最佳实践：
  - 因为它抓住了 agent 可靠性的核心，不是“让模型多做事”，而是“让模型有办法判断自己做得对不对”。
  - 许多团队的 agent 失败，并不是因为不会行动，而是因为没有验证回路。
- 适用边界：
  - 非常适合 research、coding、file workflow、knowledge work。
  - 对极短且确定的任务可能过重。

#### 2. Anthropic：多代理 Research 系统中的 orchestrator-worker 模式

- 来源：Anthropic《How we built our multi-agent research system》
- 实践内容：
  - lead agent 负责规划、分解和综合
  - subagents 并行搜索和过滤
  - 结果回流给 lead agent
  - 最后交给 citation 代理做归因
- 为什么它算最佳实践：
  - 它不仅展示多代理能用，还非常明确说明：
    - 怎样委派
    - 怎样按复杂度分配 effort
    - 怎样控制 subagent 数量
    - 怎样避免无限搜索
    - 怎样做 outcome-based eval
- 量化效果：
  - Anthropic 报告 multi-agent research system 在内部 research eval 上比单代理版本高 90.2%。
  - 并行工具调用和并行 subagents 可让复杂研究查询耗时最多减少约 90%。
- 适用边界：
  - 很适合 breadth-first research。
  - 对高耦合 coding 任务，收益未必这么大。

#### 3. OpenAI：把 handoff、guardrails、sessions、tracing 做成框架内置能力

- 来源：OpenAI Agents SDK 官方文档与 `openai/openai-agents-python`
- 实践内容：
  - SDK 核心概念直接包括：
    - agents
    - agents as tools / handoffs
    - tools
    - guardrails
    - human in the loop
    - sessions
    - tracing
- 为什么它算最佳实践：
  - 因为它提醒开发者：生产 agent loop 不只是“会调用工具”，还必须有：
    - 状态持续
    - 安全约束
    - 可观测性
    - 可调试性
    - 人类介入接口
- 适用边界：
  - 适合真正想上线而不是只做 demo 的系统。

#### 4. LangGraph：把 agent loop 建模为 stateful graph

- 来源：LangGraph 官方仓库
- 实践内容：
  - 强调 durable execution
  - human-in-the-loop
  - comprehensive memory
  - debugging
  - production-ready deployment
- 为什么它算最佳实践：
  - 它抓住了长任务 agent 的本质问题：
    - 任务可能失败
    - 失败后要恢复
    - 状态要持久化
    - 需要可调试
  - 这比只给一个 tool-calling wrapper 深得多。
- 适用边界：
  - 适合长任务、需恢复、需持久状态的系统。

### 7c. 开源项目

#### 1. LangGraph

- 项目：`langchain-ai/langgraph`
- 地址：<https://github.com/langchain-ai/langgraph>
- Star 数量级：约 29.2k
- 维护者：LangChain AI
- 它做了什么：
  - 一个低层 orchestration framework，用图和状态来表达长运行 agent。
- 技术选型：
  - Python 为主
  - 用 graph/state 结构组织任务流

## 8. 我的项目实践分析

**我的项目仓库**：

- `https://github.com/diffw/Vibe-Capture`
- `https://github.com/diffw/harness-coding`

这两个仓库都在用 `agentic loop`，但使用层级不同：

- `harness-coding`：loop 基础设施仓库
- `Vibe-Capture`：接入该基础设施的宿主产品仓库

### 8a. 概念识别

#### 一、`harness-coding` 中的实践痕迹

这个仓库不是“顺手用了一点 agent 思路”，而是非常明确地把 agentic loop 写进了执行系统。

##### 1. `AGENTS.md`

体现方式：

- 强制区分 `Micro` 与 `Small+`
- 明确执行顺序 `route -> edit -> build -> validate -> summary -> receipt -> reply`
- 明确 `Scope Lock`
- 明确“未过前置步骤不得完成”

这对应了 loop 的哪些部分：

- `route` 对应状态初始化和路径选择
- `edit` 对应行动
- `build / validate` 对应环境观察与验证
- `summary / receipt` 对应结果结构化回流
- `reply` 对应停止后交付

更关键的是，文件里直接写了：

- 不允许把流程缩成 `edit -> build -> reply`
- 只有完成前六步后才能向用户报告完成

这说明 loop 在这里不是一种建议，而是运行时契约。

##### 2. `rules/shared/scope-guard.md`

这是你这个系统里最像“控制器”的文件。

它做了几件非常 agentic 的事：

- 在行动前先输出 Scope Card 锁定状态
- 根据复杂度切换 `Hard Budget / Soft Budget / Phase Gate`
- 允许任务执行中升级风险等级
- 发现低收益循环时强制收敛

这已经不是普通的任务模板，而是非常清晰的 loop policy：

- 如何开始
- 如何控制边界
- 如何识别异常
- 如何决定继续还是收敛

尤其 `Soft Budget` 和 `Phase Gate` 很重要。很多 agent 系统只讨论“能否继续”，你这里已经开始讨论“应该怎样继续”和“何时不值得继续”，这就是成熟 loop 的标志。

##### 3. `rules/shared/execution-receipt.md`

这个文件体现的不是行动，而是 `verification + stop contract`。

它要求：

- 执行类任务必须有回执
- 回执必须包含状态、结论、测试、规则、技能
- 没过 gate 不得说完成

这相当于把“agent 完成”的语义显式化了。很多系统失败就在于：

- agent 自己以为结束了
- 用户并不认可它真的完成了

你这里已经用回执格式把这件事强绑定起来。

##### 4. `scripts/check_execution_receipt.mjs`

这是非常强的证据，因为它把文字规范推进成了程序化 enforcement。

这个脚本会检查：

- 是否有状态
- 是否有 Testing 证据
- 是否在编辑代码后记录了真实测试
- 是否给出 coverage summary
- 是否出现不合理的 passed

也就是说，在 `harness-coding` 里，`verify` 已经不只是“鼓励测试”，而是：

- `reply -> parse -> validate -> accept or reject`

这是一个典型的 agentic loop 收尾结构。

##### 5. `scripts/setup_host_agents.sh` 和 `scripts/update_host_bridge.sh`

这两个脚本说明 `harness-coding` 已经具备“可植入宿主仓库”的能力。

其逻辑大致是：

`host repo -> add .agents submodule -> configure worktree -> update bridge docs -> sync skills -> sync enforcement`

这说明你不是只在一个仓库里内部使用这套 loop，而是在把它包装成可复用 agent operating system。

结论：

- 这是有意识、成体系、完整度较高的 `agentic loop` 实践。
- 它体现得最强的不是“模型智能”，而是：
  - 任务状态锁定
  - 执行阶段划分
  - 验证与回执
  - 异常收敛
  - 宿主扩散能力

#### 二、`Vibe-Capture` 中的实践痕迹

`Vibe-Capture` 的情况更有意思。它不是一个终端用户直接感知到的 AI agent 产品，但它已经把 `agentic loop` 引入到了研发流程。

##### 1. `.gitmodules`

这里最关键的一行是：

- `.agents` 指向 `https://github.com/diffw/harness-coding.git`

这说明：

- 该产品仓库不是自己零散写 agent 规则
- 而是显式把 `harness-coding` 作为外接 loop 基础设施接进来

##### 2. `AGENTS.md`

这个文件几乎复用了 harness 的核心闭环：

- `route -> edit -> build -> validate -> summary -> receipt -> reply`
- Scope Lock
- Validation Scaling
- receipt

区别在于它多了宿主项目上下文，例如：

- 当前目标平台为 macOS
- 需要结合 `.agents/rules/platforms/macos/macos-coding.mdc`

这说明 `Vibe-Capture` 并不是简单复制文本，而是把基础 loop 适配到了具体产品环境。

##### 3. `scripts/run-local-ci.sh`

这个脚本是宿主项目层面的 `verify` 管线：

`localization check -> build -> unit tests -> integration tests -> UI tests`

非常关键的一点是，它不是只跑“某个测试”，而是按验证层级组织反馈链。

这使得 `Vibe-Capture` 中 agent 修改后的反馈路径是清楚的：

- 有没有语言资源问题
- 能不能 build
- 核心逻辑是否稳定
- 模块联动是否稳定
- UI 是否还活着

##### 4. `scripts/run-dev.sh`

这是一个轻量但很有代表性的 agentic loop 脚本。

它做了：

- 清理旧状态
- build
- 失败时看错误模式
- 若缺签名证书则切换到 unsigned build
- 重试
- 成功后自动打开 app

这个结构非常像最小 loop：

`clean -> build -> observe error -> adjust strategy -> retry -> launch`

它虽然不是 LLM 在做决策，但逻辑上已经具备 agent loop 的雏形。

##### 5. `DEV_WORKFLOW.md`

这个文档明确约定：

- 当 AI 完成会影响 app 行为的改动后，应优先执行 `./scripts/run-dev.sh`
- 验收时可执行 `./scripts/run-local-ci.sh`

这说明 loop 已经嵌入团队工作约定，而不是“写在 README 里但没人真这么做”。

结论：

- `Vibe-Capture` 确实在使用 `agentic loop`
- 但它主要体现在 **AI-assisted development loop**
- 不是说这个截图产品本身 runtime 内已经存在一个 end-user facing autonomous agent

#### 做得好的地方

##### 1. 你已经把 loop 从概念层落到了操作系统层

很多团队的 agent 还停留在：

- 一个 prompt

但 `harness-coding` 已经把 loop 变成：

- router
- rules
- skills
- receipts
- enforcement scripts
- host bridge

这说明你学到的不是“agent 会不会回答”，而是“agent 怎样稳定完成工作”。

##### 2. 基础设施与业务仓库已经分层

`harness-coding` 负责：

- loop policy
- 执行规则
- 通用 skills
- 桥接脚本

`Vibe-Capture` 负责：

- 宿主上下文
- 平台特定规则
- build/test 验证链
- 真实业务代码

这个分层很成熟，因为它避免了每个业务仓库都重新发明一套 agent loop。

##### 3. 你特别重视验证闭环

这是你这两个项目里最强的一点。

不仅有：

- test
- build
- CI

还有：

- execution receipt
- receipt validation
- scope guard
- low-yield loop detection

这说明你已经意识到：agent 的关键不只是“能干”，更是“能不能证明它干对了”。

##### 4. 你已经在思考“经济性”和“收敛”

`Soft Budget`、`Hard Budget`、`Phase Gate`、`低收益循环优先收敛` 这些设计都很成熟。

因为 agentic loop 的真正难点从来不是让系统多转几圈，而是：

- 哪些圈值得转
- 哪些圈应该立刻停

#### 存在的差距

##### 1. 当前 loop 仍偏“规则驱动”，还不够“证据自适应”

你现在的系统很强，但主要强在：

- 规则明确
- 阶段明确
- 验证明确

相对较弱的是：

- 自动根据任务轨迹学习更好的策略
- 自动在历史经验中检索相似失败模式
- 自动调整 effort policy

也就是说，它已经是成熟执行系统，但还没有完全进化成“会自我优化的执行系统”。

##### 2. 长期记忆层较弱

现在有：

- receipts
- changelog
- docs

但还缺少统一的“经验知识层”，例如：

- 哪类任务最容易低收益循环
- 哪类测试最常被误用
- 哪类 bug 最适合 Phase Gate
- 哪类规则经常导致过度收敛

这类内容如果不结构化沉淀，就很难让 loop 真正跨任务成长。

##### 3. `Vibe-Capture` 的 agentic 特征主要在研发流程，不在产品 runtime

这不是缺点，但如果你的学习目标是“把 agentic loop 作为产品能力”，那你目前还主要停留在 dev workflow 层。

换句话说：

- 你已经很会用 agentic loop 来开发产品
- 但还没有把 agentic loop 直接做成产品本身的一等功能

##### 4. 多代理与协议层还有扩展空间

虽然 harness 已经有强 loop，但从证据看：

- 还未明显形成正式多代理策略体系
- 也还未明显引入协议级互操作，如 MCP/A2A 风格的 agent-agent 编排层

这意味着你目前的系统更像“单执行代理 + 强治理”，而不是“可扩展 agent mesh”。

#### 潜在风险

##### 风险 1：规则膨胀导致 agent 僵化

规则越强，可靠性通常越高；但规则越多，也越可能出现：

- agent 为了满足规则而忽略真实证据
- 对少数特殊任务过度约束
- 本来应该快速完成的任务被流程拖慢

##### 风险 2：宿主桥接可能漂移

`Vibe-Capture` 通过 `.agents` submodule 接入 `harness-coding` 是很好的做法，但也带来一个问题：

- 宿主文档、hooks、skills、rules 的同步链路较长
- 一旦桥接脚本或同步流程漂移，宿主项目可能跑在“半更新”状态

##### 风险 3：测试成本高时，loop 容易被人类绕过

理论上验证链很完整，但如果：

- build 很慢
- UI test 容易 flaky
- 本地环境不稳定

那真实协作时最可能被跳过的，往往就是 `validate` 和 `receipt`。

##### 风险 4：回执检查强，但策略正确性评估还可以更强

现在你已经很会检查：

- 有没有测
- 有没有写状态
- 有没有 coverage summary

下一步更高阶的问题是：

- 这条 loop 选路是不是高效
- 有没有本可提前停的步骤
- 有没有本可更便宜的验证层

## 9. 阅读问答与实践补充

这一节不是重复前文，而是专门回应“读完文档后进一步追问”的部分。它的目标不是再定义一次 `agentic loop`，而是把前文里最容易抽象化、最容易和真实项目脱节的地方拉回到工程实践。

### 9.1 关于工具调用：到底应该怎么约束 AI

你的问题可以拆成三个层面：

- 应该用什么来约束 AI 的工具调用
- 可用工具是如何提供给 AI 的
- 是否需要事先把这些工具写进文档

先说结论：**不要把“工具调用约束”只理解成一份规则文档。真正有效的约束必须是分层的。**

一个比较成熟的结构通常是：

```text
目标与流程层
  AGENTS.md / system prompt / skill
  作用：规定这类任务应该怎么做

能力暴露层
  内建工具 / MCP / plugin / shell scripts / APIs
  作用：规定 agent 实际能调用什么

权限边界层
  sandbox / allowlist / approval policy / network policy
  作用：规定 agent 哪些事情不能直接做

行为审查层
  hooks / validators / receipts / tests
  作用：规定 agent 做完之后怎样被检查
```

也就是说：

- `Rules` 不是全部
- `Skills` 不是全部
- `工具 schema` 不是全部
- `permission` 也不是全部

真正可靠的做法是把它们组合起来。

再具体一点，约束工具调用通常要回答 5 个问题：

```text
1. 什么时候允许调用工具
2. 允许调用哪些工具
3. 调用前要满足什么前置条件
4. 调用后必须观察什么反馈
5. 什么情况下必须停止或升级给人
```

如果你只写“可以调用 Bash / Browser / Web”，这只是告诉 agent 有刀可以用，但没有告诉它：

- 什么时候该拔刀
- 拔哪把刀
- 拔完之后怎么确认没砍偏

所以文档当然要写，但文档写的应该是“策略”，不是“替代工具本身”。

#### 文档到底该写什么

最值得事先写进文档的，不是每个工具的所有细节，而是这 4 类信息：

```text
1. tool selection policy
2. preconditions
3. verification requirements
4. escalation policy
```

例如一个成熟文档不会只写：

```text
可调用 shell
```

而会写成：

```text
若任务涉及代码修改：
  先读相关规则
  再最小化编辑
  编辑后必须运行受影响验证
  未跑验证不得宣称完成
```

你自己的项目其实已经开始这样做了。

- [Vibe-Capture/AGENTS.md](/Users/diffwang/NWA/Vibe-Capture/AGENTS.md:58) 定义了上下文加载顺序、验证和回执要求。
- [harness-coding/AGENTS.md](/Users/diffwang/NWA/harness-coding/AGENTS.md:57) 进一步把预算、收敛和监督模式写清楚。

这些都属于“工具调用策略层”，而不是“工具实现层”。

#### 可用工具是如何提供给 AI 的

工具提供方式大体有 4 类：

```text
1. 系统内建工具
2. MCP server
3. 插件 / 扩展
4. 项目脚本通过 shell 间接暴露
```

### 9.2 关于环境反馈：它到底是不是“人的参与”

不是。人只是环境反馈的一种来源，不是全部。

更准确的理解方式是：

```text
agent action -> external world -> observable signal
```

这里的 `observable signal` 可以来自很多地方：

- 编译器
- 测试框架
- shell 退出码
- 日志
- 文件系统变化
- API 响应
- 浏览器页面内容
- GUI 状态
- 数据库状态
- 人的确认与否

所以“环境反馈”不是“有人一直盯着 agent 给意见”，而是：

```text
只要 agent 的动作作用到了外部世界
外部世界返回的任何可用信号
都属于环境反馈
```

#### 人的反馈不全面、也不可能一直在线，这怎么办

你提的问题非常关键。一个成熟系统不能把主要反馈链建立在人类持续在线上，因为这会直接毁掉 agent 的可扩展性。

比较成熟的工程原则是：

```text
机器信号优先自动化
人类信号只保留在高价值节点
```

也就是：

- 编译结果 -> 机器
- 测试结果 -> 机器
- 日志 -> 机器
- 文件变更 -> 机器
- UI 自动化结果 -> 机器
- 是否扩边界 / 是否接受风险 / 是否改变目标 -> 人

所以人类最应该参与的不是“帮 agent 看日志”，而是：

- 目标是否变了
- 风险是否接受
- 任务边界是否扩大
- 某种 tradeoff 是否值得

### 9.3 “显式状态”与“环境观察”分别是什么意思

这两个概念很容易混在一起，但它们不是一回事。

#### 一、显式状态

显式状态指的是：**agent 或其框架主动写出来、供后续使用的当前任务状态。**

例如：

- 当前目标是什么
- 已经改了哪些文件
- 是否跑过 build
- 是否跑过 test
- 当前处在什么阶段
- 当前预算剩多少
- 当前 stop block 次数是多少

它的关键特征是：

```text
不是“自然存在”
而是系统主动整理并保存
```

在你的项目里，显式状态已经存在，而且非常明确：

- [null.harness-state.json](/Users/diffwang/NWA/Vibe-Capture/null.harness-state.json:1)
- [harness-user-prompt-submit.mjs](/Users/diffwang/NWA/Vibe-Capture/.claude/hooks/harness-user-prompt-submit.mjs:7)
- [harness-post-tool-use.mjs](/Users/diffwang/NWA/Vibe-Capture/.claude/hooks/harness-post-tool-use.mjs:18)
- [common.mjs](/Users/diffwang/NWA/Vibe-Capture/.claude/hooks/common.mjs:18)

这些文件说明你的系统已经会记录：

```text
prompt
editedPaths
editedCode
editedLocalization
editedDocs
buildRan
testRan
localizationCheckRan
stopBlocks
```

这就是显式状态。

#### 二、环境观察

环境观察指的是：**agent 采取动作后，从外部世界读回来的结果。**

比如：

- `xcodebuild` 报错
- UI test 失败
- 页面结构变化
- web search 返回空结果
- 某个命令 exit code 不为 0
- 某个文件内容和预期不一致

它的关键特征是：

```text
不是 agent 自己声明的
而是环境返回给 agent 的
```

可以这样区分：

```text
显式状态 = 我现在处于什么任务状态
环境观察 = 外部世界刚刚告诉了我什么
```

再用一个非常简单的流程表示：

```text
Edit file
  -> environment changes
  -> run test
  -> test fails
  -> observe failure
  -> update explicit state
  -> choose next action
```

也就是说：

- `test fails` 是环境观察
- `testRan = true` 是显式状态

这两者都重要，但职责不同。

### 9.4 ReAct 到底是什么

ReAct 是一篇非常关键的论文，它的核心贡献不是“让模型多想一点”，而是把 `reasoning` 和 `acting` 接成一个回路。

最简形式可以写成：

```text
Thought -> Act -> Observation -> Thought -> Act -> Observation
```

其中：

- `Thought`：模型当前对问题的理解、假设、推理
- `Act`：模型采取动作，例如搜索、查文档、调工具
- `Observation`：环境返回结果

ReAct 的重要性在于，它不再假设模型一开始就知道所有东西，而是允许模型：

- 先做一件事
- 再根据结果修正想法
- 再决定下一步

这和传统单轮生成最大的区别是：

```text
单轮生成：
  input -> answer

ReAct：
  input -> think -> act -> observe -> think -> act -> observe -> answer
```

它可以看作很多后续 agent loop 实践的早期雏形。

但也要注意：ReAct 本身并不自动等于“成熟 agent 系统”。

因为一个成熟 agent loop 往往还要补上：

- state
- memory
- verification
- stop condition
- guardrails
- task handoff
- tracing

所以更准确地说：

```text
ReAct 是 agentic loop 的重要前身
不是完整终点
```

### 9.5 在 Codex 和 Claude Code 里如何使用多代理

这是一个特别值得讲清楚的问题，因为“多代理”非常容易被过度神化。

#### 一、Codex 里的多代理

Codex 的多代理更接近“明确分工的 subagents”。比较合理的理解是：

```text
main agent
  -> explorer
  -> reviewer
  -> worker
  -> docs helper
main agent 汇总和整合
```

它最适合的是：

- 探索任务并行化
- 把不同责任拆开
- 让主上下文不要被边角工作塞满

最适合的使用场景：

```text
1. 多个独立问题可以并行探索
2. 代码库很大，需要多个只读侦察线程
3. 写代码和做验证可以分工
4. 文档整理与主实现可以并行
```

不适合的场景：

```text
1. 单文件小修
2. 任务高度顺序依赖
3. 多个代理会抢同一批文件
4. 主代理自己都还没定义清楚任务边界
```

在 Codex 里，多代理最关键的规则不是“多开几个代理”，而是：

```text
谁拥有哪个文件
谁只读
谁可写
何时等待结果
哪些结果只做参考
谁负责最终整合
```

一个很稳的模式是：

```text
explorer = 只读
reviewer = 只读
worker = 可写
main agent = 路由和整合
```

#### 二、Claude Code 里的多代理

Claude Code 里常见的是两层：

```text
sub-agents
agent teams
```

- `sub-agents` 更像专职工种
- `agent teams` 更像多成员协同系统

`sub-agents` 适合：

- 把某类任务长期固定给某个角色
- 让主代理不必每次重复塞角色说明

`agent teams` 适合：

- 多个 agent 真正并行
- 彼此需要通信
- 任务跨度大
- 需要跨会话协作

#### 三、什么时候该用多代理，什么时候不该用

可以用一个很朴素的判断：

```text
任务能否被拆成多个低耦合子问题
```

如果答案是“能”，多代理通常有价值。

例如：

```text
主任务：修一个复杂功能回归

代理 A：读 spec
代理 B：读测试失败日志
代理 C：定位最近改动
主代理：汇总，决定 patch
```

如果答案是“不能”，多代理反而会增加协调成本。

例如：

```text
主任务：修改同一个 view controller 的布局问题
```

这种任务拆成多代理通常没有收益。

#### 四、如何设定多代理规则

最重要的不是写很多“个性描述”，而是写清楚下面这些边界：

```text
1. role
2. ownership
3. read/write scope
4. output contract
5. stop conditions
```

一个好用的多代理规则模板通常长这样：

```text
Role:
  你负责什么

Ownership:
  你对哪些文件或问题负责

Restrictions:
  你不能做什么

Deliverable:
  你必须产出什么

Escalation:
  遇到什么情况必须交还主代理
```

如果没有这些，多代理就很容易退化成：

```text
大家都在干活
但没人真正负责
```

### 9.6 核心机制里的 `Verify`：标准是什么，怎么建立

#### 一、Verify 的标准是什么

`Verify` 不是一个单一标准，而是一组 gate。

通常至少包括：

```text
1. correctness
2. completeness
3. regression safety
4. spec alignment
5. reproducibility
6. boundary compliance
```

如果翻成开发语言，就是：

- 结果是不是对的
- 是不是做完了，而不是只做了一半
- 有没有把别的地方搞坏

### 9.10 Memory：怎么建立，最后落成什么，哪些该放进去

Memory 非常容易被空泛化。最直接的说法是：

```text
Memory = 让系统不要每次都从零开始
```

但它不是单一文档，而是分层结构。

#### 一、Working Memory

这是当前任务的临时记忆，生命周期很短。

典型内容包括：

- 当前目标
- 当前假设
- 当前已改文件
- 当前测试是否已执行
- 当前阻塞点

在你的项目里，最接近 working memory 的东西就是：

- Scope Card
- `.harness-state.json`
- 当前回合的 receipt 约束

#### 二、Episodic Memory

这是“某一次任务、某一次事故、某一次调试经历”的记忆。

它描述的是：

```text
发生了什么
为什么发生
怎么修
验证结果如何
以后有什么启发
```

你项目里比较接近 episodic memory 的东西有：

- incidents
- postmortems
- acceptance reports
- feature review reports

例如 `.vibe-doc/reports/` 和 `.vibe-doc/incidents/` 下的很多文档，其实已经是 episodic memory 的雏形。

#### 三、Long-Term Memory

这是应该改变未来默认行为的稳定知识。

例如：

- 修改本地化后必须跑 localization check
- 某类问题优先用 targeted tests 而不是 full UI tests
- 某类 bug 必须走 Phase Gate
- 某些路径高风险，不能走 Micro

这类内容最适合进入：

- AGENTS
- rules
- skill
- stable knowledge docs

#### 四、Memory 的建立过程是什么样

比较合理的过程是：

```text
task happens
  -> observations collected
  -> outcome known
  -> extract lesson
  -> classify lesson
  -> write to memory layer
  -> future tasks retrieve it
```

更细一点可以写成：

```text
raw observation
  -> summarized episode
  -> reusable heuristic
  -> promoted rule or long-term note
```

这也是为什么我前面一直强调：你不只是要“有文档”，而是要有“从 observation 到 memory 的升级路径”。

#### 五、最终落实时，是文档还是别的

最好是“结构化记录 + 人类可读文档”并存。

最低成本的形式可以是：

```text
.vibe-doc/memory/
  working/current-task.json
  episodes/YYYY-MM-DD-<slug>.md
  knowledge/patterns.md
  knowledge/decisions.md
  knowledge/index.json
```

这样做的好处是：

- 人能读
- agent 能检索
- 后续也容易接到 MCP

#### 六、开发过程中哪些内容需要放进 memory

最值得放进去的，是“以后还会重复遇到，而且影响决策质量”的内容。

例如：

- 常见失败模式
- 高价值验证路径
- 某类 bug 的首选排查方法
- 平台环境坑
- 决策 tradeoff
- 经常被人绕过的高风险步骤

不值得放进去的，是：

- 一次性的噪音日志
- 没验证过的猜测
- 当前机器上的临时路径
- 不可复用的过程碎片

#### 七、怎么判断该不该写进 memory

一个很实用的标准是：

```text
If only this task needs it:
  Working Memory

If it explains one specific run and may help similar future runs:
  Episodic Memory

If it should change future default behavior:
  Long-Term Memory
```

你可以再加一个写入门槛：

```text
满足下面任一条件，就考虑写入：
1. 同类失败出现 >= 2 次
2. 事故级别 >= medium
3. 需要改变未来默认验证或执行策略
4. 这个经验跨功能、跨任务可复用
```

### 9.11 协议化互操作：MCP 和 A2A 在你项目里实践得如何

结论先说：**还没有真正开始。**

我在你这两个项目里，没有看到明确的 MCP 或 A2A 协议化实践痕迹。你现在主要是：

```text
local scripts
hooks
rules
submodule bridge
```

这说明你已经有“agent workflow”，但还没有“协议化互操作层”。

#### 一、MCP 是什么

MCP 的价值，不是“多一个名词”，而是：

```text
把工具暴露成标准化接口
让不同 agent / client 以统一方式访问
```

它解决的是：

- 工具接入不统一
- agent 换一个宿主就要重接一遍
- 结构化工具面太零散

#### 二、A2A 是什么

A2A 更偏“agent 和 agent 之间如何协作”，而不只是“agent 调工具”。

它解决的是：

- agent 间任务交接
- agent 间状态传递
- agent 间结果协议化
- 跨系统 agent 编排

#### 三、对你来说，最低成本应该先做什么

我不建议你现在直接上 A2A。对你的项目来说，最低成本、最高收益的起点是：

```text
先做 MCP
后看是否真的需要 A2A
```

原因很简单：

- 你已经有很多本地脚本
- 你已经有很多验证命令
- 你已经有很多文档读取需求
- 这些东西最适合先封成工具

#### 四、最小化成本的 MCP 实践建议

第一批最值得暴露成 MCP 的工具，我建议是：

```text
Vibe-Capture:
  run_local_ci
  run_dev
  check_localization
  read_product_spec
  list_test_cases
  read_latest_incident

harness-coding:
  validate_execution_receipt
  suggest_validation_level
  read_scope_guard
  read_execution_policy
  check_host_bridge
```

这样做的好处是：

- 不需要推翻现有架构
- 直接复用现有脚本
- 立刻提升 agent 可组合性
- 为后面多 agent 协作打底

#### 五、什么时候再考虑 A2A

只有当你出现下面这种需求时，A2A 才真正开始值得：

```text
agent A 发现问题
agent B 执行修复
agent C 做验收
他们需要跨会话、跨系统、异步协作
```

在你当前阶段，我认为这还不是最优先的投资点。

### 9.12 对 8b 实践评估的进一步展开

你特别提到 8b 里的几句判断，这里逐条展开。

#### 一、为什么说你已经是成熟执行系统，但还不是“会自我优化的执行系统”

因为你已经具备：

```text
route
edit
build
validate
receipt
reply
```

这说明执行闭环已经相当成熟。

但“自我优化”要求更多：

```text
execution trace
  -> lesson extraction
  -> memory update
  -> policy refinement
  -> future default improvement
```

你现在的系统虽然会留下 receipts、reports、postmortems，但还没有形成一条稳定的自动回写链。

所以它更像：

```text
会执行
会检查
会记录
```

但还不够像：

```text
会从记录中自动提炼经验
并改变下次默认做法
```

#### 二、为什么说缺少统一的“经验知识层”

不是说你没有知识，而是这些知识现在分散在不同地方：

- `.vibe-doc/specs/`
- `.vibe-doc/reports/`
- `.vibe-doc/incidents/`
- `.vibe-doc/planning/`
- `.harness-docs/`
- `rules/`
- `AGENTS.md`

问题不是“有没有”，而是：

```text
没有统一索引
没有统一写入标准
没有统一提炼机制
没有统一检索入口
```

这样 agent 在未来任务中很难稳定复用这些经验。

#### 三、为什么说还没明显引入协议级互操作

因为你目前更多是在做：

```text
agent + local repo + local scripts + local hooks
```

还不是：

```text
agent + protocolized tools + protocolized agent handoff + cross-system orchestration
```

这不表示你落后，而是说明你目前仍处在“把单 agent 工作流做扎实”的阶段。

#### 四、为什么说规则膨胀会导致 agent 僵化

规则本来是为了减少错误，但当规则过多、过硬、过细时，会出现反效果。

常见表现包括：

- 小任务也要走大流程
- agent 过度关注形式合规
- 真实证据不够重要，规则文本反而更重要
- 本来应该快速停的任务被拖长
- 规则之间开始互相冲突

最危险的一种情况是：

```text
agent 不是在解决问题
而是在完成流程表演
```

不过你这里有一个积极信号：`harness-coding` 已经明显开始修这个问题了。

例如：

- `Micro` 快车道
- `Soft Budget`
- `低收益循环优先收敛`
- `Autonomous` 下不因超预算机械停机

这说明你已经意识到僵化风险，并且开始往更成熟的 agent policy 演化。

#### 五、针对你项目特点，我最推荐的下一步是什么

如果只能选一条主线，我会建议：

```text
先补 memory / observation / MCP
暂时不要把精力放在复杂多代理编排
```

原因是：

- 你已经有强执行骨架
- 你已经有强验证意识
- 你最缺的是跨任务复用能力
- 你最缺的是协议化工具面

这两件事补起来之后，再谈更复杂的多代理，收益会更高。

### 9.13 一个最现实的落地顺序

如果你现在就想开始实践，我建议按这个顺序做：

```text
Phase 1
  统一 observation 记录

Phase 2
  建 memory 分层目录

Phase 3
  把现有脚本封成 MCP 工具

Phase 4
  增加 lesson extractor

Phase 5
  再考虑多代理和 A2A
```

再具体一点：

```text
第 1 步：
  给每次执行写一个 observation.json

第 2 步：
  建 .vibe-doc/memory/

第 3 步：
  MCP 化 run_local_ci / run_dev / validate_execution_receipt

第 4 步：
  写一个脚本，从 receipt + incident 中提炼 lessons

第 5 步：
  只有当任务已明显可拆分时，再引入稳定多代理
```

这条路线的好处是：

- 不推翻现有结构
- 每一步都直接有收益
- 每一步都在为下一步打基础
