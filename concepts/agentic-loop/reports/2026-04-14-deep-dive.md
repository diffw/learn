## 0. 全景定位

- `Agentic Loop` 不是一个单一论文中被严格定义的标准术语，更像是 2023 年后 AI Agent 工程实践里逐渐稳定下来的“工作闭环”叫法。它通常指：模型不再一次性吐出答案，而是围绕目标反复执行“获取上下文 / 规划 / 调用工具 / 观察结果 / 校验 / 再迭代”。
- 它属于更大的 `LLM-based Agents / Agentic Systems` 领域，处在“单次提示词”与“完整自治系统”之间的核心机制层。你可以把它理解为：Agent 之所以像 agent，而不是像一次性聊天接口，靠的就是这个循环。
- 从工程角度看，`agentic loop` 是连接模型能力与外部世界的中枢：没有它，模型很难稳定完成长链条、可验证、依赖工具和环境反馈的任务。
- 从研究角度看，它把多个原本分散的方向串起来了：推理（reasoning）、行动（acting）、工具使用（tool use）、记忆（memory）、反思（reflection）、规划（planning）和多代理协作（multi-agent orchestration）。

知识地图：

`Prompting / Function Calling / Tool Use / State` → **Agentic Loop** → `ReAct`、`Reflexion`、`LATS`、`Multi-Agent Systems`、`Computer Use Agents`、`Agent Protocols`

前置概念：

- `工具调用（tool use / function calling）`：先理解模型怎样把“说话”变成“调用外部能力”，否则 agent loop 的“行动”部分会显得抽象。
- `状态与反馈（state + feedback）`：agent loop 的本质不是多说几轮，而是让系统根据外部反馈改变下一步行为。

## 1. 一句话定义

- 大白话定义：**让模型边做边看边修正的任务闭环。**
- 日常类比：像做菜时一边下料、一边试味、一边调整火候，而不是开火前一次性把整道菜“想完”。

## 2. 为什么会出现

- 它要解决的根本问题是：很多真实任务并不是“知道题目就能直接答完”，而是必须在执行过程中不断获取新信息、处理意外、检查结果、再决定下一步。
- 传统的单轮 prompt 或固定 workflow 更像流水线：输入问题，输出答案。它适合短任务、规则清晰任务，但一旦任务需要搜索网页、读文件、运行代码、浏览界面、调用 API、等待返回结果、根据结果改计划，这种一次性范式就会迅速失真。
- 旧方法的根本缺陷不只是“模型不够聪明”，而是**系统没有闭环**。没有闭环，模型既不能验证自己，也不能根据环境变化调整策略，只能靠一次生成碰运气。
- 2022 年的 ReAct 把“推理”和“行动”交错起来，提供了一个清晰起点；2023 年 Toolformer、Reflexion、AutoGen、Voyager 等工作进一步把工具调用、反思记忆、多代理协作和自我改进加进来；到了 2025 年前后，Anthropic、OpenAI、LangChain 等工程体系开始把这套闭环直接产品化、框架化。
- 关键抉择主要有几类：
  - 为什么选“迭代式执行”而不是“一次性生成”：因为外部世界是动态的，中间结果本身就是信息。
  - 为什么要让模型显式调用工具，而不是只靠参数知识：因为很多任务需要最新信息、精确计算、文件系统、浏览器和业务系统。
  - 为什么要保留状态、记忆、轨迹和校验，而不是每轮都重来：因为长任务如果没有状态积累，会重复劳动、上下文漂移，并且无法可靠收敛。
  - 为什么有时要从单代理升级到多代理：因为某些任务的瓶颈不是单步推理，而是并行搜索、分工过滤和上下文容量。
- 当时的约束条件也很明确：模型上下文有限、工具接口不统一、推理成本高、评估方法不成熟、错误会级联放大。因此，agentic loop 的演化本质上是在“能力、成本、控制”三角里寻找更稳的平衡。

## 3. 核心机制

用“输入 → 过程 → 输出”解释：

- 输入：目标、初始上下文、可用工具、规则约束、停止条件。
- 过程：
  1. 解析目标，形成当前计划；
  2. 选择下一步动作：思考、搜索、读文件、调用 API、运行代码、委托子代理等；
  3. 从环境拿回观察结果；
  4. 根据观察结果更新状态、记忆和计划；
  5. 校验当前结果是否满足目标，不满足则继续循环；
  6. 达到停止条件后输出结果。
- 输出：答案、报告、代码、文件、决策建议，或一个明确的“无法完成/需要人介入”的结论。

3-5 个关键子概念：

- `State`：循环不是多轮聊天，而是有状态地推进任务。
- `Tool Use`：行动必须能穿透到模型外部世界。
- `Observation`：外部反馈决定下一步，而不是只依赖模型内部猜测。
- `Memory`：把中间发现、失败经验和长期上下文保留下来，避免反复试错。
- `Verification / Stop Criteria`：必须知道何时结束，以及如何判断自己做对了。

第一性原理追问：

- 去掉“观察”，循环会退化成自说自话，系统无法接触真实世界，只能幻觉式推进。
- 去掉“状态/记忆”，每一步都像失忆，长链任务会不停重复搜索、重复犯错。
- 去掉“校验”，错误会沿着循环放大，最后输出看似完整、实则不可用。
- 去掉“工具”，agent loop 会重新退回“文本推理器”，很多任务无法落地。

这说明：`agentic loop` 的本质不是“多调用几次模型”，而是**让模型进入一个可感知、可行动、可自纠偏的闭环系统**。

## 4. 生态位：它和谁像？和谁争？

### 易混辨析

| 概念 | 相同点 | 本质区别 |
|---|---|---|
| 工作流（workflow） | 都能把任务拆成多步 | workflow 通常是预先写死的路径；agentic loop 会根据中间观察动态改计划 |
| RAG | 都会从外部取信息 | RAG 重点是“取回上下文后生成”；agentic loop 强调“取信息、行动、观察、再决策”的持续闭环 |
| ReAct | 都强调推理与行动交错 | ReAct 更像一种经典 loop 模板；agentic loop 是更宽的总称，可包含记忆、评估、子代理、协议互通 |
| 多代理系统 | 都是 agent 架构的一部分 | 多代理是组织形态；agentic loop 是单个代理或整个系统内部的运行机制 |

### 上下游关系

- 上游通常是：用户目标、系统提示词、工具描述、任务约束、身份权限。
- 中游就是：规划、调用工具、环境交互、状态更新、反思和验证。
- 下游通常是：结果交付、轨迹记录、评估、人工接管、持久化记忆。
- 在真实工作流中，它常处于“检索”与“交付”之间，是把静态模型能力转成动态执行能力的那一段。

### 竞争与互补

- 替代方案 1：`固定 pipeline`。优点是稳定、可控、便宜；缺点是难以处理路径依赖和例外情况。适合结构固定、失败成本高、变化少的任务。
- 替代方案 2：`检索增强 + 一次生成`。优点是实现简单；缺点是缺少行动与校验。适合问答、总结、轻分析。
- 互补方案 1：`Agent + Workflow`。把高不确定性部分交给 loop，把强规则部分交给固定流程，往往更现实。
- 互补方案 2：`Agent + Human-in-the-loop`。把高风险决策交给人批准，把重复性搜索和执行交给 agent。

## 5. 发展脉络与前沿

- **2022：ReAct 把“想”和“做”第一次系统地交错起来。** 这一步的重要性不只是提升几个 benchmark，而是把“推理轨迹 + 外部行动 + 新观察”变成可复用范式。它奠定了后续 agent loop 的骨架。
- **2023：Toolformer、Reflexion、Voyager、AutoGen 把骨架长成系统。** Toolformer 说明模型可以学会何时调用工具；Reflexion 把“反思”变成显式机制；Voyager 展示了环境反馈、技能库与长期迭代；AutoGen 则把多代理对话式协作推向开发框架层。
- **2023-2024：领域开始从“案例”进入“架构化总结”。** 相关 survey 和 LATS 这类工作开始统一讨论规划、行动、反思、价值评估、环境反馈等模块，agentic loop 不再只是 prompting 技巧，而逐渐成为系统设计问题。
- **2025：工程体系开始把 loop 做成生产能力。** Anthropic 披露其多代理 Research 系统时，已经把规划、并行子代理、来源质量控制、引文代理、评估与预算控制串成一条完整生产链路。OpenAI、LangChain 等也把 handoff、guardrails、tracing、durable execution 做成 SDK 和框架能力。
- **2025-2026：协议化与平台化开始出现。** MCP 扩展了 agent 接工具和上下文的标准接口；A2A 则把不同 agent 之间的协作协议化。这意味着 agentic loop 正从“单系统闭环”走向“跨系统闭环”。

当前前沿方向：

- `可观测、可评估的 loop`：不是只让 agent 多跑，而是让每一步可追踪、可重放、可评估。
- `跨工具/跨代理协议化`：MCP、A2A 这类协议降低了接入成本，让 agent loop 更像基础设施而不是私有 glue code。
- `Computer Use / Browser Use`：当动作空间从 API 扩展到图形界面，loop 的感知、校验和安全问题都被放大了。

尚未解决的核心争议或开放问题：

- 什么时候应该停？停止条件往往比“怎么开始”更难。
- 什么时候该升级成多代理，什么时候维持单代理？并行不总是收益。
- 如何评估非确定性轨迹？很多任务不存在唯一正确路径。
- 如何处理 prompt injection、工具权限、数据泄漏与执行安全？
- 如何控制成本？当前高质量 agent loop 往往显著比普通聊天更烧 token 和工具调用。

驱动力判断：

- 底层驱动力不是“大家都在做 agent”，而是三股力量叠加：
  1. 模型推理能力更强，足以支撑多步闭环；
  2. 工具与协议生态成熟，外部行动成本下降；
  3. 企业任务越来越要求“完成工作”，而不是“回答问题”。

## 6. 怎么用

### 场景 1：深度研究

- 场景：研究一个复杂、开放、需要多来源交叉验证的问题。
- 用法：让 agent 先拆问题，再并行搜索，再综合，再补检索，再生成带引用的报告。
- 效果：比一次性 RAG 更适合处理“边查边改方向”的问题。

### 场景 2：编码与运维自动化

- 场景：修 bug、读日志、跑测试、改代码、再验证。
- 用法：让 agent 在文件系统、shell、测试框架之间循环，而不是只生成“可能正确”的 patch。
- 效果：真正把“写代码”变成“定位问题 -> 变更 -> 验证 -> 继续修”的闭环。

### 场景 3：企业后台任务

- 场景：客服升级单、财务核对、法务文档整理、销售情报汇总。
- 用法：agent 从内部系统取上下文，调用多个业务工具，必要时升级给人，最后留下轨迹。
- 效果：把高重复、低结构化、但仍需判断的工作自动化。

如果你想结合 AI 工具立刻实践，最直接的切入方式不是上来做“全自动代理”，而是先做一个**最小闭环**：

1. 给代理一个清晰目标。
2. 只接 1-2 个高价值工具。
3. 强制它每轮都做“观察总结 + 下一步理由 + 是否结束判断”。
4. 每完成一步都留下轨迹。

可立即尝试的 Prompt：

```text
你现在不是一次性回答问题，而是执行一个 agentic loop。

任务：帮我研究“为什么很多 AI agent 在长任务中会失控”。

规则：
1. 先给出 3-5 个需要验证的子问题。
2. 每轮只做一个最有价值的动作：搜索、阅读、对比、总结之一。
3. 每轮输出固定格式：
   - 当前目标
   - 本轮动作
   - 观察结果
   - 对结论的影响
   - 下一步
   - 是否已经足够回答（是/否）
4. 如果信息不足，继续循环；如果已足够，停止并给出最终结论与证据链。
5. 优先引用一手来源，不确定的内容标注为推测。
```

## 7. 深度调研：学术、实践与开源

### 7a. 关键论文

#### 1. ReAct: Synergizing Reasoning and Acting in Language Models

- 作者 / 年份 / 出处：Shunyu Yao 等，2022；ICLR 2023 / arXiv
- 核心贡献：把“推理轨迹”和“外部行动”交错起来，明确提出 LLM 不该只思考，也应该在环境中行动并根据结果更新。
- 方法论摘要：用 few-shot 提示让模型输出 reasoning trace 与 action；action 作用于 Wikipedia API、交互环境等，环境返回 observation，再进入下一轮。
- 关键结论：在问答、事实核验、WebShop、ALFWorld 等任务上，ReAct 相比只推理或只行动的基线更稳，也更可解释。
- 局限性：仍高度依赖 prompt 设计；对长任务的记忆、停止条件和多工具调度支持有限。
- 影响力判断：这是 agentic loop 的奠基性论文之一。后续大量 agent 框架虽然形式不同，但骨架都能追溯到它。

#### 2. Toolformer: Language Models Can Teach Themselves to Use Tools

- 作者 / 年份 / 出处：Timo Schick 等，2023；NeurIPS 2023 / arXiv
- 核心贡献：把“什么时候调工具、如何传参数、如何吸收返回结果”系统化，不再把工具调用只看成手写 prompt 技巧。
- 方法论摘要：通过少量演示生成带工具调用标注的数据，再做自监督训练，让模型学习 API 使用时机与方式。
- 关键结论：模型在不丢掉原有语言能力的情况下，可以通过外部工具显著提升计算、检索、翻译等任务表现。
- 局限性：评估工具集较有限；更多是在“学会调工具”层面，而不是完整长任务闭环。
- 影响力判断：它把 agent loop 里的“行动”从 prompt 工程推进到可学习机制，对后续 tool-native agent 影响很大。

#### 3. Reflexion: Language Agents with Verbal Reinforcement Learning

- 作者 / 年份 / 出处：Noah Shinn 等，2023；arXiv preprint
- 核心贡献：把“反思”做成显式模块，让 agent 不靠更新模型参数，而靠语言化反馈改进下一轮决策。
- 方法论摘要：agent 在拿到环境反馈后生成 verbal reflection，并把反思文本写入 episodic memory，后续决策再读回。
- 关键结论：在编程、语言推理和顺序决策任务中，反思式 agent 明显优于没有反思记忆的基线。
- 局限性：反思本身也可能产生噪声；如果反馈机制差，反思会把错误写进记忆。
- 影响力判断：它让“loop”从简单的 observe-act 循环升级为带学习感的自我改进循环，是从 ReAct 走向更强 agent 的关键转折。

#### 4. AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation

- 作者 / 年份 / 出处：Qingyun Wu 等，2023；arXiv preprint
- 核心贡献：把多代理对话式协作做成一个开发框架，降低了构建 agent loop 和 multi-agent loop 的工程门槛。
- 方法论摘要：用可定制、可对话的 agents 组合 LLM、人类输入与工具，并用自然语言或代码定义交互模式。
- 关键结论：多代理会话可以覆盖数学、代码、问答、运筹等不同任务，说明 agentic loop 可以从单代理推广到团队式循环。
- 局限性：更偏框架论文，很多结论来自示例系统；生产级稳定性和成本控制后来仍需额外工程化。
- 影响力判断：它极大推动了“multi-agent”热潮，也让更多开发者开始把 loop 看成架构问题而不是 prompt 问题。

#### 5. Language Agent Tree Search Unifies Reasoning Acting and Planning in Language Models

- 作者 / 年份 / 出处：Andy Zhou 等，2023；ICML 2024 / arXiv
- 核心贡献：把规划显式提升到 loop 中心，用树搜索而不是单条轨迹推进，让 agent 能探索多条候选路径。
- 方法论摘要：把 Monte Carlo Tree Search、LM-driven value function、自反思和环境反馈组合进统一框架 LATS。
- 关键结论：在编程、WebShop、交互问答和数学任务上，LATS 显示出比单一路径 agent 更强的决策能力。
- 局限性：计算和 token 成本更高；实现复杂度显著上升，不是所有业务任务都值得上树搜索。
- 影响力判断：它代表了 agent loop 的前沿方向之一，即从“线性循环”走向“带搜索的 deliberation loop”。

如果把这几篇论文串起来看，脉络非常清楚：

- ReAct 解决“边想边做”；
- Toolformer 解决“怎么学会调工具”；
- Reflexion 解决“怎么从失败中写回经验”；
- AutoGen 解决“怎么把多个 agent 组织起来”；
- LATS 解决“怎么在 loop 里做更强规划”。

### 7b. 最佳实践

#### 1. Anthropic：`gather context -> take action -> verify work -> repeat`

- 来源：Anthropic 工程文章《Building agents with the Claude Agent SDK》
- 实践内容：把 agent 设计成一个明确闭环，而不是一句大 prompt；上下文获取、行动方式和校验手段都分别设计。
- 为什么被认为是最佳实践：它把 agent loop 说得非常工程化，尤其强调“校验”必须是显式能力，而不是希望模型自觉做对。
- 可量化或可操作价值：文章给出的具体做法包括 agentic search、subagents、compaction、rules-based feedback、visual feedback、LLM judge，这些都能直接转成实现清单。
- 适用边界：适合文件系统、代码、研究、知识工作等多步任务；如果任务极短、极确定，照搬完整 loop 会过度设计。

#### 2. Anthropic：多代理 Research 系统的委派、并行、预算与评估

- 来源：Anthropic 工程文章《How we built our multi-agent research system》
- 实践内容：用 lead agent + subagents 的 orchestrator-worker 架构，先计划，再并行搜索，再综合，再决定是否继续循环。
- 为什么被认为是最佳实践：它不是停留在“多代理很酷”，而是明确说明了何时该并行、如何写委派说明、如何给 effort budget、如何避免无限搜索、如何做 outcome-based eval。
- 可量化效果：Anthropic 报告其多代理研究系统在内部 research eval 上比单代理版本高 90.2%，并称并行化将复杂查询耗时最多降低约 90%。
- 适用边界：适合可并行拆解、信息量巨大、路径依赖强的研究类任务；对共享上下文很重、强耦合的编码任务，收益未必同样明显。

#### 3. OpenAI：把 handoff、guardrails、sessions、tracing 做成一等公民

- 来源：OpenAI Agents SDK 文档与官方仓库
- 实践内容：官方 SDK 直接把 agents、handoffs、tools、guardrails、human-in-the-loop、sessions、tracing 作为核心概念暴露出来。
- 为什么被认为是最佳实践：这意味着生产级 agent loop 不应只关注“会不会做”，还要关注“如何切换角色、如何留痕、如何设安全边界、如何跨轮保持状态”。
- 可量化或工程价值：你可以少写大量样板 glue code，直接把可观测性、状态管理和安全约束纳入默认架构。
- 适用边界：适合需要长期维护、审计、调试的应用；对一次性 demo 来说，完整 SDK 可能偏重。

#### 4. LangGraph：把 agent loop 当成“有状态图执行”

- 来源：LangGraph 官方仓库与文档
- 实践内容：把 agent 视为 stateful graph，而不是单次调用链，强调 durable execution、memory、human-in-the-loop 和 production deployment。
- 为什么被认为是最佳实践：长任务 agent 最大的问题往往不是“第一步不会做”，而是“跑到第十步崩了怎么办”。LangGraph 的价值就在于把恢复、持久化、人工介入和部署问题前置。
- 可量化或工程价值：从官方仓库可见其版本迭代很快，且文档反复强调 resilience 和 debugging，说明它服务的是长期运行场景，而不是玩具 demo。
- 适用边界：适合复杂、多状态、需恢复的任务；若只是一个轻量单回合工具代理，成本可能高于收益。

### 7c. 开源项目

#### 1. LangGraph

- 项目名称 / 地址 / Star / 维护者：`langchain-ai/langgraph`，<https://github.com/langchain-ai/langgraph>，约 `29.2k` stars（截至 2026-04-14），维护者为 `LangChain AI`
- 它做了什么：一个面向长运行、可恢复、可持久化 agent 的低层 orchestration framework。
- 技术选型：以 Python 为主，采用 graph/state 组织方式；这种设计适合表达“分支、回退、记忆、人工介入、子图”等复杂 loop。
- 社区活跃度判断：高。GitHub 页面显示 `6,720` commits，`495` 个 release，最新 release 为 `2026-04-10`；基于这些信号判断，维护和迭代非常积极。
- 上手建议：先跑官方 quickstart，只做单代理 + 1 个工具 + 1 个 memory 节点，再逐步引入 persistence 与 human-in-the-loop。

#### 2. OpenAI Agents SDK Python

- 项目名称 / 地址 / Star / 维护者：`openai/openai-agents-python`，<https://github.com/openai/openai-agents-python>，约 `20.8k` stars，维护者为 `OpenAI`
- 它做了什么：一个轻量但较完整的多代理工作流框架，内置 handoffs、guardrails、sessions、tracing 等能力。
- 技术选型：Python；强调 provider-agnostic，同时原生对接 OpenAI 的 Responses / Chat Completions 与 tracing 体系。
- 社区活跃度判断：高。页面显示 `1,319` commits、`81` 个 release，最新 release 为 `2026-04-09`，说明项目仍在高速演进。
- 上手建议：直接从 README 的最小 `Agent + Runner` 示例开始，先理解 single-agent run，再加 tools、handoff、guardrail。

#### 3. smolagents

- 项目名称 / 地址 / Star / 维护者：`huggingface/smolagents`，<https://github.com/huggingface/smolagents>，约 `26.6k` stars，维护者为 `Hugging Face`
- 它做了什么：一个强调“agents that think in code”的极简 agent 库，主打 code agent。
- 技术选型：Python；核心逻辑保持很薄，强调把行动写成代码片段，这么做是为了提升表达能力和工具组合能力。
- 社区活跃度判断：高。页面显示 `1,035` commits、`34` 个 release，最新 release 为 `2026-01-16`；结合较高 stars 和较多 PR，可判断社区活跃。
- 上手建议：如果你想快速体会 code-as-action 的 loop，这是最容易上手的项目之一。直接从 `CodeAgent + WebSearchTool` 示例跑起即可。

#### 4. AutoGen

- 项目名称 / 地址 / Star / 维护者：`microsoft/autogen`，<https://github.com/microsoft/autogen>，约 `57.1k` stars，维护者为 `Microsoft`
- 它做了什么：最有代表性的多代理对话式框架之一，对整个 agent 社区的影响极大。
- 技术选型：Python、C#、TypeScript 混合生态；这反映它更像一个跨语言框架与实验平台，而不是单一 Python 库。
- 社区活跃度判断：影响力极高，但状态已变化。页面显示 `3,782` commits、`98` 个 release，最新 release 为 `2025-09-30`；但官方 README 明确标注其已进入 `maintenance mode`，并建议新用户迁移到 Microsoft Agent Framework。
- 上手建议：适合作为理解 multi-agent 编排历史的学习材料；如果是新项目，除非你有兼容旧生态的理由，否则不建议优先选它。

综合看：

- 如果你要学“loop 的骨架”，先看 `OpenAI Agents SDK`。
- 如果你要学“长任务状态管理”，看 `LangGraph`。
- 如果你要学“代码型 agent loop”，看 `smolagents`。
- 如果你要学“多代理历史与模式演化”，看 `AutoGen`。

## 8. 我的项目实践分析

**我的项目仓库**：

- `https://github.com/diffw/Vibe-Capture`
- `https://github.com/diffw/harness-coding`

这两个项目都和 `agentic loop` 有关，但层级不同：

- `harness-coding` 是**显式实现 agentic loop 的基础设施仓库**。
- `Vibe-Capture` 是**把这套 loop 接进真实产品开发流程的宿主项目**。

换句话说，前者更像“引擎”，后者更像“引擎驱动的业务应用”。

### 8a. 概念识别

#### 项目一：`harness-coding`

在这个仓库里，`agentic loop` 不是暗含原则，而是直接写进了运行时路由、执行阶段和校验规则中。

- `AGENTS.md`
  - 证据：
    - 要求先 `route`，再 `edit`、`build`、`validate`、`summary`、`receipt`、`reply`
    - 明确禁止把流程缩成 `edit -> build -> reply`
  - 关键片段：
    - `route -> edit -> build -> validate -> summary -> receipt -> reply`
    - `只有完成前六步后，才能向用户报告完成`
  - 这本质上就是一个显式定义的 agent 执行闭环，而不是“改完就说 done”。

- `rules/shared/scope-guard.md`
  - 证据：
    - 强制先输出 `Scope Card`
    - 明确区分 `Hard Budget / Soft Budget / Phase Gate`
    - 在低收益循环时要求自动切换到收敛模式
  - 关键片段：
    - `Scope Card 一旦输出，后续工作必须严格在其范围内进行`
    - `出现异常时，优先动作是收敛，不是立刻停机`
    - `Bug 根因分析 | Phase Gate | 以假设循环、patch 轮次、receipt 控制`
  - 这说明它不仅有 loop，还有状态控制、预算控制、升级规则和停止条件。

- `rules/shared/execution-receipt.md`
  - 证据：
    - 把最终输出约束成 `Status / Findings / Testing / Rules Used / Skills Used`
    - 明确“没过 gate 禁止说完成”
  - 关键片段：
    - `回执是完成条件，不是装饰`
    - `没过 gate，禁止说完成`
  - 这属于 loop 中的 `verification + termination contract`。

- `scripts/check_execution_receipt.mjs`
  - 证据：
    - 脚本会程序化检查回复里是否真的包含测试证据、状态、覆盖摘要
    - 如果编辑了代码但没记录测试，会直接报错
  - 关键片段：
    - `production code was edited but no test execution was recorded`
    - `functional/acceptance execution missing AC/EC/FR coverage summary`
  - 这说明该仓库已经把“验证反馈”从文字规范推进到机器可检查层。

- `scripts/setup_host_agents.sh` 与 `scripts/update_host_bridge.sh`
  - 证据：
    - 可以把本仓库作为 `.agents` 接到宿主仓库
    - 然后同步 `AGENTS.md`、`CLAUDE.md`、skills 和 enforcement hooks
  - 关键片段：
    - `submodule add ... .agents`
    - `Updated host bridge docs`
    - `Synced Claude enforcement`
  - 这意味着 `harness-coding` 不只是自己用 loop，而是把 loop 作为可复用执行系统分发给其他项目。

判断：

- 这是**有意识且完整度很高**的 `agentic loop` 实现。
- 它不是“无意中有点像”，而是已经具备：
  - 输入约束
  - 状态锁定
  - 动态升级
  - 反馈校验
  - 停止条件
  - 可观测回执
  - 宿主接入机制

#### 项目二：`Vibe-Capture`

这个仓库里，`agentic loop` 的存在方式更间接。它主要体现在**AI 开发流程**，而不是截图应用本身的用户态业务逻辑。

- `.gitmodules`
  - 证据：
    - `.agents` 直接指向 `https://github.com/diffw/harness-coding.git`
  - 意义：
    - 说明 `Vibe-Capture` 不是孤立维护 agent 规则，而是把 `harness-coding` 作为外接 loop 基础设施接入。

- `AGENTS.md`
  - 证据：
    - 它基本沿用了 harness 的核心 loop：`route -> edit -> build -> validate -> summary -> receipt -> reply`
    - 同样要求 Scope Lock、测试分层、执行回执
  - 意义：
    - 说明这个产品仓库的开发行为已经运行在 agentic loop 框架之上。

- `scripts/run-local-ci.sh`
  - 证据：
    - 顺序执行本地化检查、打包、单测、集成测、UI 测试
    - 每一步都建立在前一步输出之上
  - 关键片段：
    - `[1/5] Localization integrity check`
    - `[2/5] App build`
    - `[3/5] Unit tests`
    - `[4/5] Integration tests`
    - `[5/5] UI tests`
  - 这相当于把开发闭环里的“验证链”固定成可执行脚本。

- `scripts/run-dev.sh`
  - 证据：
    - 先清理状态，再 build，再根据失败日志决定是否切换到 unsigned build，再自动启动 app
  - 关键片段：
    - `retrying with code signing disabled`
    - `Build failed on attempt ...`
  - 这体现了简化版 agentic loop 的几个要素：状态清理、执行、观察错误、根据观察切换策略、继续尝试。

- `DEV_WORKFLOW.md`
  - 证据：
    - 明确把 `run-local-ci.sh` 和 `run-dev.sh` 作为 AI 完成改动后的默认动作
  - 关键片段：
    - `当 AI 完成会影响 app 行为的改动后，应优先执行 ./scripts/run-dev.sh`
  - 这说明 loop 不只是文档上的规范，而是绑定到实际开发动作。

判断：

- `Vibe-Capture` **有意识地运用了 agentic loop**，但重点在“开发过程闭环”，不是“产品 runtime 中存在一个面向终端用户的 agent”。
- 所以它不是一个 agent 产品，而是一个**被 agentic 开发系统驱动的产品仓库**。

### 8b. 实践评估

对照第 3 层（核心机制）和第 7b 层（最佳实践）来看：

#### 做得好的地方

1. `harness-coding` 已经把 loop 从“口头方法论”落成了结构化执行系统。
   - 它有输入约束（Scope Card）、状态机（task scale / risk / budget / phase gate）、动作路径（route/edit/build/validate）、环境反馈（tests/receipts）、停止条件（gate/receipt/status）。
   - 这比很多只有 prompt、没有执行边界的 agent 项目成熟得多。

2. 你已经把基础设施与宿主产品分层了。
   - `harness-coding` 负责 loop 能力，`Vibe-Capture` 通过 `.agents` submodule 接入。
   - 这种分层很接近最佳实践，因为 loop 逻辑可以迭代，而产品仓库不需要手写复制粘贴。

3. 你很重视“验证反馈必须真实存在”。
   - `execution-receipt.md` 和 `check_execution_receipt.mjs` 联合起来，已经在逼 agent 不要跳过测试、不准假装完成。
   - 这是很多 agent 系统最容易缺失的关键一环。

4. `Vibe-Capture` 已经有清晰的 build/test 反馈链。
   - `run-local-ci.sh` 和 `run-dev.sh` 使 agent 修改后的验证有可落地的动作路径，而不是只靠人工记忆“记得跑一下”。

#### 存在的差距

1. 当前 loop 主要是“流程治理型”，还不是“环境自适应型”。
   - 你已经有 route、budget、receipt、test，但规划和动作选择仍主要由规则驱动，而不是基于运行时证据自动重规划。
   - 也就是说，它更像“严格工作流 + 闭环验证”，而不是更强的 deliberative agent。

2. `Vibe-Capture` 的业务代码本身尚未体现 runtime agent loop。
   - 目前能确认的是开发过程用了 loop；无法看到面向终端用户的产品功能中有 planner / tool runner / memory / verifier 这样的结构。
   - 如果你的目标是学习 agentic loop 在产品里的应用，这一层目前更多还是“开发 loop”，不是“产品 loop”。

3. `harness-coding` 的 loop 已有较强规则，但长期记忆层相对弱。
   - 它有 receipt 和文档保留，但还不明显具备“从历史任务中自动提炼经验，再反哺后续策略”的统一 memory 层。
   - 更像可执行 SOP，而不是会演化的经验系统。

4. 验证大多仍集中在测试与回执，对“策略正确性”的评估还不够丰富。
   - 例如：何时选择单测而非集成测、何时该收敛、何时升级阶段，虽然有规则，但尚未看到系统化的 outcome eval 或 trajectory eval 体系。

#### 潜在风险

1. 规则越来越多时，loop 可能从“会自纠偏”退化成“过度依赖静态规约”。
   - 规则能提升可靠性，但也可能让 agent 过早收敛到模板动作，而不是按证据选择下一步。

2. `Vibe-Capture` 对 `.agents` submodule 的依赖意味着桥接同步一旦漂移，宿主项目和 harness 可能出现规则不一致。
   - 尤其是 `AGENTS.md`、`CLAUDE.md`、hooks、skills 的同步链路较长。

3. 如果测试成本继续升高，当前 loop 可能在真实迭代中被人为绕过。
   - 一旦 build/test 很慢，最先被牺牲的通常就是 `validate` 和 `receipt` 的完整性。

### 8c. 改进建议

1. 给 `harness-coding` 增加统一的“任务轨迹 memory / lessons learned”层。
   - 改什么：把每次执行后的关键失败模式、有效修复策略、常见低收益循环信号沉淀成结构化记忆，而不只是零散 receipt。
   - 为什么改：现在它的 loop 已经有状态、动作、验证，但对“历史经验复用”的支持还偏弱。
   - 怎么改：在 `harness-coding` 增加统一目录，例如 `references/shared/execution-patterns.md` 或结构化 `artifacts/lessons/*.json`，由 receipt 生成脚本自动汇总常见错误与成功策略。

2. 在 `Vibe-Capture` 里把“开发 loop”与“业务 runtime loop”明确分层命名。
   - 改什么：把当前基于 `.agents` 的流程明确标注为 `development agent loop`，避免未来讨论时混淆成产品功能。
   - 为什么改：现在 `Vibe-Capture` 确实在使用 agentic loop，但主要是在开发流程上；如果以后你要在产品里加 AI 功能，这两类 loop 最好从命名和目录上就分开。
   - 怎么改：在 [AGENTS.md](/Users/diffwang/NWA/Vibe-Capture/AGENTS.md:1) 或 [DEV_WORKFLOW.md](/Users/diffwang/NWA/Vibe-Capture/DEV_WORKFLOW.md:1) 增加一小节，明确“当前仓库使用的是 AI 开发闭环，不代表 App runtime 存在 end-user agent”。

3. 给 `harness-coding` 增加更明确的“策略评估”工作流。
   - 改什么：不仅校验“有没有测”，还评估“loop 选的路径是否合理”。
   - 为什么改：现在你已经把执行结果验证做得很好，但 agentic loop 的上限不只在 correctness，还在 step efficiency 和 policy quality。
   - 怎么改：新增一个轻量评估脚本，对任务回执统计：
     - 是否发生不必要重读
     - 是否出现多次无新增搜索
     - 是否在可 Micro 的任务上误升级
     - 是否在应该收敛时仍继续扩散
   - 如果涉及 AI 工具优化，可直接尝试这个 Prompt：

```text
请审查这份 agent 执行轨迹，不要判断代码对不对，而是判断 loop 选路是否高效。

输出：
1. 本次 loop 的目标是否被正确锁定
2. 哪一步开始进入低收益循环
3. 哪一步本可提前停止
4. 哪一步应该升级验证层，哪一步应该降级验证成本
5. 给出 3 条可写回 rules 的策略改进建议
```
