## 0. 全景定位

`DESIGN.md` 是 Google Labs Code 在 2026 年 4 月开源的一份**格式规范**——它定义一种文件格式，让 AI coding agent 能像读 README 一样读懂一个产品的设计系统。它属于 2025-2026 这一波正在快速形成的「**AI 工程文档协议**」浪潮中的一员。

把这一波放到一张图上：

```text
AI 工程文档协议（2025-2026 涌现）
        |
        +---- AGENTS.md         (2025-12 -> Linux Foundation)
        |     由 OpenAI / Google / Sourcegraph / Cursor / Factory 联合制定
        |     回答「agent 在我这个仓库里能做什么、不能做什么」
        |
        +---- SKILL.md          (Anthropic / Agent Skills 标准)
        |     回答「agent 应该按什么步骤完成某类任务」
        |
        +---- DESIGN.md         (2026-04 / Google Labs)   <-- 本概念
        |     回答「agent 应该按什么样的视觉语言生成 UI」
        |
        +---- program.md        (2026-03 / Karpathy / autoresearch)
              回答「agent 应该按什么纪律跑实验循环」
```

这一波的共同特征：**人写 Markdown，agent 读 Markdown，工具链做校验**。从 2024 年「让 AI 看 Figma 截图」的混乱，正在过渡到 2026 年「让 AI 读结构化设计协议」的纪律。

知识地图：

```text
前置：AI coding agent 已经能稳定写 UI 代码
       + 2010-2024 年发展起来的 Design Token 标准（W3C DTCG / Style Dictionary）
       + 2024-2025 年 AGENTS.md / SKILL.md 提供的协议层模板

本概念：DESIGN.md = "YAML token + Markdown 解释" 的设计系统协议

后续：垂直领域的 *.md 协议（DATA.md? DEPLOY.md? COPY.md?）
       + 跨工具的设计系统注册表（designmd.app 已经收录 454 个）
       + Agent-driven 设计系统迭代（设计 Token 也能进 autoresearch 循环）
```

学这个概念之前最好先了解的两个前置：

- **W3C Design Tokens (DTCG)**：业界已经为 token 命名、类型、引用语法做过 5 年标准化工作。DESIGN.md 不是从零发明，是这套规范的「Markdown 化 + Agent 友好化」。
- **AGENTS.md / SKILL.md**：DESIGN.md 处于这个三件套的最右端，最 narrow、最具体（专门管视觉），但格式哲学一脉相承。

## 1. 一句话定义

**一份让 AI 读懂你设计语言的 Markdown 文件**，前面是机器读的 token 表（YAML），后面是人读的设计理由（散文）。

日常生活类比：装修房子时给装修工的「材料清单 + 风格说明」。

```text
材料清单（机器读）：
  墙漆色号 #B84636
  地板：橡木 / 标准 18mm
  踢脚线：8cm 高度

风格说明（人读）：
  整体偏温暖，但不要乡村风。
  主色用在客厅和玄关。
  卧室刷得比客厅浅一档。
  绝对不要高反光的工业感。
```

DESIGN.md 就是把这两份合成一个文件，让任何一个新来的工人（或 AI agent）拿到这个文件就知道你想要什么——不用每次都解释一遍。

## 2. 为什么会出现

### 它要解决的根本问题

**AI Coding 时代，设计师丢失了对视觉的全局控制。**

上一个时代，设计师在 Figma 里花几周搭一套 design system——颜色、字号、间距、组件。开发者再花几个月把 Figma 翻译成代码。整个链条慢，但**每一个像素都被设计师审过一遍**。

到了 2024-2025，AI coding agent 突然能直接生成 UI 代码。这件事的好处是「想法 → 上线」从几个月压到几小时。坏处是设计师变成了局外人——agent 接到「做一个登录页」的指令后，自己拼凑出来的视觉风格往往是这种状态：

```text
- 默认蓝紫渐变（cyan-on-dark 那种「AI 感」）
- glassmorphism 玻璃拟态
- 大量阴影 + 大圆角
- 各种 emoji + glow 效果
- 配色和品牌完全无关
```

设计师过去 10 年练出来的判断力、品牌资产、设计系统，**在 prompt 翻译成代码的那一瞬间全部丢失**。

### 之前人们怎么处理

```text
1. 给 agent 看 Figma 截图  -> agent 读截图能力差，还原度低
2. 把 Figma 文件上传     -> Figma JSON 太大、太脏，agent context 装不下
3. 在 prompt 里写规则     -> 只在当前 session 起作用，下次又得重写
4. 用现成的 UI 库（shadcn / Tailwind UI）-> 风格被库绑架，失去品牌
5. 把 Tailwind 配置喂给 agent -> 只有 token 没有 rationale，agent 不知道为什么
```

每一种都解决了一部分问题，但都不能让设计师**一次定下一份「全局且持久」的设计契约**。

### 谁、什么情境、什么洞察

提出者：**Google Labs Code 团队**（与 Google Stitch 项目同源——Stitch 是 Google 的 AI UI 生成产品 stitch.withgoogle.com）。

情境：Stitch 在内部跑 AI 生成 UI 时，发现「每次重新告诉 agent 我要什么风格」是最大的体验摩擦。设计师抱怨产出的 UI 风格漂移、品牌不一致、调起来要从头解释。

关键洞察（来自 README）：

```text
1. agent 无法记住跨 session 的设计偏好
2. 但 agent 极擅长读 Markdown
3. Design Token 的 JSON 格式存在多年，但「JSON 里只有数字，没有意图」
4. 把 token 和 rationale 合写在一份 Markdown 里，agent 既能拿到精确数值，
   也能理解「为什么是这个数值」
5. 同一份文件还能被 designer / dev / agent 三方协作维护
```

这五点凑在一起，就是 DESIGN.md。

### 关键决策：为什么是 Markdown 而不是 JSON / YAML / Figma JSON？

| 选项 A | 选项 B | Google 选了 | 为什么 |
|---|---|---|---|
| 纯 JSON / YAML | Markdown 包 YAML | **Markdown 包 YAML** | 既给 agent 结构，也给人解释空间 |
| 完整定义所有 token 类型 | 只定义最常用的 6 类 | **只定义 6 类**（colors / typography / rounded / spacing / components + 自由文本） | 故意小，鼓励快速采纳；不在 alpha 阶段过度规范 |
| 强 schema（必填、类型严格） | 弱 schema（unknown 字段保留 + warning） | **弱 schema** | agent 写错也能 graceful degrade，鼓励实验 |
| 自建 token 类型 | 兼容 W3C DTCG / Tailwind / Figma | **兼容** | 不和已有生态打架，直接 export 互转 |
| 闭源（Stitch 内部用） | Apache 2.0 开源 | **开源** | 想做事实标准就得放开 |
| 一上来叫 v1 | 标 alpha + "expect changes" | **alpha** | 给社区缓冲，明确说还会改 |

整套设计哲学一句话：**「**够规范让 agent 能用，够宽松让设计师不嫌烦**」**。

## 3. 核心机制

### 输入 -> 过程 -> 输出

```text
输入：
  designer 写的 DESIGN.md 文件（一份，放在仓库根目录或 docs/ 下）

过程（agent 读取时）：
  1. 解析 YAML frontmatter -> 拿到 token 表
  2. 解析 Markdown body -> 拿到设计 rationale（按 8 个标准 section 排序）
  3. 解析 token references {colors.primary} -> 在生成代码时替换为具体值
  4. 应用 components + variants 规则 -> 生成符合品牌的 UI 组件

输出：
  agent 写出的 UI 代码（Tailwind / SwiftUI / Compose / 任何前端栈）
  视觉上和你定义的设计系统一致
```

### 文件结构示例（来自 README）

```yaml
---
name: Heritage
colors:
  primary: "#1A1C1E"        # 深墨色
  secondary: "#6C7278"      # 板岩灰
  tertiary: "#B8422E"       # Boston Clay（唯一的强调色）
  neutral: "#F7F5F2"        # 暖石灰
typography:
  h1:
    fontFamily: Public Sans
    fontSize: 3rem
    fontWeight: 600
    lineHeight: 1.1
    letterSpacing: -0.02em
  body-md:
    fontFamily: Public Sans
    fontSize: 1rem
rounded:
  sm: 4px
  md: 8px
spacing:
  sm: 8px
  md: 16px
components:
  button-primary:
    backgroundColor: "{colors.tertiary}"
    textColor: "{colors.neutral}"
    typography: "{typography.body-md}"
  button-primary-hover:
    backgroundColor: "{colors.primary}"
    textColor: "{colors.neutral}"
---

## Overview

Architectural Minimalism meets Journalistic Gravitas.
The UI evokes a premium matte finish — a high-end broadsheet
or contemporary gallery.

## Colors

The palette is rooted in high-contrast neutrals and a single accent.
- Primary (#1A1C1E): 深墨，标题与正文。
- Tertiary (#B8422E): "Boston Clay"，唯一的交互引导色。

## Typography

衬线和无衬线之间偏向几何无衬线，气质上要"庄重又克制"。

## Components

按钮使用唯一强调色 tertiary，不在一屏出现两个 primary action。

## Do's and Don'ts

✓ 主操作按钮全屏唯一
✗ 不要在中性色上叠加渐变
✗ 不要使用蓝紫色（这套品牌完全不出现冷色）
```

### 5 个关键子概念

```text
1. Frontmatter (YAML)        机器读的 token 表，放在文件最顶端
2. Body (Markdown)            人读的设计理由，按 8 个标准 section 排序
3. Token References           {colors.primary} 这种引用语法，能交叉引用
4. Components + Variants      组件级 token 组合，含 hover / active / pressed 变体
5. Lint CLI                   npx @google/design.md lint 做结构 + 对比度校验
```

### 8 个标准 Markdown section（按规范顺序）

```text
1. Overview          整体气质、品牌人格、情感反应
2. Colors            色板和语义角色
3. Typography        9-15 级字阶
4. Layout            网格、间距策略
5. Elevation & Depth 阴影 / 层次
6. Shapes            圆角和形态语言
7. Components        组件级风格
8. Do's and Don'ts   实操守则
```

未知 section 会被保留不报错（如 `## Iconography`），鼓励扩展。

### 第一性原理追问：去掉一个会怎样？

| 去掉 | 后果 |
|---|---|
| YAML frontmatter | 退化成普通 style guide，agent 拿不到精确数值，每次都要靠猜 |
| Markdown body | 退化成 Design Token JSON，agent 知道 #1A1C1E 但不知道「这是给标题用还是按钮用」 |
| Token References | 同一个色被改名后，组件定义无法同步更新，整个体系僵化 |
| Components 章节 | 设计系统变成「调色板 + 字号」两件套，无法表达组件级一致性 |
| Lint CLI | 设计师写完没法验证；AI 生成的 DESIGN.md 也无法自动校验 |

最关键的是 **YAML + Markdown 同时存在**。这是 DESIGN.md 区别于所有前辈方案的真正创新——既不是「全机器结构」也不是「全自然语言」，是把两种表达**强制绑在一份文件里**。

## 4. 生态位：它和谁像？和谁争？

### 易混辨析（核心区别表）

| 维度 | DESIGN.md | W3C DTCG (tokens.json) | Tailwind config | Figma Variables | Style guide PDF |
|---|---|---|---|---|---|
| 包含 token 数值 | ✓ | ✓ | ✓ | ✓ | ✗（图片） |
| 包含设计 rationale | ✓ | ✗ | ✗ | 部分（描述字段） | ✓ |
| 机器可解析 | ✓ | ✓ | ✓ | 通过 API | ✗ |
| AI agent 友好 | ✓✓ | ✓ | ✓ | △（需 plugin） | ✗ |
| 跨工具互操作 | export 到所有 | ⭐ 是其它格式的源 | 框架专用 | Figma 专用 | 无 |
| 上手成本 | 一份文件 | 一份 JSON + 工具链 | 一份 config | 一个 Figma 文件 | 写文档 |
| 适合 designer 维护 | ✓ | △ | ✗ | ✓ | ✓ |
| 适合 LLM 生成 / 修改 | ✓✓ | ✓ | △ | ✗ | △ |

**关键区别**：DESIGN.md 不是要替代上面任何一个，**而是要做它们之间的「**人 - AI - 工具链**」三方接口**。它的存在让设计师可以：
- 维护一份 DESIGN.md
- 自动 export 到 W3C DTCG 给设计工具用
- 自动 export 到 Tailwind 给前端用
- 直接喂给 Claude Code / Cursor / Stitch 做 AI 生成

### 上下游关系

```text
上游（设计输入）：
  Figma 设计稿 / 品牌指南 / 既有代码 / 设计师脑子里的偏好
        |
        v
本环节：DESIGN.md（人和 agent 都能读的中间层）
        |
        v
下游（消费）：
  AI coding agent（Claude Code, Cursor, Copilot, Stitch）
  Tailwind config / W3C tokens.json / SwiftUI tokens / Compose tokens
  设计系统注册表（designmd.app, awesome-design-md）
  Lint / contrast 校验工具
```

### 竞争与互补

DESIGN.md 不和 Figma 竞争（明确说自己 complement Figma）。它真正的「软竞争对手」是：

- **直接喂截图给 GPT-4V / Claude**：现在还有人这么干，但风格漂移严重
- **shadcn/ui 之类「现成 UI 库」**：用了就被库的视觉绑架，失去品牌
- **公司内部的 design system 文档（PDF / Notion / Storybook）**：信息丰富但 agent 读不懂

DESIGN.md 把这三类的优点抽出来：**截图的「视觉一致性意图」+ UI 库的「组件原子化」+ Notion 的「人话解释」**，但用一种 agent 友好的格式承载。

## 5. 发展脉络与前沿

### 关键节点（叙事而非年表）

```text
1. 2018-2022：Design Token 标准化的早期尝试
   Salesforce 开源 Theo（早期 token 工具）
   Style Dictionary（Amazon）成为事实标准
   W3C 成立 Design Tokens Community Group (DTCG)
   但所有方案都是「JSON 格式 for 工具链」，没人考虑「人 + AI」

2. 2023-2024：AI coding 引爆 + 视觉控制崩塌
   Cursor、Aider、Claude Code 让 agent 真的能写前端
   Figma Dev Mode / Figma to Code 成熟
   但 agent 依然「只看 prompt 不看品牌」
   设计师群体开始抱怨「失去对 AI 产物的视觉控制」

3. 2025-12：AGENTS.md 事实标准成立
   OpenAI / Google / Sourcegraph / Cursor / Factory 联合发布
   12 月捐给 Linux Foundation
   首次出现「行业级 agent 协议文件」

4. 2026-03：Karpathy 发 autoresearch + program.md
   不是同一个领域，但确认「Markdown as agent protocol」是趋势

5. 2026-04-10：Google Labs 发布 DESIGN.md
   Apache 2.0 开源
   作为 Google Stitch 的开放 spec
   一个月内 12k+ stars

6. 2026-04 至今：生态快速形成
   designmd.app 上线，已收录 454 个公开 design system
   VoltAgent/awesome-design-md 列表
   Anthropic、Cursor 添加 DESIGN.md 原生读取
   多个 lint / 校验 / export 工具涌现
```

### 当前前沿方向

1. **DESIGN.md as living document**：不是设计师写一次就锁死，而是 designer ↔ agent 持续协作迭代——agent 在生成 UI 时也能 propose 对 DESIGN.md 的修改建议。
2. **跨产品的 DESIGN.md 注册表**：把 Apple HIG、Material Design、Tailwind UI 全部翻译成 DESIGN.md 格式，让 agent 通过 import 一键继承。
3. **Multi-brand DESIGN.md**：一个文件描述多个 sub-brand 或多个 surface（marketing site / product UI / docs site），通过 namespace 区分。
4. **DESIGN.md + autoresearch**：把 token 当成 candidate 参数让 agent 自动搜索——但这一个方向有反作弊风险，是开放问题。

### 尚未解决的核心争议

- **Components section 范围**：spec 自己承认「actively evolving」，组件粒度做到哪一层（原子？分子？）还没定。
- **Negative defaults 缺位**：DESIGN.md 没有「禁止做什么」的官方位置（cap4u 的 design-defaults.md 把这个补上了）。
- **运行时 SSOT 与 doc SSOT 谁主导**：如果 SwiftUI 代码里的 token 和 DESIGN.md 漂移了，谁是真相？目前 spec 没规定。
- **Reward hacking**：agent 自动生成 DESIGN.md 时，会不会迎合自己想生成的 UI？这是 alpha 阶段的隐忧。

### 驱动这条线的底层力量

```text
1. AI coding agent 真的能写代码了 -> 设计输入端产生新需求
2. Markdown 成为「人 + AI 之间最自然的接口」-> 协议格式收敛
3. 设计师的全局控制焦虑达到临界 -> 推动力够强
4. 大厂（Google Labs）愿意开源做事实标准 -> 生态形成阻力降到最低
```

四件事同时到位，这一波协议浪潮才在 2025-2026 集中涌现，而不是 2022 年。

## 6. 怎么用

### 三种典型应用场景

#### 场景 A：从零做新产品（推荐路径）

- **谁**：独立开发者 / 小团队 / 没有现成设计系统
- **用法**：
  1. 在 designmd.app 上挑一个最接近气质的 design system
  2. 复制下来改成自己的（改色、改字体、改组件）
  3. 放到仓库根目录的 `DESIGN.md`
  4. 让 Claude Code / Cursor 读这个文件再开始写 UI
- **效果**：第一版 UI 就有一致的视觉语言，不会出现「AI 感乱炖」

#### 场景 B：把现有产品的设计系统迁过去

- **谁**：已经有一份 design system 文档（Figma / Notion / Storybook）
- **用法**：
  1. 用 `npx @google/design.md generate` 从已有代码（Tailwind config / SCSS variables）反向生成 DESIGN.md 草稿
  2. 人工补 Markdown body 部分（rationale）
  3. 用 `npx @google/design.md lint` 校验对比度和 token 引用
  4. 跟 agent 跑几个 UI 任务，发现漂移 → 回头补 DESIGN.md
- **效果**：把零散的设计资产 collapse 成一份单文件协议，agent 后续生成都基于这个文件

#### 场景 C：跨工具同步一份事实

- **谁**：设计 / 前端 / 移动端用不同工具栈但要保持视觉一致
- **用法**：
  1. DESIGN.md 是 Source of Truth
  2. `export json-tailwind` → 给 Web 前端
  3. `export css-tailwind` → 给 Tailwind v4 用户
  4. `export dtcg` → 给 Figma / 设计工具
  5. 自己写小工具 export 到 SwiftUI / Compose token
- **效果**：所有平台的视觉常量从同一份 DESIGN.md 派生，改一处全平台同步

### 一个可以立刻尝试的工作流

如果你现在就想试，最小可执行的 5 步：

```text
1. 在仓库根目录建 DESIGN.md，复制 Heritage 例子，把名字和颜色改成你的品牌
2. 在 AGENTS.md / CLAUDE.md / .cursor/rules 里加一条：
   "做任何 UI 任务前先读 DESIGN.md。"
3. 让 agent 生成一个组件（按钮 / 卡片 / 表单），看它是否真的用你的 token
4. 跑 npx @google/design.md lint DESIGN.md
   修掉所有 contrast-ratio warning
5. 把这份 DESIGN.md 放到 git，从此每次新功能都从它开始
```

5 分钟内能搭起来，是 2025-2026 这一波协议里**入门成本最低的一个**。

## 7. 深度调研：标准、实践与开源

### 7a. 关键标准与文献

DESIGN.md 不是从零发明的孤儿，它站在三条已有标准的肩膀上。

#### (1) W3C Design Tokens Community Group (DTCG) — 2019 至今

- **来源**：W3C 旗下社区组，由 Adobe / Salesforce / Microsoft / Atlassian 等推动。
- **核心贡献**：定义了「token 是什么、有哪些类型、如何引用、如何组合」的官方规范，输出格式是 `tokens.json`。
- **方法论**：分层 token（global token → alias token → component token），typed value（color / dimension / typography 等），引用语法 `{path.to.token}`。
- **关键结论**：不同厂商可以用同一份 tokens.json 互通，无需绑定具体工具。
- **局限性**：纯 JSON，没有 rationale 层；学习曲线陡；普通设计师写不出来。
- **影响力**：DESIGN.md 几乎完全继承了 DTCG 的引用语法和 typed value 概念，能 export 到 DTCG 格式做互通。**它是 DTCG 的「Markdown 化用户接口」**。

#### (2) Salesforce Theo / Amazon Style Dictionary — 2016 起

- **核心贡献**：早期把 design token 工具化，让一份 source 自动生成多平台代码（iOS / Android / Web / Sketch）。
- **方法论**：JSON 输入 → 配置化 transformer → 多格式输出。
- **关键结论**：「single source of truth + 多平台编译」是可行的工程模式。
- **局限性**：专家工具，需要前端工程师配置；rationale 完全在文档系统外。
- **影响力**：DESIGN.md 的 `export` 子命令，本质上是 Theo / Style Dictionary 思路的「one-file 化」。

#### (3) AGENTS.md / Linux Foundation 协议 — 2025-12

- **来源**：OpenAI / Google / Sourcegraph / Cursor / Factory 联合发布，2025 年 12 月捐给 Linux Foundation。
- **核心贡献**：第一次把「agent 协议文件」做成跨厂商事实标准。
- **关键结论**：协议文件比每个工具自己的 dot-file 更值得投资；Markdown 是合适的载体。
- **局限性**：AGENTS.md 是 general purpose，无法承载垂直领域的 schema。
- **影响力**：DESIGN.md 直接引用了「Markdown + frontmatter」这个结构哲学，可以理解为「AGENTS.md 模式在视觉领域的特化」。

#### (4) "AGENTS.md, SKILL.md, DESIGN.md: Three Layers" — DEV Community, 2026-04

- **作者 / 出处**：dev.to 社区文章，2026 年 4 月底。
- **核心贡献**：第一次把这三个协议文件作为**完整一体**来分析，提出「center of gravity 在不同层之间不同」的观点。
- **关键论点**：AGENTS.md 偏自然语言（判断驱动），SKILL.md 偏过程描述（流程驱动），DESIGN.md 偏结构数据（schema 驱动）。**三者覆盖一个 agent 跑完整产品任务所需的全部指令域**。
- **影响力**：这篇文章可能是后续行业讨论的锚定点；目前国内中文圈讨论还不多。

### 7b. 最佳实践

## 8. 我的项目实践分析（NWA/cap4u）

> **重要前置事实**：cap4u 在设计系统这件事上**已经做了相当成熟的工作**——你的 `.vibe-doc/design-token.json`（170+ 行）+ `.vibe-doc/design-system.md`（1.3 版本）+ `.agents/rules/shared/design-defaults.md` 这三个文件，已经实现了 DESIGN.md 想做的几乎所有事情，结构上甚至比 DESIGN.md 当前 alpha 版**更完整**。

走读完 cap4u 的设计相关文件后，下面是详细对比。

### 8a. 概念识别：cap4u 已经在多大程度上实践了 DESIGN.md？

| DESIGN.md 的能力 | cap4u 对应文件 | 完成度 |
|---|---|---|
| YAML token 表 | `.vibe-doc/design-token.json`（结构化 token）| ✓ 用 JSON 而非 YAML，但结构等价 |
| Markdown rationale | `.vibe-doc/design-system.md`（包含 Purpose / Sources of Truth / Appearance Contract / Color Layers / Light Dark Rules / Accessibility Contract / Component Contracts / Verification Matrix）| ✓✓ 比 DESIGN.md 标准 8 章更细 |
| Token references（{colors.primary}）| design-token.json 的 `componentRoles` 用「brand.primary / brand.primaryDark」这种引用语法 | ✓ |
| Components section | `componentRoles` 字段 + design-system.md 的 Component Contracts | ✓ |
| Lint / contrast 校验 | Cap4uDesignTokens.swift 的 Accessibility tokens + design-system.md 的 contrast contract | ✓ 但是是手写规则，不是 CLI |
| Variants（hover / active）| `liveCallAdaptive` 的 light/dark adaptive、`controlActiveSurface` 等命名约定 | ✓ |
| 运行时 SSOT | `Cap4uDesignTokens.swift`（Swift 文件）作为 runtime SSOT | ✓✓ DESIGN.md 没有这一层 |
| Negative defaults（禁止做什么）| `.agents/rules/shared/design-defaults.md` 的 Negative Defaults 章节 | ✓✓ DESIGN.md 完全没有 |
| Appearance policy（system / fixedLight）| design-system.md 的 Appearance Contract | ✓✓ DESIGN.md 没有这个概念 |
| 决策顺序（intuitiveness > structure > ...）| design-defaults.md 的 Decision Order | ✓✓ DESIGN.md 没有 |
| 平台对齐（iOS / macOS / web 各自的 default）| design-defaults.md 的 Platform Alignment | ✓ |
| Version history | design-system.md 的 Version History | ✓ |

**判断**：

1. cap4u 不是「快速搭起来的 design system」——它已经有 Light Mode / Dark Mode 双轨、WCAG AA 契约、appearance policy、运行时 SSOT 分离、negative defaults、决策顺序，**这是工业级设计系统的水平**。
2. **DESIGN.md 的几乎所有能力 cap4u 都覆盖了**，而且在多个维度上更细。
3. cap4u 缺的是 DESIGN.md 提供的**两件事**：
   - **官方 CLI 工具链**（lint / diff / export 命令）
   - **跨工具事实标准格式**（能直接喂给 Stitch / Cursor / 第三方 agent，不用每次自己写「先读 design-system.md」的规则）

### 8b. 实践评估：cap4u vs DESIGN.md 5 项核心机制

| DESIGN.md 核心机制 | cap4u 现状 | 评估 |
|---|---|---|
| 1. YAML + Markdown 同文件 | 拆成 3 个文件（token.json + design-system.md + design-defaults.md）| **理念差异**。cap4u 故意拆开是为了让 token 数据可以被代码工具消费（JSON），让 rationale 可以被人和 agent 同时读（MD），让 default rule 可以被 agent rules 系统加载（独立规则文件）。这种拆分**对工程纪律更友好**，但对「一份文件即可」的便携性弱 |
| 2. Token References（{path.to.token}）| design-token.json 用「brand.primary / brand.primaryDark」字符串引用 | **轻微差距**。cap4u 的引用是字符串约定，没有 schema 校验，agent 可能解析不一致 |
| 3. Components + Variants | `componentRoles` 字段定义了 6+ 个核心组件 | **足够**。但 variants（hover / pressed）没系统化命名 |
| 4. Lint CLI（contrast / orphan / missing）| 没有自动 CLI，靠 design-system.md 的「Verification Matrix」+ Swift 单元测试 | **中等差距**。cap4u 的契约更严，但靠人工执行；DESIGN.md 是 npx 一键 |
| 5. Cross-tool export（Tailwind / DTCG）| 只导出 SwiftUI runtime，不导出其它平台 | **明显差距**。如果未来加 web / macOS / extension，cap4u 的 token 复用成本会变高 |

对照 7b 最佳实践（Google Stitch / designmd.app / awesome-design-md）：

- **做得好**：cap4u 的 design system 在「严肃产品 UI」维度上**比 designmd.app 收录的多数 marketing 站系统更完整**。包括 appearance policy、accessibility contract、negative defaults、决策顺序——这些不是 DESIGN.md 标准里有的，但是真正在做产品 UI 时必备的。
- **存在差距**：缺少 DESIGN.md 风格的「**一份文件**」便携性。如果将来想把 cap4u 的设计系统喂给 Stitch、Cursor、或者社区 agent 工具链，需要先做一次格式翻译。
- **潜在风险**：
  1. **三个文件之间的漂移**：token.json / design-system.md / design-defaults.md 三方各自更新时，谁先谁后没有强约束，未来可能不一致。
  2. **无独立 CLI 校验**：当前 contrast 检查靠「Cap4uDesignTokens.Accessibility 单元测试」+ 人工 review，加新 token 时容易漏。
  3. **跨平台扩展性**：如果未来加 web / macOS / browser extension，要从 Cap4uDesignTokens.swift 重导一遍 token 到新平台，工作量随平台数线性增长。

### 8c. 改进建议（按优先级，影响大且改动小排前）

#### 建议 1（最高优先级）：保留 cap4u 现有 3 文件结构，但增加一个 `DESIGN.md` 作为**对外门面**

**改什么**：在 cap4u 仓库根目录加一个 `DESIGN.md`，它是 design-token.json + design-system.md 关键内容的「合规版」摘要——遵循 Google DESIGN.md 标准格式（YAML frontmatter + 8 个标准 section）。

**为什么改**：
- cap4u 现有三件套是为内部工程纪律服务的，**不要动**
- 但加一份 DESIGN.md 能让外部 agent（Stitch / Cursor / 任何工具）一眼读懂 cap4u 视觉语言
- 这就像 Apple 同时维护 HIG（人读）+ Apple Design Resources Sketch File（工具用）+ SwiftUI tokens（代码用）——三层不打架

**怎么改**：

```text
1. 写一个小脚本：从 design-token.json 提取 colors / typography / spacing / rounded
   生成符合 DESIGN.md 标准的 YAML frontmatter
2. 从 design-system.md 抽出 Purpose / Color Layers / Component Contracts 关键段
   重组为 DESIGN.md 的 8 章 Markdown body
3. 把 design-defaults.md 的 Negative Defaults 放进 Do's and Don'ts 章节
4. DESIGN.md 顶部明确写「本文件是对外摘要；内部 SSOT 是 .vibe-doc/design-token.json
   + design-system.md + .agents/rules/shared/design-defaults.md」
5. 在 AGENTS.md 加一行：「外部 agent 用 DESIGN.md；cap4u 内部 agent 用 .vibe-doc + .agents/rules」
```

效果：cap4u 保留工程纪律，同时获得 DESIGN.md 生态的全部互操作性。

#### 建议 2（中优先级）：引入 `npx @google/design.md lint` 做对比度自动化校验

**改什么**：把建议 1 的 DESIGN.md 接入官方 lint，作为 CI 检查项。

**为什么改**：
- cap4u 当前 contrast 校验靠 Cap4uDesignTokens.Accessibility 的 Swift 单元测试，覆盖了 runtime token，但**不覆盖未来加的新 token**——加新 token 时需要手工想到补测试
- DESIGN.md 的 contrast-ratio lint 是默认项，加新 token 自动校验
- 一行 CI 配置就能加，几乎零成本

**怎么改**：

```text
1. CI workflow 加一步：npx @google/design.md lint DESIGN.md
2. lint 失败 -> CI 失败 -> PR 不能合并
3. 同步把 lint 结果放进 .vibe-doc/design-system.md 的 Verification Matrix
```

#### 建议 3（低优先级，长期价值）：把 negative defaults 和 appearance policy 反推回 DESIGN.md 标准

**改什么**：把 cap4u design-defaults.md 里的 Negative Defaults 章节、design-system.md 里的 Appearance Policy 章节，整理成 DESIGN.md 标准的扩展提案，提交给 google-labs-code/design.md 的 issue tracker。

**为什么改**：
- DESIGN.md 现在没有「禁止做什么」的官方位置——这是它 alpha 阶段的明显空白
- cap4u 的 Negative Defaults（禁用蓝紫渐变 / 禁用 glassmorphism / 禁用 cyan-on-dark）**是产品级 design system 必备**，但 Heritage 那种 toy example 完全没体现
- 你作为有 20 年 UX 经验的设计师 + 实际维护过工业级 design system 的人，**反向贡献到标准里是有价值的**
- 这件事还会让 cap4u 在 Google 那边获得更多曝光（Apache 2.0 项目对 issue 贡献者很欢迎）

**怎么改**：

```text
1. 在 cap4u 项目里把 design-defaults.md 整理成一份 spec proposal
2. 在 google-labs-code/design.md 提一个 issue：
   "Proposal: add Negative Defaults section to canonical Markdown sections"
3. 附上 cap4u 实际使用的 1 年经验作为 supporting evidence
4. 同步把 Appearance Policy（system / fixedLight）作为另一个 proposal
```

哪怕最终没合并，这件事本身会让你在中文 indie 设计师圈里建立一个「在 DESIGN.md 标准上有 contributor 身份」的标签。

### 8d. 一句话总结这部分

cap4u 在设计系统层面**做的事比 DESIGN.md 想做的还多**——你已经有完整的 token + rationale + negative defaults + appearance policy + runtime SSOT 五层，DESIGN.md 当前 alpha 只覆盖前 3 层。

但你**缺一层「对外的标准化门面」**。加一份 DESIGN.md 让外部工具读得懂，不动内部三件套，是性价比最高的动作。

至于你最初的核心焦虑——「**作为设计师，能不能在 AI Coding 时代重获对设计的全局控制？**」——我的诚实回答是：

```text
DESIGN.md 是必要条件，不是充分条件。

- 它定义了「视觉词汇」让 agent 读懂
- 它没有定义「不要做什么」（这层 cap4u 已经自己补上了）
- 它没有定义「设计判断顺序」（cap4u 也已经补上了）
- 它没有定义「跨平台 runtime 怎么消费」（cap4u 也补上了）

所以重获控制的关键不是「我有没有 DESIGN.md」，
是「我有没有把 token + rationale + negative defaults + decision order + runtime SSOT 五层都明确写下来」。
你已经写下来了——这件事比有没有用 Google 的标准格式重要得多。
```

## 10. 阅读问答与实践补充

> 本节根据用户读完报告后提出的问题进行补充。问题已整合为 4 个集群。

### 10.1 集群 A：DESIGN.md 适用所有平台和产品吗？Web / iOS / macOS 结构一样吗？

#### 问题原貌

> DESIGN.md 适用于所有的平台和产品吗？比如 Web 产品、iOS App 产品、macOS 产品在不同的平台，DESIGN.md 的结构都是一样的吗？比如在网页里面有 H1，但在 iOS App 里面也有类似的 H1 吗？

#### 一句话答案

**结构上一样，但语义命名上 Web 偏多，iOS / macOS 用的时候需要做翻译层。** DESIGN.md alpha 当前**确实是 web-biased 的**，spec 自己也承认 token 命名不是 normative（非强制），你完全可以用 Apple 风格命名，但会失去部分自动 export 的便利。

#### 10.1.1 schema 层面：完全一样

DESIGN.md 的 5 类 token（colors / typography / rounded / spacing / components）在任何平台都成立：

```text
Color:      Web / iOS / macOS / Android 通用
Typography: 各平台都有 fontFamily / fontSize / fontWeight / lineHeight
Rounded:    各平台都有圆角概念
Spacing:    各平台都有间距系统
Components: 按钮、卡片、输入框是普世概念
```

所以**文件骨架完全可以跨平台复用**。一个 DESIGN.md 让 Claude Code 同时写出符合品牌的 Web 端 React 代码、iOS 端 SwiftUI 代码、macOS 端 AppKit/SwiftUI 代码，理论上完全可行。

#### 10.1.2 命名层面：H1 是 Web 的话术，iOS 不是

你的直觉很准。DESIGN.md README 的 Heritage 例子用了 `h1` / `h2` / `body-md` / `label-caps` 这种命名——这是 HTML 时代留下来的话术：

| 平台 | 文字层级的原生话术 |
|---|---|
| Web HTML / CSS | `h1 / h2 / h3 / p / span` + 自定义 class 如 `display / body / caption` |
| iOS（Apple HIG）| `largeTitle / title1 / title2 / title3 / headline / body / callout / subheadline / footnote / caption1 / caption2` |
| macOS（与 iOS 共享）| 同 iOS，但 sizes 略大 |
| Material Design（Android）| `displayLarge / headlineMedium / titleSmall / bodyLarge / labelLarge` |

如果你在 DESIGN.md 里只写了 `h1: { fontSize: 3rem }`，iOS agent 拿到这份文件会困惑——iOS 没有 H1 的概念，它的 SwiftUI 写法是 `Text(...).font(.largeTitle)`。

#### 10.1.3 三种应对策略

##### 策略 1：用「平台无关的语义名」（推荐给跨平台产品）

完全绕开 H1 / largeTitle 这种平台话术，用纯语义名：

```yaml
typography:
  display-xl:     # 对应 web 的 H1 / iOS 的 largeTitle
    fontSize: 32pt
  display-lg:     # 对应 H2 / title1
    fontSize: 28pt
  headline-md:    # 对应 H3 / title2 / headline
    fontSize: 22pt
  body-lg:        # body / large
    fontSize: 17pt
  body-md:        # body / regular
    fontSize: 15pt
  label-sm:       # caption / small label
    fontSize: 11pt
```

然后在每个平台的 token consumer 里做一层映射：

```text
SwiftUI:
  extension Font {
      static let displayXL = Font.system(size: 32, weight: .bold)
      static let bodyMD    = Font.system(size: 15)
  }

Tailwind:
  fontSize: {
    'display-xl': '2rem',
    'body-md': '0.9375rem'
  }
```

DESIGN.md spec 里明确写了 "Recommended Token Names (Non-Normative)"——**命名是你自由的**，他们的推荐只是建议。

##### 策略 2：一个平台一份 DESIGN.md（推荐给纯单平台 / 强平台差异产品）

```text
DESIGN.md            # 通用品牌色 + spacing + rounded（共享）
DESIGN-WEB.md        # web 专属字体层级 + 组件
DESIGN-IOS.md        # iOS Dynamic Type 层级 + iOS 组件
DESIGN-MACOS.md      # macOS 专属
```

每份用 `extends: DESIGN.md` 这种方式（虽然 alpha spec 还没正式支持，社区已经在提案中）。

cap4u 当前其实就接近这个模式——`Cap4uDesignTokens.swift` 是 iOS 专属的 runtime SSOT，未来如果加 Web / macOS surface，每个平台都会有自己的 token consumer。

##### 策略 3：在一份 DESIGN.md 里用 components section 做平台区分（不推荐，但能跑）

```yaml
components:
  web/button-primary:
    typography: "{typography.body-md}"
    rounded: 8px
  ios/button-primary:
    typography: "{typography.body-md}"
    rounded: 14pt
```

spec 允许任意 component 命名，所以这是合法的。但**可读性差**——一份 DESIGN.md 变成「多平台的并集」，很快会膨胀。

#### 10.1.4 我推荐的具体路径（针对 cap4u）

```text
当前：cap4u 只有 iOS。
建议：DESIGN.md 用平台无关的语义命名（策略 1），
      不用 h1 / h2 也不用 largeTitle。
      命名直接抄 Material Design 3 的 type scale：
        display-large / display-medium / display-small
        headline-large / headline-medium / headline-small
        title-large / title-medium / title-small
        body-large / body-medium / body-small
        label-large / label-medium / label-small

未来：如果加 Web 端（cap4u landing page？文档站？），
      不用改 DESIGN.md，只在 web 端写一个 token consumer 把
      display-large 映射到 .text-display-large CSS class。
```

#### 10.1.5 一个反直觉的结论

跨平台不是 DESIGN.md 的最强场景。DESIGN.md 真正擅长的是**「单产品 + 多 AI agent」**——你有一份 DESIGN.md，Claude Code / Cursor / Stitch 都能读懂同一套规则。

如果你的产品**真的跨多个平台**（iOS + Web + macOS），DESIGN.md 只能解决「颜色和间距共享」，真正的平台 idiom（导航模式、手势、平台动画）还是需要平台专属的 `references/platforms/ios/` 这种文档。cap4u 现在的结构（`.agents/references/platforms/macos/`、`.agents/rules/families/apple/`）其实已经预留了这一层，DESIGN.md 进来之后**不替代这一层**。

### 10.2 集群 B：如何确保 DESIGN.md 被严格执行？

#### 问题原貌

> 如何能够确保这个 DESIGN.md 能够被严格地执行？意思就是说，当整个产品涉及到视觉样式、控件以及组件的样式时，都能够被 DESIGN.md 控制，具体该如何做到？

#### 一句话答案

**靠「五层 enforcement」**——agent 必读、运行时强约束、CI lint、视觉回归测试、code review。**任何一层缺失，DESIGN.md 都会被「悄悄绕过」**。

#### 10.2.1 严格执行的 5 层

```text
第 1 层：agent 必读
   AGENTS.md / CLAUDE.md / .cursor/rules 里强制声明
   "任何 UI 任务前必须先读 DESIGN.md"
   防止 agent 凭印象生成而不查 token

第 2 层：运行时强约束
   代码层面让「直接写 hex 值」变得困难甚至非法
   只能消费 token consumer（DesignTokens.swift / Tailwind classes）

第 3 层：CI 自动 lint
   每次 PR 跑 npx @google/design.md lint
   contrast / broken-ref / orphaned token 出错就阻断合并

第 4 层：视觉回归测试
   每次 UI 改动后做截图 diff
   品牌色 / 间距 / 圆角偏移触发 fail

第 5 层：code review 纪律
   reviewer 明确检查 PR 是否引入 token 之外的视觉值
   引入则要求先 promote 到 DESIGN.md
```

任何一层缺了，其它层都会被绕过。cap4u 现在做到了第 1、2、5 层（部分），第 3、4 层缺失。

#### 10.2.2 每一层的具体做法

##### 第 1 层：agent 必读（cap4u 已做到一半）

在 `AGENTS.md` 里加：

```markdown
## UI 任务强制路由

任何 UI 相关任务（创建组件 / 修改样式 / 新建页面）：
1. 第一次代码编辑前必须读取 DESIGN.md
2. 同时读取 .vibe-doc/design-system.md（内部 SSOT）
3. 同时读取 .agents/rules/shared/design-defaults.md（negative defaults）
4. Scope Card 中必须列出本次任务涉及的 token 引用
```

cap4u 的 AGENTS.md 已经有「运行时强制路由」结构，加一段「UI 任务路由」即可。

##### 第 2 层：运行时强约束（cap4u 已部分做到）

这是 cap4u 已经做得最好的一层。`design-token.json` 里写着：

```text
usageRule: "Feature UI must consume semantic tokens from Cap4uDesignTokens.
            Direct RGB values are allowed only in DesignSystem files or
            content assets such as country flags."
```

强约束的实操做法：

- **iOS**：`SwiftLint` 自定义规则禁止 `Color(red:green:blue:)` 出现在 `apps/ios/**` 但不在 `DesignSystem/**` 下的文件里
- **Web / Tailwind**：ESLint plugin 禁止 inline 写 `style="color: #ABCDEF"`；只允许 `className="text-primary"`
- **更狠**：自定义 lint 禁止任何 hex 值出现在 `apps/**` 下的源码里（除了 DesignSystem 文件夹）

这一层做透了，agent 就**没法绕开 DESIGN.md**——它生成的代码必须走 token consumer，否则编译 / lint 报错。

##### 第 3 层：CI 自动 lint（cap4u 缺失）

```yaml
# .github/workflows/design-check.yml
- name: Lint DESIGN.md
  run: npx @google/design.md lint DESIGN.md

- name: Diff DESIGN.md against main
  run: npx @google/design.md diff main:DESIGN.md HEAD:DESIGN.md
```

每个 PR 都跑。任何一个：
- 颜色对比度不符合 WCAG AA → 失败
- token 引用错误（`{colors.primary}` 不存在）→ 失败
- 漏定义关键 section → warning

cap4u 当前是「单元测试覆盖 contrast」+「手工 review」，**漏掉新 token 是必然的**。接 lint CLI 是 2 小时工作量、永久价值。

##### 第 4 层：视觉回归测试（cap4u 缺失，但优先级中）

工具：Percy / Chromatic / Screenshot tests in XCTest。

```text
原理：
  baseline 截图（main 分支的 UI）
  PR 截图（current 分支的 UI）
  pixel-diff > threshold -> 标记需 review

价值：
  防止「agent 生成的代码编译过了但视觉漂移了」
  比如 button padding 从 12pt 变 10pt，token 没动但视觉变了
```

对 cap4u 当前规模（MVP 阶段、少数核心页面）来说，这一层可以晚一点做。但**生产上线前必须有**。

##### 第 5 层：code review 纪律（cap4u 已通过 PR Gate 部分实现）

最低成本但最容易漏。每个 reviewer 心中要默念两句话：

```text
"这个 PR 引入了 DESIGN.md 之外的视觉值吗？"
"这个 PR 引入的新组件，DESIGN.md 里有定义吗？"
```

cap4u 的 `.agents/rules/shared/pr-ci-governance.md` 已经覆盖 PR 流程，**只要在那里加 2 行 design-specific check 即可**。

#### 10.2.3 cap4u 当前的执行强度排序

| 层 | cap4u 现状 | 强度 |
|---|---|---|
| 1. agent 必读 | AGENTS.md 路由已经引用 design-defaults.md | 7/10 |
| 2. 运行时强约束 | Cap4uDesignTokens + usageRule 已写明 | 8/10 |
| 3. CI lint | 无 | 0/10 |
| 4. 视觉回归 | 无 | 0/10 |
| 5. code review | PR Gate 流程已建立但未明确 design check | 4/10 |

**最高 ROI 的下一步**：把第 3 层从 0 推到 7（接 `npx @google/design.md lint` 到 CI）。

#### 10.2.4 一个不能忽视的事实

即使 5 层都做了，**agent 仍然会有「按 prompt 字面理解硬上」的时刻**。比如你说「给我做一个红色警告按钮」，agent 可能直接写 `Color.red` 而不是 `Cap4uDesignTokens.error`。

这种时候第 2 层（运行时强约束）就是最后防线——**代码根本编译不过 / lint 不过**，agent 必须回头查 DESIGN.md。

所以「严格执行」的真正秘密不是某一层做到极致，**是 5 层互相补漏**。任何一层都可以失效，但 5 层一起失效的概率近乎 0。

### 10.3 集群 C：DESIGN.md 怎么产出？怎么维护和迭代？

#### 问题原貌

> 以前是用 Figma 做设计，完了之后一点一点地去提炼整个 Design System。但现在很多时候都是用 AI 直接来做设计，那最基础、最原始的那个 DESIGN.md 是如何产出的？这个 DESIGN.md 是如何维护、如何去迭代的？

#### 一句话答案

**AI 时代 DESIGN.md 的产出顺序倒过来了——以前是「Figma → 设计系统 → 代码」，现在是「DESIGN.md → AI 生成 UI → 看产出 → 反向修订 DESIGN.md」。DESIGN.md 成为设计师的新 canvas，不再是事后总结。**

#### 10.3.1 产出 DESIGN.md 的 4 种路径

##### 路径 A：从既有 Figma 提炼（传统路径，仍然有效）

适合：已经在 Figma 里搭过 design system 的设计师。

```text
1. Figma 文件 -> 用 Figma to Code Plugin / Figma Variables Export
2. 拿到 variables JSON
3. 转成 DESIGN.md 的 YAML frontmatter
4. 手写 Markdown body 的 rationale 部分
   (Figma 的「描述字段」可以做种子)
5. 用 npx @google/design.md lint 校验
```

这条路径**保留你过去 10 年的 Figma 产出**，是迁移成本最低的。

##### 路径 B：从既有代码反向生成（cap4u 适用）

适合：项目已经有运行代码，但没有正式的 design system 文档。

```text
1. 跑 npx @google/design.md generate --from tailwind.config.js
   或 --from path/to/DesignTokens.swift（社区有 extractor）
2. 拿到自动生成的 DESIGN.md 草稿
3. 人工修正：
   - 删除真正应该是「特例」的值（不是 token）
   - 补充 components section
   - 补充 Markdown body 的所有解释段
4. 跑 lint，修 contrast 问题
```

cap4u 走这条路径成本极低——从 `Cap4uDesignTokens.swift` 反向生成 DESIGN.md，可能 2 小时就能拿到第一版。

##### 路径 C：从公开 design system 改造（速度最快）

适合：从 0 开始的新产品，没有现成资产。

```text
1. 去 designmd.app（454 个公开 design system）挑一个气质接近的
2. 下载下来，改名字、改主色、改字体
3. 跑 lint
4. 直接进 agent 工作流
```

这条路径**几分钟就能拿到一份能用的 DESIGN.md**。代价是会带上原 design system 的某些痕迹（命名风格、组件分类），后续要逐步「品牌化」。

##### 路径 D：AI 协作从零生成（最新、也最少人讨论）

适合：你这种「用 AI 做设计」的工作流。

这一条单独展开说，因为它最贴近你描述的场景。

#### 10.3.2 AI 协作生成 DESIGN.md 的实操工作流

如果你想用 AI 帮你从零生成 DESIGN.md，不要直接说「帮我做一份 DESIGN.md」——那样的产出会很「平均化」，没有个性。

更好的工作流：

```text
Step 1：写一段「art direction prompt」（5-10 行）
  告诉 AI 你想要什么气质：
  "我在做一个帮非英语母语者打英文电话的 iOS App（cap4u）。
   用户场景是焦虑（不熟悉的语言 + 紧张的通话）。
   我想要的整体感觉：克制、温暖、专业但不冷漠，
   有一种『有人在你身边帮你』的安静陪伴感。
   绝对避免：高科技 / AI 感 / 冷蓝 / 玻璃拟态 / 工业风。
   参考气质：Linear 的克制 + Things 3 的温度。"

Step 2：让 AI 提一份 DESIGN.md 草稿
  Claude / GPT 会根据 art direction 选色、字体、间距。
  这一稿大概率不会完美，但**比直接说"做一份 design system"要个性化得多**。

Step 3：人审 + 修
  你作为设计师，逐行审：
  - 主色对吗？
  - 圆角是不是太大 / 太小？
  - 字阶够不够？
  - 哪个字段是 AI 凑数的？

Step 4：反向跑一次 UI 生成做验证
  让 Claude Code 用这份 DESIGN.md 生成 3-5 个核心页面。
  看视觉效果是否符合 Step 1 的 art direction。
  不符合 -> 回 Step 2 修 DESIGN.md，再跑一次。

Step 5：固化
  当 3-5 个页面都符合预期，DESIGN.md 落到 git 主线。
```

**核心心法**：**先有「不可妥协的气质 prompt」，再有 DESIGN.md，再有 UI**。如果跳过气质 prompt，直接让 AI 做 DESIGN.md，会得到一份「正确但乏味」的 design system——这也是为什么 designmd.app 上很多公开 DESIGN.md 看起来都很相似。

#### 10.3.3 维护和迭代的 3 种节奏

##### 节奏 1：每次 UI 任务后的「反向同步」

每次 AI 生成 / 你修改了 UI 之后，问自己一句：

```text
这次改动有没有引入 DESIGN.md 之外的视觉值？
  有 -> 决定：
    (a) 这是临时特例 -> 不进 DESIGN.md，但加注释解释
    (b) 这是新的通用 token -> 加进 DESIGN.md，对应改运行时
    (c) 这是错误 -> 改回到 DESIGN.md 已有的 token
```

cap4u 当前的 `design-token.json` 已经在做这件事——每次新加 surface（live call workspace、AI reply suggestions），都会回头补 token。

##### 节奏 2：每周 / 每个 sprint 的 audit

```text
跑一遍 grep "Color(red:" 或 hex pattern in source
   -> 找到所有「绕过 token」的地方
列表 review:
   哪些是合理特例（content assets like flags）？
   哪些是应该 promote 到 DESIGN.md 的？
   哪些是错误？
处理完更新 DESIGN.md 版本号 + version history
```

cap4u 的 design-system.md 已经有 Version History 章节，但目前是手工维护——可以加一个脚本帮助生成 audit 报告。

##### 节奏 3：每个 release / 季度的 major revision

```text
看过去 N 个月所有的 design 决策
重新审视 DESIGN.md 整体一致性：
   - Negative defaults 还成立吗？
   - 哪些组件用得最多？要不要 promote 到 spec?
   - 哪些 token 一年都没被引用？删掉
版本号大调（1.x -> 2.x）
```

这个节奏每年 2-4 次足够。

#### 10.3.4 一个反直觉的提醒

**不要把 DESIGN.md 当作「设计的产物」，把它当作「设计的输入」。**

旧 Figma 时代：
```text
设计师在 Figma 里做完 100 个屏 -> 提炼出 design system -> 给开发实现
DESIGN.md（如果有）是事后总结
```

AI 时代（也是 cap4u 的工作流）：
```text
设计师写 DESIGN.md（哪怕只有 30 行）-> AI 生成 UI -> 设计师审 -> 改 DESIGN.md -> 再生成
DESIGN.md 是设计师的主要 canvas，UI 是它的「渲染产物」
```

这种倒置在你身上其实已经发生——cap4u 的视觉一致性主要靠 `Cap4uDesignTokens.swift` 而不是某一份 Figma 文件强约束。你只是没意识到自己在做这种倒置。把它显式化，就是「设计师 → DESIGN.md 维护者」的转身。

### 10.4 集群 D：DESIGN.md 包含什么、不包含什么？Dark Mode / 颜色可访问性 在里面吗？

#### 问题原貌

> DESIGN.md 包含什么内容？它又不包含什么内容？
> 1. Dark Mode 和 Light Mode 的定义会包含在里面吗？
> 2. 颜色的可用性标准会包含在里面吗？

#### 10.4.1 包含什么（DESIGN.md alpha 当前 scope）

```text
✓ 颜色 token（colors）
✓ 字体 token（typography：fontFamily / fontSize / fontWeight / lineHeight / letterSpacing）
✓ 间距 token（spacing）
✓ 圆角 token（rounded）
✓ 组件级 token（components，含 hover / active / pressed 变体）
✓ Token references（{path.to.token} 引用）
✓ 整体气质 / 品牌人格（Overview section）
✓ 各 token 类别的 rationale（Colors / Typography / Layout / Shapes sections）
✓ Elevation / 阴影策略（Elevation & Depth section）
✓ 实操守则（Do's and Don'ts）
✓ contrast lint（CLI 内置 WCAG AA 4.5:1 检查）
```

#### 10.4.2 不包含什么（DESIGN.md 明确不管的东西）

```text
✗ 业务逻辑 / 信息架构 / 数据模型
✗ 用户研究结果 / persona / user journey
✗ 交互细节（手势、动画时长、状态机、reduced motion）
✗ 文案规范（应该在 COPY.md / ux-writing.md）
✗ 平台 idiom（iOS 导航模式 / macOS 菜单栏 / Web 路由）
✗ 可访问性的非颜色部分（screen reader / focus management / keyboard nav）
✗ 性能预算 / 加载策略
✗ i18n / l10n 规范
✗ 图标库 / illustration 风格
✗ 内容图像（country flags、产品图、emoji）
✗ Negative defaults（cap4u 的 design-defaults.md 那种「不要做什么」）
✗ Decision Order（设计冲突时的优先级排序）
✗ Appearance Policy（强制 light / 跟随 system / 强制 dark）
```

注意最后 3 项——这些是 cap4u 已经做、但 DESIGN.md spec 没有标准位置的东西。

#### 10.4.3 Dark Mode / Light Mode 在 DESIGN.md 里怎么处理？

这是当前 DESIGN.md alpha 最薄弱的一块。spec 里**没有官方的 dark mode 章节**。社区的几种 workaround：

##### 方式 1：颜色名带后缀

```yaml
colors:
  primary: "#B84636"
  primary-dark: "#FF9A85"
  surface: "#FFFFFF"
  surface-dark: "#111113"
```

简单，但**没有强制约束**——agent 不一定知道 `-dark` 后缀的语义。

##### 方式 2：用 components 的变体机制

```yaml
components:
  button-primary:
    backgroundColor: "{colors.primary}"
  button-primary-dark:
    backgroundColor: "{colors.primary-dark}"
```

冗余、组件多了会爆炸。

##### 方式 3：在 Markdown body 写自然语言规则

```markdown
## Colors

The palette has Light Mode and Dark Mode variants. In Light Mode,
primary surfaces use #FFFFFF; in Dark Mode they use #111113. Agents
should detect the user's system appearance and map tokens accordingly.
```

依赖 agent 「读懂自然语言」——不可靠。

##### 方式 4（cap4u 已经在做）：在 token 数据里就分 light / dark namespace

```json
{
  "color": {
    "light": { "surface": "#FFFFFF", ... },
    "dark":  { "surface": "#111113", ... }
  }
}
```

cap4u 的 `design-token.json` 用的就是这种 namespace 结构。**这比 DESIGN.md alpha 的标准做法更成熟**。

##### 我的判断

DESIGN.md spec 在这个问题上还没收敛。但 cap4u 已经有答案了——`color.light.*` / `color.dark.*` / `liveCallAdaptive.*` 三套 namespace 是更工程化的设计。在 DESIGN.md 标准里这件事还没正式做完，cap4u 的方案应该作为社区反向贡献提案（这一点在 8c 的建议 3 里也提过）。

#### 10.4.4 颜色可访问性在 DESIGN.md 里怎么处理？

这件事 DESIGN.md alpha **部分做了**，但不彻底。

##### DESIGN.md 已经做的

CLI lint 内置 contrast-ratio 检查：

```text
npx @google/design.md lint DESIGN.md
  -> 自动检查所有 component 的 textColor / backgroundColor 组合
  -> 不达 WCAG AA 4.5:1 -> warning
```

这是 token-level 的自动校验，**比 Figma 时代的「设计师手工查」可靠得多**。

##### DESIGN.md 没做的

```text
✗ 没有专门的 "Accessibility" markdown section
✗ 没有规定 large text 的 3:1 标准
✗ 没有规定 non-text contrast（图标、border、focus ring）
✗ 没有规定哪些 token pair 必须做对比度检查（你可以漏掉关键组合）
✗ 没有规定 reduced motion / dark mode 切换的可访问性影响
✗ 没有 keyboard / screen reader 相关规则
✗ 没有 WCAG version 标注（2.1 vs 2.2 行为不同）
```

##### cap4u 的优势

cap4u 的 `design-system.md` 单独写了一章 Accessibility Contrast Contract：

```text
明确写出：
  WCAG 2.2 AA 作为契约
  normal text >= 4.5:1
  large text >= 3:1
  non-text controls >= 3:1
  contrastRule：每个 semantic foreground/background token pair 必须达标
  decorative content（如国旗）豁免
  Runtime source 引用 Cap4uDesignTokens.Accessibility
```

**比 DESIGN.md alpha 完整一个量级**。

##### 综合建议

如果你做对外的 DESIGN.md（按 8c 建议 1 那种摘要版），把 cap4u 的 Accessibility Contract 内容**放到 Do's and Don'ts 章节**——这是当前 DESIGN.md spec 中唯一能容纳「accessibility 规则」的合规位置。

例：

```markdown
## Do's and Don'ts

✓ All readable foreground/background token pairs MUST meet WCAG 2.2 AA:
  - Normal text >= 4.5:1
  - Large text >= 3:1
  - Non-text controls (icons, focus rings, borders) >= 3:1
✓ Run `npx @google/design.md lint` on every PR
✗ Don't use raw RGB values outside the DesignSystem layer
✗ Don't introduce a new token without a contrast check
```

#### 10.4.5 「包含」与「不包含」的整体心法

DESIGN.md 不是设计系统的全部，**它是设计系统中「能被 AI agent 用结构方式消费」的那一层**。

```text
设计系统 = DESIGN.md
         + COPY.md / ux-writing rules（文案）
         + INTERACTION.md（手势、动画、状态机）
         + ACCESSIBILITY.md（screen reader / keyboard）
         + PLATFORM-IOS.md / PLATFORM-WEB.md（平台 idiom）
         + Figma 文件（视觉协作中间产物）
         + 实拍照片 / 插画风格 / 图标库
```

你可以把所有这些放到一份 DESIGN.md 里（DESIGN.md spec 允许「unknown sections」），但**这样会让它失去最强项——结构化的 token 表**。

更合理的做法：DESIGN.md 守住视觉 token 这一块，其它维度各起一份对应的 *.md。这正是 `AGENTS.md / SKILL.md / DESIGN.md` 三件套的扩展逻辑——未来会有更多 *.md 加入。cap4u 的 `.vibe-doc/` 已经在做这种垂直拆分。

#### 10.4.6 一句话总结这部分

```text
DESIGN.md alpha 包含：
  视觉 token + 组件 token + 设计 rationale + WCAG 对比度 lint

DESIGN.md alpha 不包含：
  Dark Mode 的标准做法（社区还在收敛）
  Accessibility 的完整章节（只有 contrast 自动校验）
  Negative defaults / Decision order / Appearance policy（cap4u 已自己补上）
  交互 / 文案 / 平台 idiom / a11y 的非颜色部分

判断标准：
  「能不能用 token 表达？」-> 进 DESIGN.md
  「能不能用 8 个标准 section 之一容纳？」-> 进 DESIGN.md
  其它 -> 另开一份 *.md
```

cap4u 在这件事上的成熟度，**实际上比 DESIGN.md spec 本身还领先半步**——你已经知道要把 negative defaults / appearance policy / accessibility contract 单独写出来。剩下要做的只是把这层共识反向贡献回标准。

## 附录 B：DESIGN.md 自检清单（5 分钟用）

如果你想快速判断自己的项目是不是「需要一份 DESIGN.md」：

```text
1. 我有 AI agent 在帮我写 UI 代码吗？
   是 -> 继续。
   否 -> 暂时不需要 DESIGN.md。

2. 我在意品牌一致性 / 视觉控制吗？
   是 -> 继续。
   否 -> agent 默认风格也能用，不必投入。

3. 我已经有一份「token + rationale」混合文档了吗？
   是 -> 加一份 DESIGN.md 做对外门面（cap4u 的情况）。
   否 -> 直接从 designmd.app 复制一份起步。

4. 我会用同一份设计跨多个平台 / 多个工具吗？
   是 -> DESIGN.md 的 export 功能价值最大。
   否 -> 价值小一些，但仍推荐。

5. 我担心未来会换 AI 工具（Claude → Cursor → ?）吗？
   是 -> DESIGN.md 是格式可移植性的最佳保险。
   否 -> 不必焦虑，但写一份不亏。
```

5 项中 ≥ 3 项「是」-> 强烈推荐写一份。
5 项中全「是」-> cap4u 就是这种情况，建议立刻加上对外门面。
