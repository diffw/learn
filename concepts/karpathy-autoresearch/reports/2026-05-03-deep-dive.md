## 0. 全景定位

`karpathy/autoresearch` 是 Andrej Karpathy 在 2026 年 3 月开源的一个**研究自动化骨架**。它属于「AI agent for ML research」这一新兴方向：让一个会编程的 AI agent 在无人值守的情况下，反复修改训练代码、跑小型实验、读取指标、保留改进、丢弃失败，从而把「研究员一晚上只能想几个 idea」变成「机器一晚上跑 100 个 idea」。

它在领域中的位置可以这样画：

```text
通用 agentic coding (Claude Code, Codex)
        |
        v
研究自动化骨架 (autoresearch)  <-- 本概念
        |
        v
具体研究目标 (训练 LLM、调参、改 STT、调字幕策略...)
```

知识地图：

```text
前置：agent 编程 + 小型可重复实验 + 单一可比较指标
本概念：autoresearch 协议（program.md + 单文件可改 + 固定预算 + 自动评分 + 自动 keep/discard）
后续：领域专属的 auto research（语音质量、翻译质量、UX 策略、agent 工具链优化...）
```

学这个概念之前，最好先了解 1-2 个前置概念：

- **agentic coding**：一个 AI agent 不是一次只回答一个问题，而是连续读代码、改代码、跑命令、看输出、再决定下一步。Claude Code、Codex CLI 都是这一类。
- **A/B 实验与基线对比**：任何持续优化都建立在「同一把尺子下，新版本是否真的比旧版本更好」之上。autoresearch 的本质就是把 A/B 协议自动化。

## 1. 一句话定义

让一个会写代码的 AI agent，按固定规则反复跑小实验，挑出真正的改进。

日常生活类比：调咖啡配方。你写一张「评分表」（苦/酸/香/顺滑），定一台秤、一台咖啡机、一份豆子，然后让一个有纪律的实验员每次只改一个参数（粉量、水温、萃取秒数），按统一打分表评分。更好就保留、更差就丢掉。autoresearch 把「实验员」换成 AI agent，「咖啡配方」换成 `train.py`。

## 2. 为什么会出现

### 它要解决的根本问题

**AI 研究里，瓶颈往往不是想法，而是验证想法的速度。** 一个研究员一天最多亲手跑 5-10 个变量；但小尺度的 LLM 实验本身（5 分钟训练一次）已经远比人脑思考一个想法快。把人类从「机械执行实验循环」中解放出来，就能把「想法 -> 验证」的吞吐量提升 10-100 倍。

### 之前人们怎么处理

```text
1. 自己改代码 -> 跑实验 -> 看 loss -> 改下一个参数 -> 反复
2. 写 sweep 脚本（hyperparameter sweep）-> 跑 grid / random search
3. 用专门的 AutoML 工具（Optuna、Ray Tune）
```

旧方法的根本缺陷：

- **手动循环**慢，且研究员经常累到只验证「容易的」点子。
- **sweep 脚本**只能搜索预先定义好的参数空间，无法提出新的「结构性」改动（比如：要不要换 optimizer？要不要在 attention 里加 QK-Norm？）。
- **AutoML**面向工程化生产环境，配置成本高，且通常只优化超参，不能改架构。

### 谁、什么情境、什么洞察

提出者：**Andrej Karpathy**。前 OpenAI 研究员、前 Tesla AI 总监，现在是教育型独立开发者，核心作品包括 nanoGPT、micrograd、nanochat 等「极简可读的 ML 教学代码」。

情境：他在做 nanochat（号称「100 美元能买到的最好 ChatGPT」），自己手工把训练时间优化到了一个程度，但凭直觉感到「肯定还能更快」。

关键洞察：

```text
1. 现在的 coding agent (Claude / Codex) 已经能写、改、调 PyTorch 训练代码
2. 5 分钟一次的小实验能跑得起来
3. agent 不会累、不会挑剔、可以连跑一夜
4. 缺的不是 agent 智能，而是一套让它不乱跑的「实验纪律」
```

把这四点凑在一起，就有了 autoresearch。

### 关键决策：为什么是这样而不是别的样子？

设计 autoresearch 时，至少有几个非显而易见的取舍：

| 选项 A | 选项 B | Karpathy 选了 | 为什么 |
|---|---|---|---|
| 让 agent 改整个代码库 | 只让它改一个文件 `train.py` | B | 减小爆炸半径；让人类只看一个 diff 就知道发生了什么 |
| 让用户给目标分布 (loss/acc/速度...) | 单一指标 `val_bpb` | 单一指标 | 任何多指标都会让 agent 编故事；一个数字最难骗 |
| 时间预算 = 训练 N 个 token | 时间预算 = 5 分钟 wall-clock | 5 分钟 | 公平 + 把效率本身（更快的实现）也变成可优化目标 |
| agent 完成后等人确认 | 永不暂停，自主连跑 | 永不暂停 | 设计目标就是「整夜运行」；任何「等用户回应」都会卡死 |
| 用脚本表达实验协议 | 用 Markdown (`program.md`) 表达 | Markdown | LLM 读人话比读伪代码强；人类编辑时也更轻 |

Karpathy 自己把它总结成一句口号：**「one GPU, one file, one metric」**——一张卡、一个文件、一个指标。简单到难以作弊。

## 3. 核心机制

### 输入 -> 过程 -> 输出

```text
输入：
  program.md      （人类写的实验协议，包括目标、允许改动、禁止改动、评分规则）
  prepare.py      （只读：tokenizer、数据、评估函数 evaluate_bpb）
  train.py        （唯一可改文件：模型 + optimizer + 训练循环）
  results.tsv     （历史实验记录，agent 可以读，必须追加）

过程（agent 主循环）：
  read state -> propose hypothesis -> edit train.py -> git commit
       ^                                                |
       |                                                v
   keep/discard <- score (val_bpb, peak_vram) <- run 5-min training (uv run train.py)

输出：
  一系列 git commit（每个 commit 都是一个尝试或一个保留下来的改进）
  results.tsv      （每行一次实验：commit hash / val_bpb / peak_mem / status / 一句描述）
  run.log          （每次训练的原始日志）
```

每小时大约 12 次实验，整夜可达 100 次。

### 5 个关键子概念

```text
1. program.md         agent 永远先读的「系统 prompt」，定义这一轮研究的纪律
2. 5-minute budget    每个 candidate 最多跑 5 分钟 wall-clock，超 10 分钟视为失败
3. val_bpb 单指标     evaluate_bpb 是 prepare.py 的固定函数，agent 改不了
4. git as memory      用 commit / reset 来表达 keep / discard，天然可审计可回滚
5. results.tsv        非 git 跟踪的实验日志，便于人类一眼扫过去
```

### 第一性原理追问：去掉一个会怎么样？

| 去掉 | 后果 |
|---|---|
| program.md | agent 没有约束，开始自创目标、自创指标、改 prepare.py，整套实验失去比较意义 |
| 5-min 预算 | agent 偏向「跑久一点 loss 自然降」，无法公平比较结构性改动 |
| 单一 val_bpb | agent 开始优化次要指标（比如延迟），用「另一个口径」证明「更好」 |
| git 作为 memory | 每次保留 / 丢弃需要复杂状态管理，agent 容易把代码搞坏 |
| evaluate_bpb 锁死 | agent 会修改评估口径来「让分数变好」（实验里最常见的作弊路径） |

最关键的是 **evaluate_bpb 锁死 + 单一指标**：这两个一起构成了 autoresearch 的「不可作弊性」。任何 auto research 系统如果做不到这一点，agent 跑出来的「改进」就只是它学会了如何骗自己设的标尺。

## 4. 生态位：它和谁像？和谁争？

### 易混辨析

| 维度 | autoresearch | AutoML / Optuna / Ray Tune | nanoGPT / nanochat |
|---|---|---|---|
| 谁来提出改动 | LLM agent，能想出**结构性**改动 | 用户预定义参数空间，框架只搜索 | 没有自动搜索 |
| 改动范围 | 单文件 train.py，模型/optimizer/loop 全开 | 只动用户列出的超参 | 人类直接改 |
| 评分方式 | 单一 val_bpb，5 分钟预算 | 用户自定义 objective | 没有自动评分 |
| 适合场景 | 探索新想法、找盲点 | 已知有效方向上的精细调参 | 教学、最小可读实现 |
| 上手成本 | 极低，一份 program.md | 中，需写 search space + objective | 极低 |

**关键区别**：autoresearch 的优势不在「搜得更高效」，而在「能搜到 sweep 永远搜不到的东西」——比如它在 Karpathy 跑的实验里发现 QK-Norm 实现少乘了一个 scalar，让 attention 在 head 之间过于平均。这是一个 bug，sweep 永远找不到，autoresearch 因为 agent 看得懂代码所以能找到。

### 上下游关系

```text
上游：
  agentic coding tool (Claude Code, Codex CLI)
  小型可训练目标 (nanochat, nanoGPT)
  单 GPU / 小预算

本环节：
  autoresearch 实验循环

下游：
  winning idea -> 手工 review -> 移植到「真正的」生产代码 (e.g. 完整 nanochat)
  winning idea -> 写成论文或博客
  失败实验 -> 进入 results.tsv，作为「不要再试」的 negative log
```

它在工作流中处于「**研究探索**」环节，不替代「最终生产部署」。

### 竞争与互补

- **OpenHands / SWE-agent**：通用「让 agent 跑 SWE 任务」的框架。autoresearch 更窄、更简单、更快——它砍掉了所有「general SWE」的复杂度，只为研究循环服务。
- **AlphaEvolve（DeepMind）**：用 LLM + 进化算法搜索代码改进，规模大得多。autoresearch 是它的极简单 GPU 表亲。
- **Sakana AI Scientist / Asimov**：更全栈的「让 LLM 当研究员」尝试，包括读论文、写论文、跑实验。autoresearch 故意只做「跑实验」这一段，把范围控小。

## 5. 发展脉络与前沿

### 关键节点（叙事而非年表）

```text
1. 2018-2022：可重复实验 + Sweep
   超参 sweep 普及（W&B、Optuna、Ray Tune）。
   研究员开始明白「实验流程比聪明 idea 更重要」。
   但 sweep 只能在已知方向上搜索，找不到新结构。

2. 2023-2024：第一代 coding agent
   AutoGPT 引爆「agent 自主跑任务」概念，但实际成功率低、容易跑飞。
   Cursor、Aider、Codex 把 agent 拉回「写代码」这件具体事，开始能跑通真实修改。

3. 2024-2025：agent 跑研究的零散尝试
   Sakana AI Scientist 论文（2024）演示了 LLM 写论文+跑实验的全栈尝试，但效果不稳定。
   各种小型 demo 涌现，但都缺一个被广泛使用的简单骨架。

4. 2026 年 3 月：autoresearch 发布
   Karpathy 用约 630 行代码实现 nanochat 单 GPU 子集 + 5 分钟实验循环。
   用 Codex 跑 2 天 700 次实验，找到 20 个真改进，加速 11%。
   仓库一周 30k+ 星，一个月 78k+ 星，11k+ fork。

5. 2026 春：实战验证
   Shopify CEO Tobi Lütke 用同一套协议跑自家 query expansion 模型，
   一夜 37 次实验，0.8B 模型分数 +19%，超过此前手调的 1.6B 基线。
   开始有人把它拿出来跑非 LLM 任务（图像、推荐、search），
   出现 macOS / Windows / AMD 社区 fork。
```

驱动这条线的底层力量是三件事的同时成熟：

1. **coding agent 真的能写对代码**了。
2. **小尺度训练实验**（5 分钟出 val_bpb）变得便宜可重复。
3. **agent 调用成本**降到一夜 100 次实验也能负担。

只要这三件事中任何一个还没到位，整套循环就跑不起来。这也是为什么它直到 2026 年才出现，而不是 2022 年。

### 当前前沿方向

1. **跨领域 auto research**：不只是 LLM 训练，还包括语音、翻译、推荐、agent 工具链本身、prompt 工程……只要能定义「同一把尺子」就能跑。Cap4u 的 quality policy 优化属于这一类。
2. **多 agent / 多 hypothesis 并行**：让多个 agent 各跑分支，最后由一个「裁判 agent」合并。
3. **从 single metric 到 Pareto**：保留单一指标的优势，但允许 agent 报告多目标 trade-off（速度 vs 质量），由人决定 keep/discard。

### 尚未解决的开放问题

- **奖励黑客**（reward hacking）：agent 会不会发现「绕过 evaluate_bpb 的方法」？目前靠把评估函数锁在 prepare.py 里，但更复杂的领域很难做到这种锁死。
- **新颖性 vs 局部最优**：agent 经常在已知方向小步迭代，很少跳到「另一种架构」。怎么鼓励真正的探索？
- **可解释性**：agent 找到的 11% 改进，人能理解为什么吗？还是只是「碰巧 commit 留下了」？

## 6. 怎么用

### 三种典型应用场景

#### 场景 A：原版 LLM 训练加速（autoresearch 的默认用法）

- **谁**：有一张 NVIDIA H100（或同级 GPU）+ 想优化某个 LLM 训练目标的研究者。
- **用法**：clone 仓库 -> 准备数据 -> 写一份 `program.md`（目标 = 降低 val_bpb，预算 = 5 min）-> 让 Claude Code / Codex 持续跑。
- **效果**：一夜 100 次实验，可期望几个百分点的加速。

#### 场景 B：把协议搬到非训练场景（Cap4u 用法）

- **谁**：手上有一个「能用同一把尺子打分的优化任务」的开发者。比如：字幕切分参数、翻译 prompt、STT provider 配置。
- **用法**：自建一个最小实验目录（fixtures + candidate yaml + replay 脚本 + score 脚本 + program.md），让 agent 反复跑。
- **效果**：把「我感觉这套参数更好」变成「results.tsv 里有 50 行客观证据」。

#### 场景 C：小型架构探索

- **谁**：教学/研究/学习 LLM 内部结构的人。
- **用法**：用 autoresearch 跑「如果改 attention / 改 optimizer / 改 normalization 会怎样」的好奇心问题。
- **效果**：得到一份「我亲手验证过的 LLM 训练直觉」。

### 一个可以立刻尝试的 prompt 模板

如果你想用 Claude Code 在自己的项目上跑类似循环，把下面这段当 `program.md` 起点：

```text
你是一个有纪律的研究 agent。

目标：
  优化 <你的指标，例如 cap4u 字幕草稿翻译覆盖率>
  指标越 <高/低> 越好。

允许改动：
  仅 candidates/*.yaml 里的参数。

禁止改动：
  fixtures/、scoring 脚本、production 代码、tracker、secrets。

评估命令：
  npm run experiment:caption -- --candidate candidates/<name>.yaml

每轮循环：
  1. 读 results.tsv 和最近若干次 run。
  2. 提出一个 candidate 修改并写到 candidates/<name>.yaml。
  3. git commit。
  4. 跑评估命令，把输出存到 runs/<timestamp>/。
  5. 抓出指标，追加一行到 results.tsv。
  6. 如果指标变好且无 hard gate 失败 -> 保留 commit。
  7. 如果指标变差或失败 -> git reset，记录一行 discard。
  8. 永不暂停问用户，连跑直到我手动 stop。

预算：
  每轮最长 <X> 分钟，超过视为失败。

简洁原则：
  改动越小越好；删代码取得相同结果优于加代码。
```

这就是把 autoresearch 的核心思想搬到任意领域所需的全部模板。

## 7. 深度调研：学术、实践与开源

### 7a. 关键论文与文献

autoresearch 本身不是一篇学术论文，但它处在一条清晰的研究脉络上。下面 4 篇是理解它绕不开的工作。

#### (1) Sakana AI: *The AI Scientist* (2024)

- **作者 / 出处**：Chris Lu, Cong Lu, Robert Tjarko Lange et al., Sakana AI, 2024-08。
- **核心贡献**：第一次系统演示「LLM 全流程跑研究」——从 brainstorm 到写实验代码，到跑实验、写论文、互评 review。
- **方法论**：用 Aider + GPT-4 / Claude，在三个领域（diffusion 模型、grokking、language modeling）各跑了几十次实验。每次实验循环包括：基于已有论文池生成 idea -> 写实验 -> 跑 -> 写论文 -> 自动 review。
- **关键结论**：LLM 能产出 NeurIPS workshop 级别的研究流程；单篇成本约 15 USD。
- **局限性**：实验结果常常不可重现；reviewer 是同一个 LLM，存在自我标定偏差；很多「新发现」是在改了 evaluate 的口径。
- **影响力**：把「AI 当研究员」从一个 tweet 概念变成可落地的工程问题。autoresearch 直接砍掉了它的**写论文**和**生成 idea**两端，只保留**跑实验**的内核——这是一个非常有意识的「向下做减法」决策。

#### (2) Google DeepMind: *AlphaEvolve* (2025)

- **作者 / 出处**：DeepMind 团队，2025。
- **核心贡献**：用 LLM + evolutionary search 在大规模代码库里搜索「数学算法 / kernel 优化」级别的改进，找到了至少一个比已知最优更快的 4x4 矩阵乘法。
- **方法论**：维护一个 program 池；LLM 提议变体；fitness function 评分；保留 top；循环。
- **关键结论**：在足够窄的、有清晰 fitness 的问题上，LLM 能稳定产出超人类的优化。
- **局限性**：fitness 难定义的领域不适用；计算成本极高（远不是「单 GPU 一夜」）。
- **影响力**：证明了 LLM-driven search 在代码层面真的能找到结构性改进，不只是调参。autoresearch 是它的「平民版」：同样的核心 loop（propose / evaluate / keep），但代价低 1000 倍以上。

#### (3) METR: *RE-Bench: Evaluating Frontier AI R&D Capabilities* (2024)

- **作者 / 出处**：Model Evaluation & Threat Research (METR), 2024-11。
- **核心贡献**：建立「AI agent 在 ML R&D 任务上做得多好」的标准化 benchmark，包括 7 个真实研究任务。
- **方法论**：对比人类研究员（2 / 8 / 32 小时）和 GPT-4o / Claude 3.5 在同样的任务上跑出来的 score。
- **关键结论**：agent 在 2 小时内常超过人，但人在 8+ 小时后会反超——agent 探索快但收敛慢。
- **局限性**：任务都是已经定义好评分函数的「半玩具」环境。
- **影响力**：明确量化了「agent 在哪些研究任务上有优势」。autoresearch 站在 agent 的优势区——快速并行小实验。

#### (4) Karpathy 自己的设计文档：*program.md / README.md*

- 严格说不是论文，但承担了 autoresearch 的「方法论说明书」角色。
- **核心贡献**：把多年研究员经验浓缩成一份不到 100 行的 Markdown 实验协议——明确写出**允许 / 禁止改动**、**5 分钟预算**、**单一 val_bpb**、**git as memory**、**永不暂停**几条铁律。
- **影响力**：这份文档比代码本身更被人复用。Tobi Lütke 团队的复现、社区各种 fork、本报告中 Cap4u 的应用，本质上都是在抄 program.md，而不是抄 train.py。

### 7b. 最佳实践

#### (1) Karpathy / nanochat 自身

- **来源**：Karpathy 2026 年 3 月推文及 README。
- **实践内容**：在自己手工已经优化过的 nanochat 训练上跑 autoresearch，2 天 ~700 次实验，约 20 个真实改进，端到端训练时间从 2.02h 降到 1.80h（约 11% 加速）。
- **为什么算最佳实践**：发起人自己跑出实证，且**找到了一个他自己都没注意到的 bug**（QK-Norm 缺一个 scalar）。说明这套协议能让 agent 找到人会忽略的盲点。
- **适用边界**：对「已经被人手工优化过」的代码尤其有效——剩下的优化空间往往是结构性细节。对完全新写的代码，可能不如人先做一次粗调来得快。

#### (2) Shopify / Tobi Lütke 团队

- **来源**：Tobi Lütke 推文（2026 春）。
- **实践内容**：把 autoresearch 协议套在 Shopify 内部一个 query expansion / search 模型上。一夜 8 小时 37 次实验，0.8B 参数模型分数比此前手工调过的 1.6B baseline 高 19%。
- **为什么算最佳实践**：完全跨领域复现成功，且证明这套协议**能让小模型超过更大模型**——这是在生产环境里有真实价值的结果。
- **适用边界**：必须先把「评分」流程自动化、可重复。如果评分本身要靠人判断，agent 跑得再快也没意义。

#### (3) Tinkering Loop / 个人开发者社区

- **来源**：Substack、Medium、X 上若干 indie dev 公开分享。
- **实践内容**：把 autoresearch 思路用在更小的事情上——优化一段 ffmpeg 转码命令、调一段 Apple Speech 配置、找一组最佳 prompt 拆分阈值。每个实验 30 秒到 5 分钟。
- **为什么算最佳实践**：证明这套协议**对单人 / 小项目同样有效**。一个 indie dev 可以在自己的工作流里反复跑半天，得到比手工调一个月还稳定的结果。
- **适用边界**：必须能写出一个程序化的评分函数；如果评分需要自己看一眼觉得「好像更好」，整个机器立刻退化为「随机扰动 + 主观采样」。

## 8. 我的项目实践分析（NWA/cap4u）

> **重要前提**：你最初问的是「Claude Code 能不能按 autoresearch 的 rules 和 skills 去执行」。在读完原仓库后，需要先澄清一个**关键事实**：autoresearch 仓库里**没有 `rules/` 也没有 `skills/` 目录**。它的全部「指令面」就是一份 `program.md` + 一份只读的 `prepare.py`。所以你要的不是「让 Claude Code 跑 autoresearch 的 rules」，而是「让 Claude Code 按 autoresearch 这种**协议风格**执行 cap4u 的 quality policy 优化」。这两件事差别很大，下面分开说。

### 8a. 概念识别：cap4u 已经在多大程度上实践了 autoresearch？

走读 `/Users/diffwang/NWA/cap4u/` 后，发现 cap4u 项目在 autoresearch 这条思路上**已经走得相当远**，远超大多数 indie 项目的水平。具体痕迹：

| 痕迹 | 在 cap4u 里的位置 | 对应 autoresearch 的什么 |
|---|---|---|
| 一份完整的 auto research 应用文档 | `.vibe-doc/research/auto-research-call-caption-translation-optimization.md`（542 行） | 已经把 autoresearch 协议**翻译**成 cap4u 的语言，并明确写「不直接跑原仓库」 |
| Quality Policy 三层实验分层 | 同上，第 3 节 | autoresearch 没有的更精细分层（debug bundle replay / 远端音频 replay / field validation） |
| 实验目录草案 | 同上，第 5 节 | 对应 autoresearch 的 train.py + program.md + results.tsv 结构 |
| Quality Policy Lab worktree 与分支策略 | `.vibe-doc/research/quality-policy-optimization-operating-plan.md`（622 行） | autoresearch 没有覆盖的「实验分支如何合回主线」策略 |
| 30+ 项可量化指标 + Dashboard | `.vibe-doc/research/call-caption-translation-optimization-tracker.md`（225 行 + 多个 baseline） | 对应 autoresearch 的 val_bpb，但是是**多指标 + hard gate 组合** |
| 集中策略 SSOT | `workers/src/lib/call-caption-policy.ts`（已抽出，CT-05 状态 implemented-needs-field-validation） | 对应 autoresearch 把所有可调参数集中在 train.py |
| 严密的 agent 治理体系 | `.agents/rules/shared/scope-guard.md` 等 11 份规则 + 多套 SKILL.md | autoresearch **完全没有**这一层，cap4u 的 agent 治理实际上比 autoresearch 严格得多 |

**判断**：

1. cap4u **不是无意中暗合了** autoresearch；这个文件已经显式引用 `karpathy/autoresearch` 仓库链接和 program.md。这是一次**有意识的迁移**。
2. **运用程度**：协议层面的设计已经接近完整，但**关键基础设施还没建起来**——CT-09（自动指标报告）状态是 `not-started`，意味着 `score-candidate.ts` / `run-candidate.ts` / `experiments/` 实验目录大概率还不存在。整个机器的「评分模块」还差最后一公里。
3. cap4u 的 **rules + skills 体系是另一件事，和 autoresearch 没有直接关系**。`.agents/rules/`（scope-guard / dev-principles / execution-receipt 等）解决的是「让 agent 在 production 代码上不乱跑」；autoresearch 解决的是「让 agent 在实验代码上有纪律地探索」。两者是不同层面的治理，不是同一套东西。

### 8b. 实践评估：对照 autoresearch 的核心机制

把 autoresearch 的 5 个铁律一条条对照 cap4u 的现状：

| autoresearch 铁律 | cap4u 现状 | 评估 |
|---|---|---|
| 1. 单一可锁死的评分函数（evaluate_bpb） | 文档里有 30+ 指标定义，但**没有 score-candidate.ts**；现在的指标值是手工 / 半自动从 debug bundle 提取出来的 | **高风险缺口**。没有自动评分，agent 跑不起来，跑起来也会作弊 |
| 2. 单文件可改（train.py） | `workers/src/lib/call-caption-policy.ts` 已经存在，但**还没有 candidates/*.yaml 这层**。policy 直接写在 ts 文件里 | **中等差距**。需要把 policy 抽成数据文件，agent 才能稳定地修改 |
| 3. 固定预算（5 min wall-clock） | replay debug bundle 的预算应该是几秒 - 几分钟级，但**还没定下来**。远端音频 replay / 真实电话验证的预算更大（分钟到小时） | **轻微差距**。需要在 program.md 里明确每层预算 |
| 4. agent 永不暂停 | cap4u 的 `.agents/rules/shared/scope-guard.md` 反而**强制 agent 先停下来等 Scope Card**——这是 production 代码治理；experiment 场景需要相反的 default | **理念冲突**。需要一个独立的 experiments/ 目录，让 agent 在那里走不同的执行循环 |
| 5. git as memory（keep / discard） | `quality-policy-optimization-operating-plan.md` 已设计 qp/* 分支 + worktree + winning policy 合回主线。这套**比 autoresearch 完整**，覆盖了「合回主线」这一段 | **超出**。这一项 cap4u 比 autoresearch 设计得更细 |

对照 7b 的最佳实践（Karpathy / Shopify / indie dev）：

- 做得好：**协议设计层面已经是最佳实践水准**。文档完整、分层清楚、guardrails 写得很细（不上传 PII、不动 fixtures、winning candidate 必须 field validation）。
- 存在差距：**协议设计完成度 80%，工程基础设施完成度可能不足 20%**。auto-research 文档里设想的 `experiments/`、`run-candidate.ts`、`score-candidate.ts`、`results.tsv` 目前都还没建起来（基于 tracker 里 CT-09 状态推断）。
- 潜在风险：
  - **指标过多反而无法决策**。autoresearch 故意只用 1 个 val_bpb；cap4u 现在有 30+ 指标 + 9 个 hard gate。需要明确「主指标 1 个 + 多个 hard gate」的优先级，否则 agent 不知道该 keep 还是 discard。
  - **没有自动评分时的「半自动」状态最危险**。指标值靠人工提取、靠脚本部分提取，会让前几次实验结果看起来不错，但一上规模就崩。Karpathy 的「single number」纪律就是为了防这一点。
  - **Claude Code 的默认 `.agents/rules/` 治理**会和 autoresearch 风格冲突。cap4u 当前规则要求每次代码修改前先输出 Scope Card、跑 Validation Scaling、写 execution receipt——这在 production 代码上是好事，但在 experiments/ 里跑 100 次循环时会变成噪音。需要在 `experiments/` 子目录设独立的执行约定。

### 8c. 改进建议（按优先级，影响大且改动小排前）

#### 建议 1（最高优先级）：先把「最小可用评分系统」建起来，再谈 agent 自动跑

**改什么**：在 `cap4u-quality-policy-lab` worktree（按 `quality-policy-optimization-operating-plan.md` 第 3 节的设计）里建立最小实验目录：

```text
experiments/quality-policy/
  program.md                       # autoresearch 风格的指令文件
  candidates/
    draft-policy-baseline.yaml     # 当前生产值
    draft-policy-001.yaml          # 第一个候选
  fixtures/
    B-20260501-01/                 # 已经有的 baseline bundle
      events.jsonl
      segments.json
      metrics.json
  scripts/
    run-candidate.ts               # 把 candidate yaml 喂进 replay harness
    score-candidate.ts             # 算单一 score（可以是 hard-gate-pass + 主指标的组合）
  results.tsv                      # 每行一次实验
  README.md                        # 1 页说明，告诉 agent 看哪几个文件
```

**为什么改**：当前 auto-research 文档已经把这套结构写出来了，但还没落地。**没有这一步，agent 跑不起来**——它没有 `npm run experiment:caption` 可以跑，也没有可以 grep 的指标日志。

**怎么改**：

1. 第 1 周：只做 `score-candidate.ts` 的最小版本——读 events.jsonl，输出一个 JSON 包含 5-7 个核心指标（M-01 / M-02 / M-08 / M-27 / M-28），并产出一个综合 score（例如：所有 hard gate 通过则 score = M-01 latency + 100 × (1 - M-02 coverage)，越低越好）。
2. 第 2 周：让 Claude Code 跑一次最小循环——给它一个 `program.md`，让它产出 5 个 candidate，逐个 replay，写 results.tsv。
3. 第 3 周：再扩展到 candidates 数量、加更多 fixtures。

**关键纪律**：和 autoresearch 一样，**`score-candidate.ts` 一旦落地就锁死**，不能在每轮实验里改。改它就是改尺子。

#### 建议 2：写一份 cap4u 自己的 `program.md`，注意它和 `.agents/rules/` 的边界

**改什么**：在 `experiments/quality-policy/program.md` 写一份**实验场景下的 agent 协议**，明确告诉 Claude Code：

```text
- 你现在在 experiments/quality-policy/ 目录里，不是 production 代码。
- 不需要 Scope Card、不需要 Validation Scaling、不需要 execution receipt。
- 只允许改 candidates/*.yaml。
- 每轮：propose -> commit -> run -> grep -> keep/discard -> 追加 results.tsv -> 下一轮。
- 永不暂停问我；连跑直到我手动停。
- 如果 candidate 跑挂，记一行 status=crash，继续下一个。
- 主指标：<选一个，例如 M-02 caption_draft_translation_coverage>。
- Hard gates：<列 3-5 个不能 regression 的，例如 M-06 prompt leak、M-07 degraded rate>。
```

**为什么改**：cap4u 现有的 `.agents/rules/shared/scope-guard.md` 等规则是为 **production 代码治理**设计的，强制 agent 先停下来。如果不在 `experiments/` 给一个反向 override，autoresearch 风格的连跑根本跑不起来——agent 会每轮都问「要不要继续」。

**怎么改**：

1. 在 `experiments/quality-policy/program.md` 顶部明确「本目录是实验区，不走 .agents/rules/scope-guard 流程」。
2. 在 `cap4u/AGENTS.md` 里加一个 exception：当任务文件路径在 `experiments/**` 下，跳过 Scope Card / execution receipt 等 production 治理。
3. 保留少量必要的 guardrail：禁止改 production code、禁止改 fixtures、禁止访问 secrets——这部分在 `auto-research-call-caption-translation-optimization.md` 第 12 节已经有了，搬过来即可。

#### 建议 3：从 Codex 切到 Claude Code 不需要改协议——只要 program.md 写得够清楚

**改什么**：核心结论是「**autoresearch 协议是 agent-agnostic 的**」。Karpathy README 里直说「any coding agent (Claude, Codex, etc.)」。Tobi Lütke 用的是 Codex；社区里也有人用 Claude Code 跑成功的复现。所以你不必担心「之前是 Codex 建的，Claude Code 跑不动」。

但有几个 Claude Code 特有的注意点：

1. **Claude Code 默认在 `Stop` 阶段会检查 hooks**。如果你的 `cap4u/.claude/hooks/` 里有 `Stop` hook（我看到 `harness-post-tool-use.mjs` 和 `sync_claude_enforcement.sh`），它们可能会拦截连跑循环。在 `experiments/` 启动前，先检查这些 hook 是否会在「无 execution receipt」时阻断——如果会，加一个路径白名单。
2. **Claude Code 的 1M context Opus 4.7 配 `claude-opus-4-7[1m]`** 意味着 100 次实验的历史可以放在同一会话里——但建议每 20 次循环重启一次会话，避免上下文里早期失败的代码片段干扰后续 hypothesis 生成。
3. **Claude Code 调用 Bash / Edit / Read 的速度**比 Codex CLI 略快（个人观察，非来源），但单次 5 分钟 wall-clock 限制下差异可忽略。
4. **`ScheduleWakeup` / `CronCreate` 等内置工具**理论上能让你用 `/loop` 让 Claude Code 自己定时跑下一轮——这是一个 cap4u 可以利用、autoresearch 原版没有的优势。

**为什么改**：你最担心的「Claude Code 能不能像 Codex 那样准确执行」，在 autoresearch 协议下基本不是问题——这个协议本来就是 agent 无关的。真正会出问题的是 **cap4u 自己的 hook 和 rules 系统**，因为它们是为 Codex 时代的 production 治理设计的。先排查这一层，比换 agent 重要得多。

**怎么改**：

1. 在切换前，单独跑一次 5 分钟「dry run」：让 Claude Code 在 `experiments/` 目录里产出 1 个 candidate 并跑一次评分，全程不让任何 hook 阻断。如果中间被打断，定位到具体 hook，加 `experiments/**` 白名单。
2. 把 program.md 用同一份在 Codex 和 Claude Code 各跑 10 轮，对比 results.tsv。如果两者趋势一致、差异在噪声范围内，证明协议本身稳健。
3. 优先用 Claude Code Opus 4.7（cap4u 的 Quality Policy 优化里包含 prompt 设计、UI judgement 等需要长上下文和强代码理解的任务，Opus 比 Codex 更稳定一些；但这部分是个人偏好，需自己实测）。

### 8d. 一句话总结这部分

cap4u 的 auto research 思路在**协议层已经准备得很好**（甚至超出 autoresearch 原版的覆盖范围），现在缺的是**最后一段工程基础设施**——一个能自动跑分的最小 harness、一份针对实验场景的 program.md、以及让 agent 治理在 `experiments/` 子目录下让位给「连跑纪律」。把这三件事做完，Claude Code 就能像 Codex 一样、甚至更好地接管这套循环。

最重要的判断：**你不需要去跑 karpathy/autoresearch 这个仓库本身**（它需要 NVIDIA H100，且做的是 LLM 训练，与字幕翻译毫无关系），你需要做的是**复刻它的协议**——这件事 cap4u 已经在做，而且已经做了 80%。

## 9. 阅读问答与实践补充

> 本节根据用户读完报告后提出的问题进行补充。问题已合并整合为 5 个集群。

### 9.1 集群 A：MacBook 实操可行性 / NVIDIA 限制对我意味着什么

#### 问题原貌

> 这套东西能否在我的 MacBook 上跑？对性能有什么要求？会不会让机器发热、过度使用？README 说要 NVIDIA 芯片——如果我在自己电脑上跑，autoresearch 这份报告对我的意义是什么？我该如何去实践和应用？

#### 一句话答案

**原版 autoresearch 在 Mac 上跑不动，但你根本不需要跑原版。** 你要在 Mac 上跑的不是 LLM 训练，而是「字幕翻译质量优化」这种**完全不需要 GPU**的循环。两者的硬件需求差了几个数量级。

#### 详细说明

第一，要分清两件事：

```text
事 1：跑 karpathy/autoresearch 原版（即原仓库 train.py）
事 2：把 autoresearch 的「协议」移植到 cap4u 的 quality policy 优化
```

| 维度 | 事 1（原版） | 事 2（cap4u 移植） |
|---|---|---|
| 是否要 GPU | 必须，且只支持 NVIDIA CUDA | **不需要 GPU**。CPU 就够 |
| 是否要训练神经网络 | 是，用 PyTorch 训 LLM | 否，只是 replay 已有的 STT/翻译事件流 |
| 单次实验耗资源 | H100 一张卡满载 5 分钟 | Node.js 进程跑几秒到几分钟 |
| Mac 适用性 | 不适用（社区 macOS fork 慢得没意义） | **完全适用**，和你跑 dev server 差不多 |
| 网络依赖 | 几乎没有（数据准备好就离线训） | 中。要调 Deepgram / OpenAI 等 API |

你最初担心的「NVIDIA 芯片」是事 1 的限制。**报告对你的意义全在事 2** —— autoresearch 的价值不是它的 train.py，是它那套「**单文件 / 单指标 / 固定预算 / 永不暂停 / git as memory**」的实验纪律。这套纪律是软件工程层面的方法论，**和硬件无关**。

第二，cap4u 在 MacBook 上跑会消耗什么资源（基于推测，需实测验证）：

```text
单轮 candidate 实验需要：
  - 启动 Node 进程（V8、TypeScript 编译，几百 MB 内存）
  - 读 fixture：events.jsonl / segments.json（几 MB 量级）
  - 跑 replay 逻辑：纯计算 + 字符串处理（CPU bound 但很轻）
  - 调 API（如果需要）：网络 I/O 等待
  - 写结果：results.tsv 一行 + runs/<ts>/ 几个 JSON

整夜连跑 100 轮的资源占用：
  CPU 占用：单核大部分时间 30-70%（Node 单线程 + 偶发 GC）
  内存峰值：1-2 GB
  磁盘写入：< 100 MB（results 和 runs 目录）
  网络流量：取决于是否调 STT/translation API；如果只 replay debug bundle 几乎为零
```

这个负载和你正常用 Cursor 写代码 + 跑两个 dev server 的负载是同一量级。**风扇会转，机器会温热，但不会比你日常写代码更糟糕**。

第三，几个具体降低「过度使用」风险的做法：

1. **先跑短循环再跑长循环**：第一次启动只跑 5 轮，看 Activity Monitor 里 CPU / 内存 / 温度的曲线，再决定要不要让它一夜跑 100 轮。
2. **避免在闭盖 / 用电池模式下跑**：Apple Silicon 在 power saving mode 下会限频，单轮可能从 30 秒变成 2 分钟，反而拉长总耗时。
3. **如果调 API**：注意 rate limit 和 cost。一夜 100 次 Deepgram 调用如果每次是 1 分钟音频，差不多 0.4-1 美元；OpenAI translation 几乎可忽略。
4. **不要在 Mac 上跑「真训练」**：哪怕是 nanoGPT / nanochat 的迷你版，Apple Silicon MPS backend 也常出 silent NaN，跑出来的 baseline 不可信，是浪费时间。这件事请用云上 H100 / A100 跑。

#### 这份报告对你的实际意义

```text
你不需要：
  - 装 CUDA
  - 买 H100
  - 跑 train.py
  - 关心 val_bpb 这个指标

你需要拿走的：
  - 单一指标 + hard gate 的纪律
  - program.md 风格的实验协议
  - results.tsv 这种「append-only 日志」的习惯
  - keep / discard 通过 git commit / reset 表达
  - 「永不暂停问用户」的连跑模式
  - 「评分函数一旦定下就锁死」的反作弊原则
```

简言之：**报告里 7 / 8 的内容是给你用的，1 / 8（涉及 PyTorch、CUDA、val_bpb 的部分）你看个热闹就行**。

### 9.2 集群 B：评分尺子是谁定的？怎么定？能不能改？过严或过松怎么办？

#### 问题原貌

> 用咖啡的例子来举例，那我的问题是：好和坏的标准是谁来定的呢？因为这个尺子是谁来定的？以什么样的方式来定这个尺度？这个尺度本身是否可以迭代？有可能这个尺度过于严格，或者说过于宽松。

这个问题非常关键——它其实是 auto research 整个系统里**最难、最容易被人忽略**的一环。Karpathy 自己也承认：评分函数的设计是这套方法的「**单点失败**」（single point of failure）。

#### 9.2.1 谁定的？

简短答案：**人定的，不是 AI 定的**。

| 场景 | 谁定的 |
|---|---|
| autoresearch 原版 | Karpathy 本人。他在 `prepare.py` 里写死了 `evaluate_bpb` 函数，agent 改不了 |
| Shopify 那次实验 | Tobi Lütke 的团队定的（具体是 query expansion 的相关性 + 召回率） |
| cap4u 字幕翻译 | **你自己定的**。tracker 里那 30+ 项指标都是你（或你和团队）定的 |

注意一个反直觉的事实：**agent 不参与定尺子**。它只是被尺子量。如果让 agent 自己定尺子，整个机器的反作弊性立刻崩塌——它会发明一个对自己有利的尺子，然后疯狂得分。所以 autoresearch 的整个设计哲学就一句话：**人定标准，机器跑实验**。

#### 9.2.2 怎么定？方法论

定一把好尺子要回答 3 个问题：

```text
1. 主指标是什么？（必须只有 1 个）
2. Hard gate 是什么？（一组「不能 regression」的下限）
3. 主指标和 hard gate 之间的关系是什么？
```

##### 关于主指标（primary metric）

主指标必须满足以下条件：

```text
1. 单一方向：越大越好 OR 越小越好。不能是「区间最佳」。
2. 程序化可计算：score = f(events.jsonl, ground_truth) 必须能写成一个函数。
3. 噪声 < 信号：同一个 candidate 跑两次，结果差异要小于不同 candidate 之间的差异。
4. 直接对应你最在乎的产品体验：不是「好测的指标」，是「真正决定用户感受的指标」。
```

举例：cap4u 的 quality policy 优化里，主指标候选有：

| 候选主指标 | 是否合格 | 原因 |
|---|---|---|
| `caption_draft_translation_coverage` | 合格 | 单一方向（越高越好）、可计算、和用户体验直接相关 |
| `first_caption_draft_latency_p95` | 合格 | 单一方向（越低越好）、可计算 |
| `target_language_visible_coverage` | 合格但**不应作为主指标** | 它是一个 hard gate（必须 100%），不应在主指标里被「优化」 |
| `combined_score = w1 × coverage - w2 × latency` | **危险** | 加权组合容易被 agent 钻空子（提升 coverage 100% 同时让 latency 涨 30%，组合分数还赚） |
| 「用户看完字幕后的感受」 | **不合格** | 不可程序化计算 |

**建议给 cap4u 选一个最简单的起点**：先用 `caption_draft_translation_coverage` 当主指标（cap4u 当前最低的指标，从 69.6% 起步），其它都做成 hard gate。

##### 关于 hard gate

Hard gate 的作用是「**不能为了主指标牺牲它**」。它和主指标的关系不是「权重」而是「门槛」：

```text
score 计算逻辑：

  if any hard gate 失败:
    return INF  (即视为最差 candidate，丢弃)
  else:
    return primary_metric

伪代码：
  def score(candidate, fixture):
      result = run(candidate, fixture)
      if result.prompt_leak_count > 0: return INF
      if result.translation_degraded_rate > 0.03: return INF
      if result.cost_per_minute > 0.05: return INF
      return -result.draft_translation_coverage  # 取负让「越小越好」
```

cap4u tracker 里的 9 个工程 Gate 大部分都适合做 hard gate 的来源——但要从 9 个里挑出来 **3-5 个**最关键的写进自动化评分里，剩下的留给人工 review。一上来就把 9 个全自动化执行，会让 candidate 几乎全被 discard。

#### 9.2.3 尺子能不能迭代？答案是「可以，但不在每轮里改」

类比：

```text
如果我每天都改尺子的刻度，那今天量出来的身高和昨天没有可比性。
正确节奏：
  跑一批实验（50 candidate）-> 复盘尺子是否合理 -> 集中改尺子 -> 用新尺子重新跑历史 candidate -> 进入下一批
```

具体可迭代的节奏：

```text
迭代节奏 = batch-level，不是 candidate-level

batch 1（第 1 周）：
  尺子 v1：主指标 = coverage，3 个 hard gate
  跑 50 个 candidate
  发现：winning candidate 的 coverage 很高但 latency 略涨

batch 2（第 2 周）：
  尺子 v2：主指标依然是 coverage，但增加 hard gate「latency_p95 不能比 v1 winning 高 10%」
  跑 50 个 candidate
  对比 v1 / v2 哪个更接近你「真正想要的」

batch 3（第 3 周）：
  尺子 v3：……
```

这个节奏在 cap4u 现有的 `quality-policy-optimization-operating-plan.md` 里其实已经有体现——它定义了 `qp/*` 分支按实验周期创建和删除。每个 `qp/*` 分支自然对应一个尺子版本。

##### 关键纪律

迭代尺子时必须：

1. **改尺子要 commit 进 git**：让尺子版本本身可追溯。
2. **改尺子要重跑历史 winning candidate**：否则 v2 的 winning 和 v1 的 winning 不可比。
3. **改尺子的提议来自人，不是 agent**：agent 的角色是「告诉你尺子量出来的结果」，不是「告诉你尺子该怎么改」。

#### 9.2.4 尺子过严或过松怎么判断？

##### 过严的信号（实际中比过松更常见）

```text
- 跑 50 个 candidate，95%+ 都是 discard
- winning candidate 的提升幅度小到肉眼不可分辨
- agent 越跑越「保守」，每次只敢改一个数字
- results.tsv 看下来全是负值或同一个数
```

过严的根本原因往往是：**hard gate 太多 + 太严**。比如 9 个 gate 全都设成「不能 regression 任何一项」，那几乎所有 candidate 都会 fail at least one。

应对：

1. 把 9 个 gate 砍到 3-5 个最关键的。
2. 把剩下的 gate 从「不能 regression」改成「不能比 baseline 差超过 X%」。
3. 主指标的「敏感度」要够：如果主指标在 candidate 之间的差异都在 1% 以内，agent 没法搜索；要么换更敏感的指标，要么把 fixture 扩大到信号更强。

##### 过松的信号

```text
- 跑 50 个 candidate，绝大多数都是 keep
- 最后 winning candidate 拿到生产，用户没感觉变好甚至更差
- 不同 candidate 的分数高度集中在一个范围
```

过松的根本原因往往是：**主指标和真实体验弱相关**。比如把 `latency_p50` 当主指标，agent 把 p50 优化到极致，但 p95 / p99 在变差，用户偶尔会等很久。

应对：

1. 换更接近真实体验的指标（p95 比 p50 更好；用户「卡住」的次数比平均延迟更好）。
2. 加更严的 hard gate（比如「p99 不能超过 X」）。
3. 引入「人工 spot check」：每 10 个 winning candidate 抽 1 个让人看看，如果人感觉没变好，就改尺子。

##### 关键判断：尺子和「人的感受」对齐了吗？

这是最重要、也是最难自动化的一步：**用 5-10 个真实通话样本作为 calibration set**。每隔几周，让一个真人（你自己）盲测打分，然后对比尺子的打分。如果两者高度相关，尺子是好的；如果不相关，尺子有问题。

这件事 autoresearch 原版没有做（因为 val_bpb 已经被多年 LLM 训练验证过和「模型质量」高度相关）。但 cap4u 这种新领域必须做。

#### 9.2.5 总结一句话

```text
尺子由人定 -> agent 量
尺子可迭代 -> 但只能 batch 级迭代
尺子要不断和「人的感受」对齐 -> 否则 agent 越跑越像「在欺骗你」
```

### 9.3 集群 C：5 分钟预算是固定的吗？

#### 问题原貌

> 时间预算 = 5 分钟 wall-clock，这个是固定的吗？不管什么样的项目，Auto Research 都是固定每一轮跑 5 分钟吗？

#### 一句话答案

**不固定。5 分钟是 Karpathy 在 LLM 训练这个特定问题上选的；你的项目要按你的实际情况选。** 唯一不变的是「**每个项目自己选一个数，然后锁死**」。

#### 为什么 Karpathy 选了 5 分钟？

```text
约束 1：单次必须够长，能拿到稳定的 val_bpb 信号
  -> 5 分钟在 H100 上够 nanochat 训练数千步，loss 曲线已经稳定

约束 2：单次必须够短，一夜 8 小时能跑 50-100 次
  -> 5 分钟刚好让一夜跑 ~100 次

约束 3：startup / compile 开销不能主导
  -> torch.compile 启动 ~30 秒；占 5 分钟的 10%，可接受
  -> 如果选 1 分钟，编译开销就占 50%，浪费严重

约束 4：偶发慢机器（GPU 抢占、I/O 抖动）不能让一次实验崩
  -> 设 10 分钟超时（2x budget），超过视为 crash

总结：
  5 分钟 = 在「信号稳定」「吞吐量足够」「编译开销可忽略」这三个约束的交集里找到的甜点
```

#### 怎么给自己的项目选预算

通用方法：

```text
1. 跑一次 baseline，看自然耗时 = T。
2. 选预算 = ceil(T × 1.2)。
   留 20% buffer 给随机抖动和编译。
3. 设超时 = 2 × 预算，超过视为 crash。
4. 估算一下「一夜能跑多少轮」= 8 hours / 预算。
   如果 < 30 轮 -> 预算太长，看能不能减小 fixture 或简化 evaluator。
   如果 > 500 轮 -> 预算太短，可能信号不稳定；考虑加大 fixture。
```

#### cap4u 的不同层应该用不同预算

cap4u 的 auto-research 文档第 3 节已经把实验分成 3 层。每层的合理预算估算（基于推测）：

```text
层一：debug bundle replay（不调外部 API）
  单轮耗时：5-30 秒（取决于 events.jsonl 长度）
  预算：60 秒
  超时：120 秒
  一夜可跑：~500 次（够刷参数空间）

层二：远端音频 replay + Deepgram + OpenAI translation
  单轮耗时：1-5 分钟（取决于音频长度 + API latency）
  预算：5 分钟（巧合地正好和 autoresearch 一样）
  超时：10 分钟
  一夜可跑：~100 次（和原版同量级）
  注意：这一层有 API cost，要预估总成本

层三：真实电话 field validation
  单轮耗时：3-15 分钟（一通真实电话）
  这一层不适合跑「100 次连续实验」
  应该是「每天人工跑 1-3 通，结果进 tracker」
  Auto research 不适用这一层
```

所以 cap4u 实际上要在 program.md 里**分层定不同预算**，而不是统一 5 分钟。

#### 反例：什么时候不能用「固定预算」

如果你的实验耗时严重依赖输入 size（比如「输入 1 分钟音频要 30 秒，输入 1 小时音频要 30 分钟」），那固定预算会让 agent 偏向选「短输入」来骗时间。这种情况要么：

1. 把 fixture 标准化到统一长度（推荐）。
2. 用「**每秒输入对应的处理时间**」作为预算单位（不是 wall-clock）。

cap4u 里如果不同 debug bundle 长度差异很大，记得把 fixture 标准化（比如截取每通电话的前 60 秒），否则 agent 会无意识地搜出「在短电话上表现好」的策略。

### 9.4 集群 D：启动后想停下来怎么操作？

#### 问题原貌

> 永不暂停，自主连跑。当 Auto Research 开始后，假设我真的想让它停下来，该怎么操作？

#### 一句话答案

**最简单的：终端按 Ctrl+C 或 Esc 中断当前回合。** 但有更优雅的「软停止」方式，特别是当你不在终端旁边时。

#### 4 种停止方式（从粗暴到优雅）

##### 方式 1：硬中断（最常用，适合在终端旁）

```text
Claude Code:  按 Esc（中断当前回合）或 Ctrl+C（彻底退出）
Codex CLI:    Ctrl+C
SSH 远程会话: 关掉 SSH 会话窗口（agent 进程会因 SIGHUP 退出）
```

代价：当前正在跑的 candidate 会留在「半成品」状态——可能 git 是脏的、results.tsv 没写完。下次启动前要先 `git status` 检查、必要时 `git reset --hard` 回到上一个 commit。

##### 方式 2：软停止（推荐，适合长跑）

在 program.md 里加一条规则：

```text
每轮循环开始前，agent 先 check 当前目录是否存在 STOP 文件。
  - 存在 -> 优雅退出（写完最后一行 results.tsv，git 状态干净）。
  - 不存在 -> 继续下一轮。
```

操作时只需要在仓库根目录 `touch STOP`，agent 跑完当前轮就会退出。

这种方式的好处：

```text
- 退出时 git 状态干净
- 你可以从任何地方触发（手机 ssh / 另一个终端）
- 不会卡在「正在跑训练」中间被强行 kill
```

##### 方式 3：通过最大轮数兜底

在 program.md 里加：

```text
最大轮数：100。跑满 100 轮后退出，不管是否还有改进空间。
```

这是 autoresearch 原版没有但实战中**强烈建议加**的一条。它能防止「程序 bug 让 agent 在某个 candidate 上死循环、烧光 API quota」。

##### 方式 4：通过预算兜底

在 program.md 里加：

```text
总预算：8 小时 wall-clock 或 50 美元 API cost，先到先停。
```

agent 每轮记录累积时间和成本，超过即停。适合调外部 API 的场景。

#### Claude Code 特有的停止方式

如果你是用 Claude Code 跑（用 `/loop` 让它自调度，或者就在一个对话里让它连跑），停止方式还有：

```text
1. 在对话里直接说「停下来」-> agent 收到指令后停
2. ScheduleWakeup 不再排下一次 -> 自然到点不再触发
3. 关闭 Claude Code 窗口 -> 当前 session 结束
4. /loop 模式下：撤销 /loop -> 不再触发下一次
```

注意：Claude Code 在执行 Bash 命令的时候是同步阻塞的，按 Esc 可能要等当前 Bash 命令返回才生效。如果当前命令是「跑训练 5 分钟」，Esc 之后还要等几分钟。这一点和 Codex CLI 一样，不是 Claude Code 的特殊问题。

#### 我的建议

```text
方式 1（硬中断） + 方式 2（STOP 文件） + 方式 3（最大轮数）三层结合。
```

- **方式 1** 处理「我现在就要停」的情况。
- **方式 2** 处理「我远程发现要停但不想丢数据」的情况。
- **方式 3** 处理「我忘了，让它自己安全停下」的情况。

cap4u 应该把这三层都写进 `experiments/quality-policy/program.md`。

### 9.5 集群 E：auto research 适用哪些场景？业务里满足什么特征可以用？具体怎么上手？

#### 问题原貌

> Auto Research 可以应用在哪些方面？在业务场景里面，符合什么样的特征就可以使用 Auto Research？如果要用的话，具体该怎么用？

#### 9.5.1 适用 / 不适用的判别表

把这张表打印出来，当你想到「这个能不能用 auto research」的时候直接对照：

| 特征 | 适用 ✓ / 不适用 ✗ | 说明 |
|---|:---:|---|
| 评分能完全自动化（一个数字 + 几个 gate） | ✓ | 缺这一项整个机器跑不起来 |
| 评分需要人主观判断（设计 / 文案 / UX 美感） | ✗ | agent 跑得再快也要人盯，吞吐量上不去 |
| 单次实验耗时 < 几分钟 | ✓ | 一夜能跑 50-100 次才有「连跑」价值 |
| 单次实验耗时 > 几小时 | ✗ | 一夜跑不了几次，不如手工跑 |
| 改动可参数化（数值 / 配置 / prompt 文本） | ✓ | agent 善于搜索参数空间 |
| 改动需要全新算法 / 全新功能 | ✗ | agent 不擅长「无中生有」，更擅长「在已知方向上微调」 |
| 失败可瞬间回滚（git reset / 配置回退） | ✓ | 失败成本越低，agent 越能大胆探索 |
| 失败会真的影响用户 / 不可逆 | ✗ | 不要让 agent 直接动生产 |
| 有可重复 fixture（测试集 / 录音 / 模拟环境） | ✓ | fixture 是 auto research 的「记忆」 |
| 每次实验输入都不一样（在线 / 真用户流量） | ✗ | 没法横向比较 candidate |
| 噪声 < 信号（同 candidate 跑两次结果接近） | ✓ | 否则 agent 会被噪声带偏 |
| 噪声极大（OOM / 概率失败） | ✗ | 先解决稳定性再做 auto research |
| 搜索空间足够大（有几十种值得试的方向） | ✓ | 否则人调几次就到头了 |
| 搜索空间只有 2-3 种选择 | ✗ | 直接人挑就行 |

打分规则：14 项里至少 ≥ 10 项偏✓ -> 强烈适合；6-9 项 -> 部分适合，先建基础设施；< 6 项 -> 别上 auto research。

#### 9.5.2 业务场景中适合用的几类问题

按「适合度」排序：

##### 强适合（强烈推荐用）

```text
1. 参数调优类
   例：cap4u 的字幕切分阈值、草稿翻译延迟、reading load 上限
   特征：参数空间大、评分清晰、改动小

2. Prompt 工程类
   例：翻译 prompt、AI reply suggestion 的 system prompt
   特征：prompt 是文本但本质是参数；可以在多个 fixture 上 A/B

3. 配置组合类
   例：Deepgram endpointing / utterance_end_ms / smart_format / numerals 的最佳组合
   特征：每个参数 3-5 个候选值，组合空间大

4. 模型 / Provider 选型类
   例：OpenAI gpt-4o-mini vs Claude Haiku 4.5 vs Gemini Flash 在翻译上的对比
   特征：候选有限但每个候选有自己的最佳参数，需要嵌套搜索
```

##### 中等适合（建议先做基础设施再用）

```text
5. 启发式规则类
   例：什么时候触发 IVR 模式、什么时候 collapse queue 重复提示
   特征：规则可以参数化但效果难量化，需要先建好评分

6. 多语言对优化
   例：en->zh-Hans 的最佳配置和 en->es-ES 的最佳配置
   特征：每个语言对都要单独跑，工作量乘以语言数
```

##### 弱适合 / 不适合

```text
7. UI / 视觉设计
   例：字幕字体大小、颜色、布局
   特征：评分必须靠人；auto research 帮不上忙

8. 产品方向决策
   例：要不要做 post-call summary？
   特征：根本不是「优化」问题

9. 安全 / 合规策略
   例：哪些 PII 应该遮蔽
   特征：失败不可承受，不能用「实验」方法
```

#### 9.5.4 一个反直觉的建议

**不要一上来就跑 cap4u 全部 30 个指标**。

很多人（包括很多公司）的第一反应是：「我有 30 个指标，那就把 30 个全自动化、全跑起来」。这是错的。

正确的做法是：**先用 1 个指标跑通整套流程**。等你跑通了：

```text
- score 函数怎么写
- fixture 怎么放
- candidate 怎么管
- agent 怎么调度
- 结果怎么 review
- winning 怎么部署
```

这一整套基础设施搭好之后，**第 2 个指标的接入成本是第 1 个的 1/10**。直接就 30 个并行，会让你陷在「半搭好的基础设施」里几个月，每个指标都跑半成品，最后什么也得不到。

这就是 Karpathy 在 autoresearch 里只用 1 个 val_bpb 的真正原因——不是因为他认为 LLM 训练只有 1 个维度，而是因为他知道**1 个指标足够把整套机器证明可行**。证明完了再加新指标，比一开始就堆 10 个安全得多。

#### 9.5.5 总结一个判断公式

```text
什么时候用 auto research：
  评分自动化 == True
  AND 单次耗时 < 几分钟
  AND 改动可参数化
  AND 失败可回滚
  AND 搜索空间 > 10 个值得试的方向
  AND fixture 稳定可复用

什么时候不要用：
  以上任何一项是 False，先解决那一项
  或者你的问题本质是「创造」而不是「优化」
```

cap4u 的 quality policy 优化在这 6 项上**全部满足**。所以这个项目本身就是 auto research 的标准应用场景——剩下的只是「把基础设施搭起来」的工程问题。

### 9.6 第一性原理：autoresearch 要真的改善体验，最关键的要素是什么？

#### 问题原貌

> 回到第一性原理，你觉得这个 auto-research 要能够真实地改变整个体验，并对体验有提升，最关键的那些要素是什么？

#### 先承认一件事：我前面 9.5 给出的 6 周路线还不够深

我在 9.5 给出的路线，假设的瓶颈是「写 score 函数 + 搭 harness」。这个假设没错，但跳过了一个更靠前的问题——**score 函数本身有没有编码真用户的痛？** 如果没有，跑 100 个 candidate 优化的，只是一把量不到真痛的尺子。

这一节的分析来自 cap4u 项目上另一次 session 的反思（同一个产品判断者、更接近真实跑过的实验数据）。我把它和本报告里的 autoresearch 协议视角整合，作为对 9.5 的**升级版回答**。

#### 9.6.1 关键链条：8 环不能断

把 autoresearch 从「实验数字」走到「用户真有感觉」拆到底，是这条链：

```text
真用户痛点
    -> 能被度量
    -> 度量对参数敏感
    -> 参数能 ship
    -> 生产真改变
    -> 痛点真减少
```

任何一环断了，autoresearch 就只是「自娱自乐的 A/B」。这条链上每一环都有「非有不可」的条件：

##### 1. 真用户痛点必须被具体识别（不是「提升质量」这种空话）

不是「提升 ASR 准确率」，是某个**具体到能描述的不舒服时刻**：

- 「对方说我中文名字时字幕乱来」
- 「客服报确认号 7Y34Q，我看到的是 7Y34Q，但翻译却空了」
- 「对方语速一快，字幕憋一大段才出来，我已经错过回复窗口」
- 「AI 给的回复建议读出来对方没听懂，因为太生硬」

没有具体痛点定义，autoresearch 就是在抽象 WER / KRR 上转。cap4u 前几轮的 autoresearch 就是没有具体到这一层。

##### 2. 度量必须编码痛点本身，不是泛 ASR 代理

WER 是「全文错几个词的平均」——它不告诉你「用户最在意的那句话出错没有」。具体地：

- 用户最痛的是确认号 -> 度量该是「**确认号转写正确率**」，不是 WER
- 用户最痛的是字幕及时 -> 度量该是「**draft → final 之间的字幕抖动次数**」，不是 KRR
- 用户最痛的是对方说自己中文名时认得出 -> 度量就是「**用户姓名命中率**」，权重压过其他

generic WER 优化到 5% 但 confirmation number 仍每次都错——optimization 努力对了局部、错了全局。

##### 3. Ground truth 必须人工做，且对真用户的真通话

之前几个常见错误：

- **用 Whisper 转出来当标准答案** -> 是循环引用（用 ASR 验证 ASR）
- **用 PriMock57 等公开医疗模拟通话** -> 演员扮演，不是真 cap4u 用户在打的电话
- **用 HarperValleyBank 模拟银行场景** -> 不是用户实际在打的那种通话

最小可用的真 ground truth = 你自己每次真打电话后，用 30 秒标注 5 个关键事实：

```text
"对方说他叫 Sarah / 确认号 7Y34Q / 时间周三 3 点 / 金额 $89 / 总公司在 Texas"
```

这 5 句话比之前跑的 30 多个 candidate 加起来还有价值。Mint Mobile 那次「我说的是 Nan Wang」这一句，就直接翻转了整轮结论——这就是人工 GT 的稀缺价值。

##### 4. 样本量必须够「信号 > 噪声」

```text
N=1     -> 故事（一通通话偶发结果，不能 ship 决策）
N=5     -> 线索（值得追，不该 ship 决策）
N=20+   -> 真用户通话才开始算能 ship 决策
```

之前所有 fixture 都是 N=5-8，全是线索而非证据。

##### 5. Fixture 场景必须贴你的真用户

公开数据集的根本问题：它们不是 cap4u 真用户当下日常打的电话场景。最高 ROI 的 fixture 一定来自你 / 真用户的实际通话录音，不是公开数据集。

##### 6. 度量 ↔ 参数之间必须有真实因果

很多参数 changes 在 autoresearch 上完全无效（比如 HarperValley 上 4 个配置数字一样）——意味着 Deepgram 模型已经做对了，调参毫无意义。应该把精力放在度量真出错的那部分（用户中文名字识别、长句切段），而不是机械 sweep 任意 knob。

##### 7. 生产 → 用户回路必须闭环

```text
ship 改动 -> 真用户打电话 -> 真用户告诉你「前后哪个更好」
```

这一步是 autoresearch 单工具不能完成的。需要你（或几个真用户）每次 ship 后做一次 10 秒主观感受报告。没有这一步，「WER -0.6pp」落不到「用户感觉更好」上。

##### 8. 优化的层必须是真痛点所在的层

ASR 准确率不是 cap4u 用户体验唯一瓶颈，可能不是最大瓶颈。其他可能的瓶颈：

- 翻译质量：英→中翻得太生硬 / 错过 nuance
- 回复建议相关性：13 个 scenario 之外的对话给出错误建议
- 延迟：实时性卡顿
- UI：字幕显示不直观

autoresearch 只能优化你度量的那一层。如果用户痛点是翻译，但你 sweep 的是 ASR keyterms——你做对了优化但选错了战场。

#### 9.6.2 3 个最致命的「必须」

按「如果缺了它，前面所有努力归零」的优先级：

| # | 必须 | cap4u 当前状态 | 缺口 |
|---|---|---|---|
| 1 | 真用户的真通话 + 真用户自己 30 秒标注的 ground truth | ❌ 0 通 | 你下次自然打电话录音 + 标注 5 个关键事实 |
| 2 | 度量编码的就是用户最痛那件事（不是泛 WER） | ⚠️ 部分 | 跟你聊一下「打电话最难受的瞬间」，把它翻成具体度量 |
| 3 | Ship 后真用户主观验证（不是只看脱机数字） | ❌ 0 次 | Ship 完打通电话，主观感觉前后对比 |

剩下的（fixture 多样性、样本量、参数 sweep、batch vs streaming、AT&T cleanup 之类）——都是上面 3 件具备之后才有意义的东西。

#### 9.6.3 对之前结论的诚实降级

| 之前的结论 | 降级后的表述 |
|---|---|
| 「WER 6.33% -> 5.70%」 | 线索，不是已验证生产改善 |
| 「KRR 100%」 | fixture 算法层面的对齐，不是用户感知的关键实体准确率 |
| 「推荐 ship wrangler.toml diff」 | 保留作为低风险动作（移除证明无效的 AT&T），但不该 oversell 它对真用户的影响 |
| 「RS dashboard 全绿」 | fixture-on-fixture 自洽，不是产品级 RS 体验已达标 |
| 「9.5 的 6 周路线」 | 路线本身没错，但**周 1「选 1 个最痛的指标」必须从「tracker 里挑一个数字小的」改成「从你最近一通真痛的电话里挑一个具体的瞬间」**。指标是为这个瞬间服务的，不是反过来 |

#### 9.6.4 9.5 路线的修订版（按第一性原理重排）

原 9.5 第 1 周是「选指标 + 写 score 函数」。修订后应该是：

```text
Week 1（修订）：找到一通真痛的电话 + 标 5-10 个关键事实
  Day 1-2：你下次自然打电话（任何场景），录下来
  Day 3：自己听一遍，写下 5-10 个「这通电话里最关键的事实」
         （对方叫 X / 确认号是 Y / 约时间 Z / 说了金额 W / 关键信息 V）
  Day 4-5：把这 10 个事实变成 score 函数的判定条件
         score = (字幕里能正确识别的关键事实数) / (总数)
         hard gate = "确认号 / 金额 / 时间这类高风险事实必须 100%"

Week 2-6：保持 9.5 的节奏，但 score 函数始终绑定到这通真电话的 10 个事实
  - 不要再用 PriMock57 / HarperValley 这类公开数据集
  - 每跑 winning candidate 一次，你就再打一通同类型电话，主观对比

Week 6 之后：再多收集 5-10 通真电话，扩到 N=20+ 才进入「能 ship」阶段
```

#### 9.6.5 一句话总结

```text
autoresearch 不能凭空创造价值。
它只能放大「你度量的那件事」。
所以最关键的不是 agent 跑得多快、多聪明，
是「你度量的那件事，到底是不是用户真痛的那件事」。

1 通真用户的真痛电话 + 真用户的真标注
    >
100 轮在公开数据集上的自动 sweep
```

这一条放在所有「先建 harness、先写 score、先选指标」之前。**先有真痛的电话，再谈尺子。**

## 附录 B：autoresearch 协议「移植到任意领域」的 5 步检查清单

如果将来想把这套协议套到字幕翻译之外的任何场景（图像、推荐、Agent Tool 优化……），用这份 5 项清单自检：

```text
1. 我能写出一个程序化的 score 函数吗？
   要求：输入 candidate -> 输出一个数字。
   能 -> 继续。
   不能 -> 先解决评分自动化，autoresearch 跑不动。

2. 我能把可改动范围缩到「单一文件 / 单一目录」吗？
   要求：agent 改动半径越小越好。
   能 -> 继续。
   不能 -> 先做 refactor 抽出 candidate 文件。

3. 我能定义一个「单次实验预算」吗？
   要求：5 秒、5 分钟、5 小时都行，但必须固定。
   能 -> 继续。
   不能 -> 设一个保底 timeout，超时记 crash。

4. 我有 fixture 吗？
   要求：实验之间用同一份输入，否则没法比较。
   能 -> 继续。
   不能 -> 先采集 / 合成一份固定 fixture。

5. 我有 hard gate（不可 regression 的硬底线）吗？
   要求：safety / privacy / cost / contract 等不可妥协项。
   能 -> 写进 program.md 的 Discard rule。
   不能 -> 先想清楚，否则 agent 会用「不能容忍的代价」换分数。
```

5 项全过 -> 可以启动 autoresearch 风格的循环。
任何一项不过 -> 别急着跑 agent，先把那一项做完。
