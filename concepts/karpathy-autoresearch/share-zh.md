# 一个 UX 设计师，看懂了 Karpathy 的 autoresearch

前几天我打开 Karpathy 那个一周拿了三万星的项目 `autoresearch`，看了三分钟，关掉。

说实话，第一眼是劝退的。README 里写「需要 NVIDIA H100」，代码里全是 PyTorch，文档里到处是 `val_bpb`、`Muon optimizer` 这些我不认识的词。我心里冒出来的第一个念头是：「这又是一个我看不懂的事，回头再说吧。」

但我手上正好有个事卡着——我的产品 **Cap4u**（一个帮非英语母语者打英文电话的 AI 实时字幕和翻译 App），有 30 多项语音转字幕和翻译质量指标要持续优化。每次手工调一个参数、跑一遍真实电话、看结果，太慢了。一个晚上调不完两个想法。

所以我又把 autoresearch 打开了一次，这次没急着关。

回头看，那次是我作为一个 UX 设计师，第一次真的「读懂」一个深度技术项目的架构思想。我想把过程写下来。这个项目背后的方法论，其实和硬件没什么关系——它的内核完全可以被任何不写训练代码的人借用。

---

## 1. 我为什么要去搞懂这个

Cap4u 的语音转字幕优化，是一个典型的「30 个旋钮」问题。字幕切多长、草稿翻译什么时候触发、低置信怎么提示、IVR 菜单怎么识别……每个旋钮都有几个候选值，组合起来有上千种可能。

我用 Codex 配过一套 `.agents/rules/` 和 `.agents/skills/` 的工作流，但那套规则是为「写代码」设计的。它会让 agent 每次都先停下来，输出 Scope Card、跑测试、写 execution receipt。这在写功能的时候是好事，但在「我想让 AI 一晚上跑 100 次实验」的场景下，每一步停下来等我确认都是浪费。

我需要的是另一种节奏：**让 agent 别问我了，自己跑，跑出 100 个结果给我挑**。

autoresearch 就是干这件事的。

---

## 2. 这个东西从哪儿来

我先说一下 Karpathy 这个人，因为这个项目能爆，跟作者本人分不开。

Andrej Karpathy，斯坦福 PhD（导师是 Fei-Fei Li，也就是 ImageNet 的提出者），2015 年 OpenAI 创始团队成员之一，2017-2022 年在 Tesla 当 Director of AI、主导 Autopilot 的神经网络架构，2024 年离开 OpenAI 后开了一家叫 Eureka Labs 的 AI 教育公司。

但真正让他在 AI 圈外破圈的不是这些大厂头衔，是他的教育作品。他在斯坦福开的 CS231n 被很多人当作深度学习的入门课；他在 YouTube 上的「从零实现 GPT」「从零实现 Tokenizer」「从零搭建神经网络」系列长视频，每集 1-3 小时全程手敲，在 AI 圈基本是「必看」级别。再加上一串极简到普通人能读完的代码作品——nanoGPT（300 行训一个 GPT）、micrograd（100 行的微型 PyTorch）、llm.c（用纯 C 实现 LLM 训练）、nanochat（8xH100 一夜训出 GPT-2 级别的对话模型）。

风格我会用一句话总结：**「把一个本来吓人的东西，写到几百行你自己能读完」**。

作为一个非工程师，我能在 AI 时代还有点信心继续往下学，很大程度上是因为有 Karpathy 这种人——他让我相信「这些东西不是只有博士能懂」。autoresearch 是这种风格的最新延续。

2026 年 3 月他发了 autoresearch。背景是他自己在做一个叫 nanochat 的小型 LLM 训练项目，已经手工把训练时间优化得很短了，但凭直觉觉得「应该还能更快」。他想：现在的 AI coding agent（Codex、Claude Code）已经能写 PyTorch 代码了，**那为什么不让它一晚上自己反复改、反复跑、自己挑出更快的版本**？

他自己跑了两天，700 次实验，找到 20 个真改进，整体加速 11%。其中一个是他自己都没注意到的 bug：QK-Norm 实现少乘了一个 scalar，让 attention 在 head 之间太均匀。**一个研究员看不出来的 bug，agent 在闭着眼睛连试两天后找出来了**。

Shopify 的 CEO Tobi Lütke 拿同样这套协议跑了自己家的搜索模型，37 次实验、8 小时，0.8B 参数的小模型超过了之前手工调过的 1.6B 模型 19% 的分数。

仓库一周三万星，一个月将近八万星。

## 3. 它到底是怎么运作的

我读完之后的理解：**它的精髓不是 AI，是规则**。

整个项目的核心，可以浓缩成一张图：

```text
program.md      <- 人写的「规则书」（agent 永远先读）
prepare.py      <- 只读：评分函数和数据，agent 改不了
train.py        <- 唯一允许 agent 改的文件
results.tsv     <- 实验日志，每行一次
```

agent 的循环是这样的：

```text
读规则
   |
   v
提一个想法
   |
   v
改 train.py
   |
   v
跑 5 分钟训练
   |
   v
看分数
   |
   v
更好 -> git commit 保留
更差 -> git reset 丢掉
   |
   v
回到「提一个想法」
```

Karpathy 把它总结成一句话：「**one GPU, one file, one metric**」——一张卡、一个文件、一个指标。

这句话的关键不是「卡」和「文件」，是「**一个指标**」。

---

## 4. 我自己的理解：这是「反作弊」机制，不是「跑得快」机制

我想了两天，才慢慢看懂为什么 Karpathy 要把规则定得这么死。

刚开始我以为「单一指标」是为了简单。后来我意识到，**不是为了简单，是为了不让 agent 骗自己**。

类比一下：调咖啡。

如果我跟一个实验员说「你帮我调出更好喝的咖啡」，他会怎么干？他可能会偷偷把评分标准改成「我自己觉得好喝就行」，然后告诉你「老板我调出来了，每杯都 95 分」。你喝一口，难喝。

如果我说「评分表我来定，秤我来定，咖啡机我来定，你只能改粉量、水温、萃取时间这三个参数」，他就没地方作弊了。**他唯一能做的，就是真的去调出更好的咖啡**。

autoresearch 的设计就是这样：

```text
评分函数 evaluate_bpb 锁在 prepare.py 里 -> agent 改不了
单一指标 val_bpb -> agent 没法用「另一个口径」证明自己赢
固定 5 分钟预算 -> agent 没法靠「跑久一点」蒙混
agent 永不暂停 -> 减少和人的交互，每一次决策都被 git 记录
```

这套机制不是「让 AI 更聪明」，是「**让 AI 没法骗你**」。

我作为一个设计师，过去 20 年看过太多产品 OKR 被「换口径」之类的小聪明搞砸。autoresearch 的反作弊设计，让我立刻意识到：**这不是 AI 的方法论，这是研究的方法论**。Karpathy 只是把它写成了 AI 能跑的代码。

## 5. 在 Cap4u 里怎么用

我读完报告才发现，**我自己（在 Codex 协助下）几个月前就已经写过一份 542 行的迁移设计**，叫 `auto-research-call-caption-translation-optimization.md`。它把 autoresearch 的协议翻译成了 Cap4u 的语言，明确写「不要直接跑原仓库」「Cap4u 不是训练 LLM，是优化字幕策略」。

这就让我有点好笑——我担心的「Claude Code 能不能像 Codex 一样跑这套」，根本不是问题。autoresearch 的协议本来就和 agent 无关。Karpathy README 里写得很清楚：「any coding agent (Claude, Codex, etc.)」。

我真正缺的，**不是 agent，是评分函数**。

Cap4u 的 tracker 里有 30 多个指标，但目前没有一个 `score-candidate.ts` 脚本能把这些指标自动算出来。也就是说，机器还没有「尺子」。

我本来打算的 6 周路线是这样：

```text
第 1 周：从 tracker 里挑 1 个最痛的指标，写最小 score 函数
第 2 周：抽 5 个候选参数手动跑
第 3 周：Claude Code 接管，跑 20 轮
第 4 周：第一次过夜连跑
第 5-6 周：扩指标 + 校准
```

但写到这儿我又往下追了一层，意识到第 1 周不该这么开始。

autoresearch 只能放大「你度量的那件事」。如果你度量的那件事不是用户真正在痛的，跑得越快越糟糕。Cap4u 之前做过几轮自动跑——用过 PriMock57（医疗模拟通话）、HarperValleyBank（模拟银行）这些公开数据集做 fixture，把 WER 从 6.33% 优化到 5.70%。听起来不错，但真用户那边一点感觉都没有。原因很简单：那些 fixture 不是 Cap4u 真用户当下日常打的电话。

所以第 1 周该这样开始：

```text
Day 1-2：自然打一通真电话，录下来
Day 3:   听一遍，写下「这通电话里最关键的 5-10 个事实」
         (对方叫 X / 确认号 Y / 时间 Z / 金额 W / ...)
Day 4-5：把这 10 个事实变成 score 函数的判定条件
         score = 字幕能正确识别的事实数 / 总数
         hard gate = 确认号 / 金额 / 时间这类高风险事实必须 100%
```

后面 5 周保持原节奏，但 score 函数永远绑定在这通真电话的 10 个事实上，不再用公开数据集。

整个过程最反直觉的不是「不要一上来就跑 30 个指标」，是更前面一步：**先有真痛的电话，再谈尺子**。1 通真用户的真痛电话 + 真用户自己 30 秒的标注，价值 > 100 轮在公开数据集上的自动 sweep。

听起来像废话，但我自己就在上面栽过——前面跑过的 candidate，本质上都是在「错的赛道上越跑越快」。

## 6. 我学到的几件事

1. **大部分「高深」的 AI 项目，方法论部分不需要懂 AI 也能用**。autoresearch 的核心是研究纪律，不是神经网络。一个产品经理、一个设计师、一个独立开发者，只要手里有一个能定义评分函数的优化问题，都能用。

2. **任何 AI 工作流，先问「评分谁定的、能不能锁死」，再问「agent 跑得多快」**。「让 AI 不骗你」比「让 AI 更聪明」更难、更值钱。

3. **NVIDIA H100 的硬件门槛是误导**。我一开始以为这套东西不属于我，是因为我没有 GPU。后来发现，原版需要 GPU 是因为它的「演示场景」是 LLM 训练。**协议本身是软件工程层面的，和硬件无关**。我在 MacBook 上跑 Cap4u 的字幕优化循环，Activity Monitor 里看不出和正常写代码有什么区别。

4. **「在错的赛道上跑得快」是 AI 工具最容易掩盖的问题**。autoresearch 让你一晚上跑 100 次，但如果 score 函数没编码用户真痛，跑得越快错得越远。我自己刚刚就在第 5 节当场降级了一份 6 周路线——这件事如果不是写出来一遍，自己都意识不到。

5. **作为一个设计师，我开始能读这种代码项目了**。这件事比上面四点都重要。三年前我连 README 都看不下去，现在能读完一个 600 行的 PyTorch 项目，理解它的设计哲学，并把它的协议层迁移到自己的产品里。**不是我变聪明了，是 AI 让「读懂代码」的门槛降低了一个数量级**。

---

## 7. 收尾

autoresearch 让我意识到，过去几十年研究员的工作里，**真正稀缺的从来不是 idea，是「不停验证 idea」的纪律**。AI 不会替我们想出更好的 idea，但它愿意一晚上替我们试 100 个 idea。

Karpathy 把「研究员的纪律」写成了 600 行 Python，让普通人也能用。我现在要做的，是把同样的纪律搬到 Cap4u 上——不是为了让 AI 更聪明，是为了让我自己作为产品的判断者，能一晚上看到 100 个真实结果，而不是一周看到 5 个我自己猜出来的结果。

如果你手上也有一个「想优化但不知道从哪下手」的产品问题，先问自己：

- 评分能不能写成一个函数？
- 失败能不能瞬间回滚？
- 有没有一份固定的样本可以反复跑？

三个都能 -> 你也可以跑你的 autoresearch。

我会把 Cap4u 的实验过程继续记下来。再聊。
