## 0. 全景定位

PR (Pull Request) 与 CI (Continuous Integration) 是现代软件工程中**协作与质量保障**的两大核心实践。它们属于软件开发过程（Software Development Process）大领域中"代码集成与交付"这一环节，位于个体编码与最终部署之间的关键桥梁位置。PR 解决的是"多人协作时代码如何被审查和合并"的问题，CI 解决的是"合并后如何快速验证代码是否破坏了系统"的问题。两者在现代开发工作流中几乎总是协同出现——PR 触发 CI，CI 结果反馈到 PR，形成一个质量反馈闭环。

知识地图：

```
版本控制 (Git) -> 分支策略 -> **PR & CI** -> CD (持续交付) -> 生产部署
```

学习本概念之前，最好先了解的前置概念：

1. **Git 分支模型**：Git 允许开发者在不影响主线的情况下创建独立的工作分支，是 PR 机制的物理基础。
2. **自动化测试**：针对代码行为编写的可重复执行的验证程序，是 CI 能够"自动判断代码是否正确"的基础能力。

---

## 1. 一句话定义

**PR**：请求将你分支上的改动合并进主分支，同时让他人审查。

**CI**：每次代码变更后自动构建并运行测试，立刻发现集成问题。

日常生活类比：PR 像是给编辑部投稿——你写完文章交给编辑审阅，编辑批注修改意见，你改完再确认发表。CI 像是印刷前的自动校对机——稿件一入稿池，机器立刻检查错别字、格式问题、标点规范，几分钟内给出"通过/不通过"的结论。两者配合：投稿时自动过校对机（PR 触发 CI），编辑看到校对结果再决定是否发表（CI 状态影响 PR 合并决策）。

## 2. 为什么会出现

### 2.1 要解决的根本问题

软件开发中存在一个基本矛盾：**并行开发的效率需求** 与 **代码集成的质量需求** 之间的冲突。多个开发者同时工作时，各自的改动最终要汇聚到同一个代码库，这个汇聚过程如果缺乏控制，就会引入缺陷、破坏已有功能、或造成代码质量下降。

具体来说：

- **集成地狱（Integration Hell）**：在传统开发中，开发者可能独立工作数周甚至数月，最后一次性合并。此时冲突量巨大、问题难以定位，团队陷入长时间的"集成修复"工作。
- **代码审查缺失或低效**：没有结构化的审查流程时，要么完全不审查（质量失控），要么依赖正式的 Fagan Inspection（高成本、低频率、阻塞开发）。
- **质量反馈延迟**：bug 在引入数天甚至数周后才被发现，此时开发者已经忘记当时的上下文，修复成本指数级增加。

### 2.2 之前人们怎么处理

**集成方面**：

- 传统做法是"Big Bang Integration"——所有人各自开发完毕后一次性集成。问题集中爆发、难以定位。
- 后来出现"Nightly Build"——每晚自动构建一次，次日早上检查结果。但反馈周期仍然以天为单位。

**审查方面**：

- 1976 年 Michael Fagan 提出"Fagan Inspection"——一种正式的、有角色分工的代码检查流程。需要专门安排会议、指定主持人/记录员/审查员，仪式感重，成本高，难以跟上敏捷开发的节奏。
- 或者完全不做审查，依赖开发者自觉和事后测试。

旧方法的根本缺陷：**反馈周期过长**。无论是集成失败还是代码质量问题，发现得越晚修复成本越高。Fagan Inspection 虽然有效但不可扩展，无法适应现代软件每天数十次甚至数百次提交的节奏。

### 2.3 谁、在什么情境下提出了它

**CI 的起源**：

1. **1996 年，Kent Beck** 在开发 Chrysler C3 项目时，将 Continuous Integration 作为极限编程（Extreme Programming, XP）的十二个核心实践之一正式提出。其洞察是：既然集成越晚问题越大，那就让集成**尽可能频繁**——每天多次而非每月一次。
2. **2000 年，Martin Fowler** 发表文章 "Continuous Integration"，系统性地阐述了 CI 的实践方法，使其从 XP 社区传播到更广泛的软件工程领域。
3. **2001 年，CruiseControl** 作为第一个专门的 CI 服务器工具发布，将 CI 从实践理念变成了可落地的工具化方案。

**PR 的起源**：

1. PR 机制的思想根植于 Linux 内核的开发流程。Linus Torvalds 在 2005 年创建 Git 时，就设计了分布式的"pull"模型——维护者从贡献者的仓库中拉取代码。
2. **2008 年，GitHub** 推出了 Pull Request 功能，将这一分布式协作模式产品化、可视化——任何人都可以 fork 一个仓库、在自己的分支上改动、然后通过 Web 界面发起一个 Pull Request 请求合并。这大幅降低了代码审查的参与门槛。
3. GitHub 的 PR 模型将**代码审查**、**讨论**、**自动化检查**整合到一个流程中，创造了"轻量级、工具化、异步"的现代代码审查范式。

### 2.4 关键决策逻辑

**CI 的关键抉择**：

- **为什么选择"每次提交都集成"而非"定期集成"？** 约束条件是：bug 发现越晚修复成本越高（已有研究表明这个成本呈指数增长）。如果每次提交就跑测试，问题在几分钟内暴露，开发者脑中还有完整上下文。
- **为什么选择自动化而非人工构建？** 约束条件是：人工构建不可扩展（一个项目一天可能有几十次提交），且人工操作易出错。

**PR 的关键抉择**：

- **为什么选择"pull"模型而非"push"模型？** 在 push 模型中，任何有权限的人都可以直接向主分支推送代码，缺乏审查关卡。Pull 模型天然创造了一个"请求->审查->批准->合并"的控制点。
- **为什么选择异步审查而非同步审查（会议）？** 约束条件是：分布式团队（不同时区）和高频率变更。异步方式允许审查者在方便的时候审查，不阻塞开发者。

## 3. 核心机制

### 3.1 运作原理

**PR 的输入-过程-输出**：

```
输入: 开发者在 feature 分支上的代码改动 (commits)
  -> 过程:
     1. 开发者创建 PR (描述改动目的、影响范围)
     2. 自动化检查启动 (CI、Linting、安全扫描)
     3. 审查者阅读 diff、提出评论、请求修改
     4. 开发者响应评论、推送修正
     5. 审查者批准 (Approve)
     6. 合并 (Merge/Squash/Rebase)
  -> 输出: 改动被合并进主分支，PR 关闭
```

**CI 的输入-过程-输出**：

```
输入: 代码仓库中的一次变更 (push 或 PR 事件)
  -> 过程:
     1. CI 服务器检测到事件，拉取最新代码
     2. 按 pipeline 定义依次执行: 安装依赖 -> 编译构建 -> 运行测试 -> 生成报告
     3. 记录每个步骤的成功/失败状态
  -> 输出: 构建状态 (pass/fail) + 构建产物 + 测试覆盖率报告
```

**PR + CI 的联动**：

```
push to branch -> 触发 CI -> CI 结果回写到 PR (status check)
  -> 审查者看到绿色勾/红色叉
  -> 仅当 CI 通过 + 审查通过时允许合并
```

### 3.2 关键子概念

1. **Branch Protection Rules（分支保护规则）**：对主分支设置的限制条件——必须通过 CI、必须有 N 人审批、禁止强制推送。这是将 PR+CI 从"建议"变成"强制"的执行机制。

2. **Status Checks（状态检查）**：CI 执行完毕后向代码托管平台报告的结果标记（成功/失败/进行中），直接显示在 PR 页面上，是 CI 与 PR 之间的通信协议。

3. **Merge Strategy（合并策略）**：决定如何将 PR 分支的改动整合进主分支——Merge Commit（保留完整历史）、Squash（压缩为单次提交）、Rebase（线性历史）。不同策略影响 git 历史的可读性和可追溯性。

4. **Pipeline（流水线）**：CI 中定义的一系列按顺序或并行执行的任务（jobs/steps），描述了"代码变更后要做哪些自动化验证"。

5. **Merge Queue（合并队列）**：当多个 PR 同时就绪时，按顺序测试和合并，避免"两个 PR 各自通过 CI 但合并后互相冲突"的问题（语义冲突）。

### 3.3 第一性原理追问

- **如果去掉 CI 中的自动化测试**：CI 退化为"自动化编译检查"，只能发现编译错误而无法发现逻辑缺陷。大量 bug 会逃逸到生产环境。这说明 CI 的核心价值不在于"自动化运行"本身，而在于**测试覆盖率赋予的信心**——如果测试不充分，CI "通过"给出的是虚假安全感。

- **如果去掉 PR 中的人工审查**：PR 退化为"自动化 gate"，只剩 CI 的机器检查。虽然能拦住编译错误和测试失败，但无法发现设计问题、命名不当、架构违背、知识传递缺失等人类判断力相关的问题。Bacchelli & Bird (2013) 的研究表明，代码审查的首要价值实际上不是找 bug，而是**知识传递和团队认知对齐**。

- **如果去掉分支保护规则**：PR 和 CI 都变成"可选建议"，任何人可以绕过它们直接推送到主分支。在团队规模增长后，必然会有人（有意或无意地）跳过流程，导致主分支质量不可预测。这说明**工具层面的强制执行**是流程可靠性的基础，仅靠文化约定不够。

## 4. 生态位：它和谁像？和谁争？

### 4.1 易混辨析

| 维度 | PR (Pull Request) | MR (Merge Request) | Code Review (泛义) |
|------|-------------------|---------------------|---------------------|
| 来源 | GitHub 术语 | GitLab 术语 | 通用概念 |
| 本质 | 一种代码审查的工作流载体 | 与 PR 功能完全等价 | 可以有多种实现形式 |
| 范围 | 特指"分支合并请求"这一具体机制 | 同左 | 更广，包括 pair programming、Fagan inspection、over-the-shoulder review 等 |
| 区别点 | PR 和 MR 是同一事物在不同平台的不同名称。真正需要区分的是：PR/MR 是一种特定的异步、工具化的 Code Review 实现方式，而 Code Review 还包括更多形式。 |

| 维度 | CI (持续集成) | CD (持续交付/持续部署) |
|------|---------------|------------------------|
| 关注点 | 代码合并后的自动验证 | 验证通过后的自动发布 |
| 输出 | 构建状态 + 测试报告 | 部署到 staging/production 的产物 |
| 失败后果 | 阻止合并，开发者修复 | 阻止发布或触发回滚 |
| 边界 | CI 在"代码正确性"层面工作 | CD 在"发布就绪性"层面工作 |
| 关系 | CI 是 CD 的前提。没有 CI 的 CD 相当于盲目部署。 |

### 4.2 上下游关系

```
需求分析 -> 编码 (feature branch) -> PR 创建 -> CI 执行 -> Code Review -> 合并 -> CD -> 部署 -> 监控
                                        ^                              |
                                        |______ 如果 CI 失败 __________|
                                        |______ 如果审查不通过 ________|
```

PR & CI 在实际工作流中搭配使用的工具/概念：

- **上游**：Git 分支策略（GitFlow / Trunk-Based / GitHub Flow）、Issue Tracker、项目管理工具
- **同层**：静态分析（Linting）、安全扫描（SAST/DAST）、代码覆盖率工具
- **下游**：CD 管道、Feature Flags、Canary Release、Monitoring/Alerting

### 4.3 竞争与互补

**分支策略的竞争**：

| 策略 | 适合场景 | PR/CI 角色 |
|------|----------|------------|
| GitHub Flow | 小团队、快速迭代 | 每个 feature branch 一个 PR，CI 必须通过才能合并到 main |
| GitFlow | 有正式发布周期的项目 | PR 用于 feature->develop 和 release->main 两个环节 |
| Trunk-Based Development | 高频发布、大团队 | 短生命周期分支（<1天）、小 PR、CI 极快 |

**审查方式的互补**：

- **Pair Programming**：实时同步审查，适合高复杂度或新人上手阶段，与 PR 互补而非替代
- **Stacked PRs（堆叠式 PR）**：将大功能拆分为多个小 PR 按依赖关系堆叠，解决"大 PR 难审查"的问题
- **AI 辅助审查**：AI 工具自动发现代码问题、建议改进，作为人工审查的补充

## 5. 发展脉络与前沿

### 5.1 关键演进节点

**节点一：1996-2001 —— 从 XP 实践到工具化**

Kent Beck 在极限编程中提出 CI 实践时，主要依靠团队纪律——开发者每天手动拉取最新代码、在本地跑测试、然后推送。2001 年 ThoughtWorks 团队发布 CruiseControl，第一次将 CI 变成了**自动化服务器**。这个转变的意义在于：将 CI 从"人的纪律"变成"系统的自动执行"，使其可以扩展到更大规模的团队。

**节点二：2008 —— GitHub 发明 Pull Request**

GitHub 在 2008 年将 Linux 社区的 pull 模型产品化为 Pull Request 功能。这不仅是一个技术特性，更是一个社会化创新——它让代码审查变得**可见、可讨论、可追溯**，并且极大降低了开源协作的门槛。任何人都可以 fork 一个项目、改动代码、发起 PR。这个模式后来被 GitLab（Merge Request）、Bitbucket 等平台全面采用，成为行业标准。

**节点三：2011-2013 —— CI-as-a-Service 兴起**

Travis CI（2011）率先提供"CI 即服务"——开发者只需在仓库中放一个 `.travis.yml` 文件，就能获得云端的自动构建和测试。这消除了自建 CI 服务器的运维成本。Jenkins（2011 年从 Hudson 重命名）则提供了自托管但高度可定制的方案。这一时期，CI 从"先进团队的实践"变成了"开源项目的标配"。

**节点四：2018-2019 —— GitHub Actions 将 CI 与代码托管原生集成**

GitHub Actions（2018 年发布，2019 年正式 GA）将 CI/CD 直接内嵌到代码托管平台中。开发者不再需要配置第三方 CI 服务的 Webhook，workflow 文件直接放在 `.github/workflows/` 目录中。这进一步降低了 CI 的采用摩擦力。配合 GitHub Marketplace 的可复用 Actions 生态，标准化了常见 CI 任务。

**节点五：2023 —— Merge Queue 与 AI Code Review**

GitHub 在 2023 年正式推出 Merge Queue 功能，解决了高并发 PR 场景下的"语义冲突"问题——两个 PR 各自通过 CI 但合并后互相破坏。同期，AI 代码审查工具（如基于 LLM 的自动审查）开始进入主流，补充人工审查在"机械性检查"方面的不足。

### 5.2 当前前沿方向

1. **AI 驱动的代码审查**：利用大语言模型自动识别代码问题、生成审查建议。目前已有 GitHub Copilot for Pull Requests、CodeRabbit 等工具，但在"判断设计合理性"方面仍不如人类审查者。

2. **Stacked PRs / Stacked Diffs**：受 Meta（Facebook）内部 Phabricator 工作流启发，Graphite 等工具在 GitHub 上实现了堆叠式 PR——将大功能拆分为多个有依赖关系的小 PR，每个 PR 足够小以便快速审查，同时保持整体功能的连贯性。

3. **CI 的智能化调度**：根据代码变更的影响范围选择性运行测试（test impact analysis），而非每次都跑全量测试套件。例如只修改了前端组件就不跑后端的集成测试，显著缩短反馈时间。

### 5.3 尚未解决的核心争议

- **PR 大小的最优解**：小 PR 审查快但上下文碎片化，大 PR 完整但审查质量下降。业界共识趋向"小"但没有明确的最优阈值。
- **CI 速度与覆盖率的权衡**：全量测试给出更高信心但耗时长（阻塞开发者），选择性测试快但可能遗漏问题。
- **审查的"形式化"问题**：当 PR 审查变成例行公事（"LGTM"打卡），其质量保障价值被掏空。如何维持审查的实质性是一个管理难题。

### 5.4 驱动力判断

推动 PR & CI 演进的底层力量是：

1. **软件规模的增长**：更多代码、更多开发者、更高的集成频率需求
2. **发布节奏的加速**：从年度发布到月度、周度、甚至持续发布
3. **云计算的普及**：提供了按需、弹性的计算资源来运行 CI，消除了自建基础设施的门槛
4. **开源协作的全球化**：跨时区、跨组织的协作需要异步、工具化的审查流程

## 6. 怎么用

### 6.1 场景一：个人开发者的 solo 项目

**场景**：你是一个独立开发者，开发一个 macOS 应用，只有你自己写代码。

**用法**：
- 仍然使用 PR（向自己发起）而非直接推送到 main。原因：PR 创建了一个"检查点"，CI 自动跑测试确保改动不破坏已有功能；PR 的 diff 视图帮助你在合并前做最后的自我审查；git 历史更清晰。
- CI 配置自动构建 + 单元测试 + 覆盖率报告。

**效果**：减少"改了 A 不小心破坏了 B"的回归 bug；commit 历史按功能组织而非按时间散乱；随时可以回溯"这个功能是什么时候、因为什么引入的"。

### 6.2 场景二：小团队的敏捷开发

**场景**：3-5 人团队，两周一个 Sprint，使用 GitHub Flow。

**用法**：
- 每个任务一个 feature 分支，完成后发 PR
- PR 要求至少 1 人审批 + CI 通过
- CI pipeline: lint -> build -> unit test -> integration test
- PR 描述模板要求填写：改动目的、影响范围、测试方案
- 使用 Squash Merge 保持主分支历史简洁

**效果**：代码质量通过审查持续提升；团队成员通过审查了解彼此的工作；CI 在几分钟内给出反馈，不阻塞开发流程。

### 6.3 场景三：大型组织的 Monorepo

**场景**：数百人的工程团队，单一代码库（Monorepo），每天数百个 PR。

**用法**：
- Trunk-Based Development + 短生命周期分支（<1 天）
- 启用 Merge Queue 避免语义冲突
- CI 使用 test impact analysis 选择性跑测试
- 代码所有权（CODEOWNERS）自动指派审查者
- Stacked PRs 拆分大功能
- 自动化 bot（Danger / Reviewdog）处理机械性检查（PR 描述是否完整、是否更新了文档、是否有破坏性变更等）

**效果**：在不牺牲质量的前提下保持高频发布节奏。

### 6.4 结合 AI 工具的实践切入

如果你想结合 AI 工具来优化 PR & CI 实践，最直接的切入方式是使用 Claude 或类似 LLM 来辅助 PR 审查。以下是一个可以立刻尝试的工作流：

**工作流示例 —— AI 辅助 PR 描述生成**：

```
1. 在 CI pipeline 中添加一个步骤：
   - 获取 PR 的 diff
   - 将 diff 发送给 AI，请求生成结构化的 PR 描述

2. Prompt 模板：
   "分析以下代码变更的 diff，生成一份 PR 描述，包含：
    - 改动目的（一句话）
    - 主要变更列表
    - 潜在影响范围
    - 建议审查者关注的重点区域"

3. AI 输出作为 PR 描述的 draft，人工确认后发布
```

这个切入点的优势是：低风险（AI 只辅助描述，不做决策）、高频使用（每个 PR 都能用）、立竿见影（节省写描述的时间、提高描述质量）。

## 7. 深度调研：学术、实践与开源

### 7a. 关键论文

#### 论文一：Expectations, Outcomes, and Challenges of Modern Code Review

- **作者**：Alberto Bacchelli, Christian Bird
- **发表**：2013, ICSE (35th International Conference on Software Engineering)
- **出处**：ACM/IEEE ICSE 2013

**核心贡献**：这是第一篇系统性研究现代（工具化、轻量级）代码审查的大规模实证论文。它定义了"Modern Code Review"的三个特征：(1) 非正式的（对比 Fagan Inspection）；(2) 工具辅助的；(3) 经常性发生的。

**方法论摘要**：研究团队在 Microsoft 进行了混合方法研究——包括对 17 名开发者的观察和访谈，对数百条审查评论的人工分类，以及对更大范围开发者的问卷调查。研究横跨多个团队，覆盖不同产品线和开发文化。

**关键结论**：
1. 虽然"发现缺陷"是开发者参与代码审查的**主要动机**，但实际上审查中发现的缺陷比预期少得多。
2. 代码审查的实际主要价值是**知识传递**、**提升团队意识**、**寻找替代方案**——这些"非缺陷发现"的收益才是审查持续存在的核心原因。
3. 代码审查的挑战包括：理解变更的上下文、审查者的时间分配、以及审查反馈的及时性。

**局限性**：
- 研究仅在 Microsoft 内部进行，其审查工具（CodeFlow）和文化可能不代表所有组织。
- 对审查评论的分类依赖人工判断，存在主观性。
- 未能量化审查的长期价值（如知识传递的复利效应）。

**影响力判断**：这篇论文奠定了整个"现代代码审查"研究领域的基础。它被后续几乎所有 Code Review 研究引用，其"审查主要价值不是找 bug"的结论颠覆了工业界的普遍认知，促使团队重新定义审查的目标和评估标准。论文中提出的研究框架也被 Google、Facebook 等公司的后续研究采用。

#### 论文二：An Exploratory Study of the Pull-based Software Development Model

- **作者**：Georgios Gousios, Martin Pinzger, Arie van Deursen
- **发表**：2014, ICSE (36th International Conference on Software Engineering)
- **出处**：ACM/IEEE ICSE 2014（获 ACM SIGSOFT Distinguished Paper 提名）

**核心贡献**：首次对 GitHub 的 Pull Request 模型进行大规模实证研究，系统描述了 pull-based 开发模型的运作方式、效率和影响因素。

**方法论摘要**：研究基于 GHTorrent 数据集（GitHub 事件归档），分析了 GitHub 上的项目数据，并从中精选 291 个活跃项目进行深入分析。研究量化了 PR 的周转时间、合并率、贡献者参与度等关键指标。

**关键结论**：
1. Pull-based 模型提供了**快速的周转时间**——大部分 PR 在数小时到数天内被处理。
2. 该模型**增加了社区参与机会**——降低了外部贡献者参与项目的门槛。
3. **减少了合并贡献的时间**——相比传统的 patch-via-email 方式显著更快。
4. PR 是否被合并的关键因素包括：提交者的历史贡献记录、PR 涉及的代码量、以及 PR 与项目当前优先级的对齐程度。

**局限性**：
- 研究聚焦于开源项目，企业内部的 PR 模式可能有不同的动态。
- GHTorrent 数据集无法捕捉 PR 之外的沟通（如 IRC、邮件列表讨论）。
- 未深入分析 PR 审查质量，主要关注流程指标。

**影响力判断**：这篇论文是 pull-based 开发模型研究的奠基之作。它为后续大量关于 PR 效率、PR 审查质量、PR 大小优化的研究提供了方法论模板和基线数据。论文配套发布的 GHTorrent 数据集也成为软件工程领域最广泛使用的 GitHub 挖掘数据源之一。

---

#### 论文三：Modern Code Review: A Case Study at Google

- **作者**：Caitlin Sadowski, Emma Soderberg, Luke Church, Michal Sipko, Alberto Bacchelli
- **发表**：2018, ICSE-SEIP (Software Engineering in Practice)
- **出处**：ACM/IEEE ICSE 2018

**核心贡献**：在 Google 规模下（日均约 25,000 次代码变更）研究了现代代码审查的实践细节，揭示了超大规模组织如何让代码审查保持轻量且高效。

**方法论摘要**：结合三种方法——12 次深度访谈、44 人问卷调查、以及对约 900 万条审查记录的日志分析。研究基于 Google 内部的代码审查工具 Critique。

**关键结论**：
1. Google 的代码审查非常**轻量级**：大多数变更只需要一个审查者，且没有额外评论，只有授权合并的批准。
2. **70% 的变更在发出审查请求后 24 小时内完成合并**，工作日内中位数周转时间约 4 小时。
3. 审查者通常只需要满足两个条件：**代码所有权（ownership）** 和 **可读性认证（readability）**。
4. 尽管经过多年优化，代码审查仍然面临**交互复杂性**带来的崩溃——当审查涉及多方利益相关者时效率显著下降。
5. 开发者对代码审查要求表示**满意**——他们认为审查的收益大于成本。

**局限性**：
- Google 的 Monorepo、自建工具链、强大的代码所有权机制使其经验不一定可直接迁移到其他组织。
- 研究主要关注流程效率指标，对审查的实际质量（如发现的问题是否真正重要）分析不足。
- 样本偏向 Google 文化——一个高度工程化、对代码质量有共识的组织。

**影响力判断**：这篇论文提供了工业界最大规模的代码审查实证数据，证明了"轻量级审查可以在超大规模下工作"。其"通常只需一个审查者"的发现影响了许多团队简化其审查流程。论文也揭示了代码所有权（CODEOWNERS）机制在规模化审查中的关键作用。

#### 论文四：Usage, Costs, and Benefits of Continuous Integration in Open-Source Projects

- **作者**：Michael Hilton, Timothy Tunnell, Kai Huang, Darko Marinov, Danny Dig
- **发表**：2016, ASE (31st IEEE/ACM International Conference on Automated Software Engineering)
- **出处**：ACM/IEEE ASE 2016

**核心贡献**：第一篇大规模量化研究 CI 在开源项目中的采用率、使用成本和实际收益的论文。

**方法论摘要**：采用三种互补方法——(1) 对 GitHub 上 34,544 个开源项目的定量分析，统计 CI 的使用情况；(2) 对使用 CI 的项目维护者的问卷调查，了解动机和挑战；(3) 对项目历史数据的纵向分析，比较采用 CI 前后的变化。

**关键结论**：
1. **使用 CI 的项目发布频率是不使用 CI 项目的两倍**——CI 使团队有信心更频繁地发布。
2. CI 的主要成本包括：初始配置的时间投入、CI 基础设施的维护、以及处理"flaky tests"（不稳定测试）的持续精力消耗。
3. CI 的核心收益：更快发现 bug、更高的代码质量信心、更快的 PR 处理速度。
4. 采用 CI 的最大障碍是：**现有项目缺乏足够的自动化测试**——没有测试的项目采用 CI 收益很小。

**局限性**：
- 研究主要基于 Travis CI，不同 CI 工具可能有不同的使用模式。
- "发布频率翻倍"是相关性而非因果性——可能是更好的团队本身更倾向于使用 CI 且更频繁发布。
- 开源项目的 CI 使用模式可能不代表企业私有项目。

**影响力判断**：这篇论文为"CI 是否真的有用"提供了第一份大规模实证数据。其"发布频率翻倍"的结论被工业界广泛引用来论证 CI 投资的 ROI。论文也明确指出了 CI 的前提条件（需要有测试）和主要成本（flaky tests），对后续 CI 相关工具和研究的方向产生了直接影响。

---

#### 论文五：Quality and Productivity Outcomes Relating to Continuous Integration in GitHub

- **作者**：Bogdan Vasilescu, Yue Yu, Huaimin Wang, Premkumar Devanbu, Vladimir Filkov
- **发表**：2015, ESEC/FSE (10th Joint Meeting on Foundations of Software Engineering)
- **出处**：ACM ESEC/FSE 2015

**核心贡献**：研究了 CI 对软件项目**质量**（bug 发现率）和**生产力**（PR 合并速度）的具体影响。

**方法论摘要**：分析了 GitHub 上使用 Travis CI 的项目，通过比较核心开发者和外部贡献者在 CI 环境下的行为差异来评估 CI 的效果。采用了回归分析等统计方法控制混淆变量。

**关键结论**：
1. 使用 CI 的项目中，**核心开发者能识别出显著更多的 bug**——CI 提供的自动反馈帮助开发者更早发现问题。
2. **核心开发者提交的 PR 在 CI 环境下被更快合并**——CI 的自动验证减少了人工审查的负担。
3. CI 对外部贡献者的 PR 合并速度影响不如对核心开发者明显——因为外部贡献者的 PR 还需要更多的人工信任评估。

**局限性**：
- 同样是相关性研究，无法完全排除选择偏差。
- 只分析了 Travis CI 平台的项目。
- Bug 的识别依赖 Issue 标签分类，可能有误分类。

**影响力判断**：这篇论文为 CI 的质量收益提供了具体的量化证据，补充了 Hilton 等人在产出效率方面的发现。它也揭示了 CI 对不同角色（核心开发者 vs 外部贡献者）的差异化影响，为 CI 在开源协作中的设计提供了指导。

### 7b. 最佳实践

#### 实践一：Google 的代码审查文化

- **来源**：Google Engineering Practices documentation (公开); Sadowski et al. 2018 ICSE 论文
- **实践内容**：
  - 所有代码变更必须至少经过一个人审查才能提交（无例外）。
  - 变更应该**小而频繁**——Google 的中位变更大小约为 24 行。
  - 审查者通常在 24 小时内完成审查，目标是当天响应。
  - 代码所有权（CODEOWNERS）机制自动分配审查者，确保熟悉该模块的人来审查。
  - "可读性认证（Readability）"制度：对每种编程语言，开发者需要通过认证才能批准该语言的代码。

- **为什么是最佳实践**：
  - 数据支撑：70% 的变更在 24 小时内完成合并，证明轻量级审查不会阻塞开发。
  - Google 管理着全球最大的单一代码库（数十亿行代码），该实践在此规模下仍然有效。
  - 开发者满意度调查显示大多数人认为审查的收益大于成本。

- **适用边界**：
  - 有效条件：团队有足够的工程师可以快速响应审查请求；代码库有清晰的所有权定义；有自动化工具支持审查者分配。
  - 不适用时：极小团队（2-3 人）中强制审查可能造成瓶颈；紧急 hotfix 场景可能需要事后审查（post-commit review）机制。

---

#### 实践二：Spotify 的 CI/CD 与开发者平台

- **来源**：Spotify Engineering Blog; Backstage 开源项目文档
- **实践内容**：
  - 超过 2,700 名工程师，每天执行 4,100+ 次生产部署。
  - 使用 Backstage（自建并开源的开发者门户）统一管理所有服务的 CI/CD 配置。
  - 新服务通过标准模板创建——模板内置了 CI pipeline、部署配置、监控集成等最佳实践，开发者不需要从零配置。
  - 声明式基础设施——CI/CD 配置用 YAML/JSON 描述，而非命令式脚本。

- **为什么是最佳实践**：
  - 通过模板化将 CI/CD 最佳实践"烤入"项目创建流程，确保一致性。
  - Backstage 作为单一入口，消除了"去哪里看构建状态""去哪里配置 pipeline"的认知负担。
  - 将 CI/CD 视为平台产品而非每个团队自行维护的基础设施，显著降低了运维成本。

- **适用边界**：
  - 有效条件：微服务架构、大量独立服务需要统一管理；有专门的平台团队负责维护。
  - 不适用时：单体应用或极少服务的小团队；自建 Backstage 的投入在小规模下不划算。

---

#### 实践三：小 PR 策略（来自 Graphite/堆叠式 PR 实践）

- **来源**：Graphite 团队博客; The Pragmatic Engineer newsletter (Gergely Orosz)
- **实践内容**：
  - 将所有功能开发拆分为多个小 PR（每个 PR < 200 行变更）。
  - 使用 Stacked PRs 工具（如 Graphite）管理 PR 之间的依赖关系。
  - 每个 PR 有独立的 CI 验证，可以独立审查和合并。
  - 上游 PR 合并后，工具自动 rebase 下游 PR。

- **为什么是最佳实践**：
  - 小 PR 审查速度快（审查者更容易理解、更少遗漏问题）。
  - 减少了"大 PR 搁置数天无人审查"的问题。
  - 出问题时更容易 git revert 回退单个小变更。
  - Meta（Facebook）内部大规模验证了这一模式（使用 Phabricator + Stacked Diffs），是其高频发布的支撑之一。

- **适用边界**：
  - 有效条件：团队有足够快的 CI（每个 PR 需要独立过 CI）；开发者愿意投入精力做合理拆分。
  - 不适用时：某些变更本质上不可拆分（如数据库 schema 迁移 + 应用层适配需要原子性）；CI 太慢时小 PR 反而增加等待总时间。

---

#### 实践四：Trunk-Based Development + 短生命周期分支

- **来源**：DORA (DevOps Research and Assessment) "Accelerate" 研究; trunkbaseddevelopment.com
- **实践内容**：
  - 所有开发者在主干（trunk/main）上工作，或使用极短生命周期的分支（< 1 天）。
  - 分支创建后尽快合并——不允许长期存在的 feature 分支。
  - 通过 Feature Flags 解耦"代码合并"与"功能发布"——未完成的功能可以合并到主干但不对用户可见。
  - CI 必须极快（目标 < 10 分钟），以支持高频合并。

- **为什么是最佳实践**：
  - DORA 研究（基于 23,000+ 受访者）发现：高绩效团队使用 trunk-based development，且活跃分支数 < 3、分支生命周期 < 1 天。
  - 短分支从根本上消除了"合并地狱"——冲突在萌芽阶段就被解决。
  - 主干始终保持可部署状态，任何时候都可以从主干发布。

- **适用边界**：
  - 有效条件：团队有充分的自动化测试和快速 CI；有 Feature Flags 基础设施；团队纪律性高。
  - 不适用时：需要维护多个长期版本的项目（如 Linux 内核）；测试覆盖不足导致主干频繁破坏。

---

#### 实践五：Branch Protection + Required Checks 的强制执行

- **来源**：GitHub 官方文档; 广泛的行业实践
- **实践内容**：
  - 在 main/production 分支上启用保护规则：
    - 禁止直接推送
    - 要求 PR 必须通过所有 required status checks（CI）
    - 要求至少 N 名审查者批准
    - 要求分支在合并前必须与 base 分支保持最新（避免 stale merge）
    - 禁止 force push 和删除分支
  - 配合 CODEOWNERS 文件自动分配审查者。

- **为什么是最佳实践**：
  - 将质量门禁从"靠人记得"变成"系统强制"——任何人（包括管理员）都无法绕过流程。
  - 消除了"紧急情况下直接推送、事后忘记补审查"的系统性风险。
  - 对新人友好——流程由工具引导，不需要记忆复杂的团队规范。

- **适用边界**：
  - 有效条件：几乎所有使用 GitHub/GitLab 的团队都应该启用。
  - 需要注意的边界：必须配合合理的紧急通道（如 hotfix 流程）——完全无例外的保护在紧急事故响应时可能造成延误。通常做法是为 hotfix 设置一个精简的 fast-track 流程（如只需 1 人审批 + CI 通过即可合并）。

### 7c. 开源项目

#### 项目一：nektos/act

- **项目名称**：act
- **GitHub 地址**：https://github.com/nektos/act
- **Star 数量级**：~56k stars（基于 2025 年数据，推测）
- **主要维护者**：nektos 社区

**它做了什么**：在本地运行 GitHub Actions workflow——无需推送到远端就能测试 CI 配置是否正确。

**技术选型**：使用 Go 语言编写，依赖 Docker API 来模拟 GitHub Actions 的运行环境。选择 Go 的原因是：跨平台编译方便（单二进制分发）、并发处理性能好（多 job 并行）。使用 Docker 是因为 GitHub Actions 本身就运行在容器环境中。

**社区活跃度判断**：项目持续活跃，提交频率高，Issue 响应及时。作为 GitHub Actions 本地开发的事实标准工具，有大量社区贡献者。

**上手建议**：
1. 安装：`brew install act`（macOS）
2. 进入项目目录，运行 `act`——它会读取 `.github/workflows/` 并在本地 Docker 中执行
3. 首次使用需选择基础镜像大小（micro/medium/large）
4. 用 `act pull_request` 模拟 PR 事件触发

#### 项目二：reviewdog/reviewdog

- **项目名称**：reviewdog
- **GitHub 地址**：https://github.com/reviewdog/reviewdog
- **Star 数量级**：~9.2k stars
- **主要维护者**：haya14busa 及社区

**它做了什么**：将任意 linter/静态分析工具的输出转化为 PR 上的 review comment——让 CI 中的代码检查结果直接显示在 PR 的对应代码行上。

**技术选型**：使用 Go 语言编写。设计为**与 linter 无关**的中间层——它不做分析本身，而是将任何工具的输出（只要符合特定格式）转化为代码平台的 review API 调用。支持 GitHub、GitLab、Bitbucket 等多平台。

**社区活跃度判断**：项目活跃，GitHub Marketplace 上有大量基于 reviewdog 的预制 Actions（如 reviewdog/action-golangci-lint、reviewdog/action-eslint 等）。社区维护了数十种语言的 linter 集成。

## 9. 阅读问答与实践补充

### 9.1 PR & CI 是确保代码质量的唯一手段吗？

先回答：**不是唯一手段，但在你的背景下，是性价比最高且几乎不可替代的手段。**

确保代码质量的手段可以分成几层：

```
手动验证层
  肉眼测试、手动操作 app、截图对比
  你目前主要在用这一层

自动化验证层
  CI（自动构建、自动测试、自动 lint）
  这是你想要建立的层

流程控制层
  PR（强制代码变更走审查流程、触发 CI）
  这一层把自动化验证变成"不可跳过的门禁"

静态分析层
  SwiftLint、类型检查、安全扫描
  不运行代码就能发现问题

运行时监控层
  Crash 报告、用户行为分析、性能监控
  代码已上线后的最后一道网
```

这些手段之间不是替代关系，而是互补关系。但对你来说，有几个关键判断：

#### 判断 1：你不懂代码，所以"人工 code review"对你价值不大

传统 PR 的一个核心价值是让人审查代码。但你自己说了——技术方面的判断你做不了。所以 PR 对你的价值不在于"你审查 AI 的代码"，而在于：

```
PR 的价值（对你）
  1. 触发 CI -> 让机器替你做技术判断
  2. 记录变更历史 -> 每次改动有清楚的描述和边界
  3. 强制 AI 小步提交 -> 避免一次性改太多导致不可控
  4. 出问题时可以 revert -> 回退到上一个稳定状态
```

#### 判断 2：CI 对你来说几乎是唯一的技术质量把关者

因为你不写代码，也不看代码，所以：

- 你不能靠"自己读代码"来发现问题
- 你不能靠"pair programming"来实时审查
- 你不能靠"经验直觉"来判断代码是否有隐患

CI 做的事情是：**让机器自动检查 AI 写的代码有没有基本问题。** 它不完美，但在你的背景下，它是唯一一个不需要你懂代码就能运作的技术质量屏障。

#### 判断 3：你能做的判断——用户视角——也需要被系统化

你说"从用户角度出发，某个功能用户使用时会遇到什么问题，这个我可以判断"。这非常有价值，但如果只停留在"我打开 app 试试"，那是不可复现的、不可积累的。

更好的做法是：

```
你的用户视角判断 -> 转化为 UI 测试 / 集成测试的 spec
AI 根据你的 spec -> 写出自动化测试
CI 每次变更 -> 自动跑这些测试
```

这样你的判断力就不是每次手动发挥，而是被固化成可重复执行的自动检查。

#### 结论

```
你的情况：
  不懂代码 + AI 写代码 + solo 开发

最佳质量保障组合：
  PR（流程强制）
    + CI（自动化测试 + 构建验证）
    + 静态分析（SwiftLint 等）
    + 运行时监控（Crash 报告 + 分析）
    + 你的用户视角（转化为测试 spec）

其中 PR + CI 是骨架，其他是补充。
不是唯一手段，但是你这个背景下最核心的手段。
```

### 9.2 PR 和 CI 是什么关系

你的理解基本正确，但需要更精确一点。

**CI 不是 PR 的"子环节"，它们是两个独立概念，在实践中形成了协作关系。**

```
独立看：
  PR = 代码合并的审查流程
  CI = 代码变更的自动化验证

协作看：
  PR 触发 CI -> CI 结果回写 PR -> PR 决定是否允许合并
```

更准确的理解是：

```
PR 是流程层
  回答：这些改动可以合并吗？

CI 是验证层
  回答：这些改动通过了自动化检查吗？

两者协作：
  PR 向 CI 提问 -> CI 回答 -> PR 根据回答做决定
```

CI 可以在没有 PR 的情况下运行。比如直接 push 到 main 时也可以触发 CI。但这样做的问题是：CI 告诉你"代码有问题"的时候，代码已经进了 main，你只能事后修复而不是事前拦截。

```
没有 PR 的 CI：
  push to main -> CI 检查 -> 发现问题 -> 但代码已经在 main 了 -> 事后修复

有 PR 的 CI：
  push to branch -> 创建 PR -> CI 检查 -> 发现问题 -> 代码还没进 main -> 修完再合并
```

所以 PR + CI 的组合比单独的 CI 更强，因为 PR 给了 CI 一个"在代码进入主线之前"拦截的机会。

再看你的 Vibe-Capture 项目，`.github/workflows/ci.yml` 里有：

```
on:
  pull_request:
    branches: [main]    # PR 触发 CI
  push:
    branches: [main]    # 直接 push 也触发 CI
```

两个事件都触发 CI，但只有第一个（PR 触发）能起到"事前拦截"的作用。第二个（push 触发）只能起到"事后发现"的作用。

**结论：CI 是 PR 的信息提供者，PR 是 CI 的执行触发者和结果消费者。它们是合作关系，不是包含关系。**

### 9.3 CI 的测试标准：如何建立、如何确保正确和充分

这是最值得深入讲的一个问题。

#### 一、CI 基于什么来测试

CI 本身不"知道"怎么测试。它只是一个执行器。真正决定"测什么、怎么测"的是**测试代码本身**。

```
CI 的执行链：
  代码变更 -> 触发 CI -> CI 读取 workflow 配置 -> 按步骤执行：
    1. 拉取代码
    2. 安装依赖
    3. 编译构建（能不能编译通过）
    4. 运行测试（测试代码是否通过）
    5. 运行 lint（代码风格是否合规）
    6. 生成报告
```

其中"运行测试"这一步，跑的就是你仓库里已有的测试文件。以 Vibe-Capture 为例：

```
CI 跑的是 VibeCapTests/ 目录下的测试文件
这些测试是 AI 或开发者事先写好的
CI 只是"按指令跑"，它不自己发明测试
```

所以核心问题不是"CI 怎么测试"，而是"**测试本身写得对不对、全不全**"。

#### 二、测试标准如何建立

测试标准应该从三个来源推导：

```
来源 1：业务需求
  用户需要什么功能 -> 这些功能必须正常工作 -> 每个功能写至少一个测试

来源 2：历史事故
  以前出过什么 bug -> 这些 bug 不能再出现 -> 每个修复过的 bug 写一个回归测试

来源 3：技术约束
  编译必须通过 -> 构建测试
  内存不能泄漏 -> 性能测试
  兼容多个系统版本 -> 矩阵测试
```

对你来说，最实用的建法是：

```
你的角色：提需求、报 bug、定义"什么算正常"
AI 的角色：根据你的定义写测试代码
CI 的角色：每次改动自动跑这些测试

具体流程：
  你说："onboarding 页面必须正常显示"
  -> AI 写一个测试：启动 app -> 进入 onboarding -> 检查关键 UI 元素存在
  -> CI 每次改动都跑这个测试
  -> 如果某次改动让 onboarding 坏了，CI 立刻报红
```

#### 三、如何确保测试标准是正确的

这是一个很好的担忧。测试本身确实可能写错。防范方法有几层：

```
第 1 层：测试必须先失败再通过（TDD 思维）
  写完测试 -> 先确认它能发现已知问题 -> 再确认修复后它通过
  如果一个测试从来没失败过，它可能什么都没真正检查

第 2 层：测试要检查具体行为，不要检查实现细节
  好的测试："截图后文件出现在指定目录"
  坏的测试："某个内部方法被调用了一次"
  前者验证用户关心的结果，后者只验证代码内部路径

第 3 层：突变测试（Mutation Testing）
  故意在代码里插入错误（比如把 > 改成 <）
  看测试是否能发现这些错误
  如果测试没发现，说明测试不够严格
  这个你可以让 AI 来做

第 4 层：代码覆盖率作为参考（不是标准）
  覆盖率高不代表测试好，但覆盖率低基本代表测试不够
  你的项目目前是 44%，意味着超过一半的代码没有被任何测试触及
```

#### 四、怎样确保测试是充分的

"充分"不是一个绝对概念，但有几个实用的判断标准：

```
标准 1：核心路径全覆盖
  用户最常用的功能路径（截图、保存、分享等）
  每条路径至少一个测试

标准 2：边界情况有覆盖
  空输入、超大输入、无网络、磁盘满
  每个已知的边界至少一个测试

标准 3：回归测试全覆盖
  每个修复过的 bug 有一个对应测试
  确保同一个 bug 不会再出现

标准 4：新功能必须带测试
  每个新功能的 PR 必须包含对应的测试
  CI 可以检查"是否有新增测试文件"
```

对你来说，最实用的做法不是追求 100% 覆盖率，而是：

```
优先级：
  1. 核心功能的 happy path 测试（最重要的用户路径能走通）
  2. 已知 bug 的回归测试（修过的 bug 不再复发）
  3. 边界情况测试（极端情况不崩溃）
  4. UI 快照测试（界面没有意外变化）
```

#### 五、测试范围如何恰当

测试太少 -> 该发现的问题没发现
测试太多 -> CI 变慢、维护成本高、flaky test 增多

恰当的范围通常遵循"测试金字塔"：

```
                    /\
                   /  \
                  / UI \         少量：端到端测试
                 /------\        验证完整用户流程
                /集成测试\       中量：模块间协作
               /----------\      验证模块组合正确
              /  单元测试   \    大量：单个函数/类
             /--------------\    验证逻辑正确
```

对 Vibe-Capture：

```
单元测试（大量）：
  核心业务逻辑、数据处理、格式转换
  -> 快、稳定、CI 必跑

集成测试（适量）：
  截图流程（授权 -> 截图 -> 保存 -> 索引）
  iCloud 同步逻辑
  -> 稍慢但重要、CI 应该跑

UI 测试（少量）：
  onboarding 流程、关键页面加载
  -> 最慢且容易 flaky、可选跑
```

### 9.4 Solo + AI 团队的最佳实践

这个问题非常切中你的实际情况。你和大部分开发者不同——你不写代码，AI 写代码，你做产品判断。这意味着最佳实践也要相应调整。

#### 核心原则

```
传统团队：人写代码 -> 人审查代码 -> 机器测试
你的模式：AI 写代码 -> 机器审查代码 -> 你审查产品

你不需要成为代码审查者
你需要成为"测试标准的定义者"和"产品质量的最终裁判"
```

#### 一、macOS App（以 Vibe-Capture 为例）

你已经有了一个很好的基础。针对你的背景优化后的最佳实践：

```
开发流程：
  1. 你提需求（自然语言描述功能或 bug）
  2. AI 在 feature 分支上写代码 + 写测试
  3. AI 创建 PR（包含改动描述和测试说明）
  4. CI 自动运行：
     - xcodebuild 编译（macOS 14/15/26 三版本）
     - 单元测试
     - 集成测试
     - SwiftLint 代码风格检查
  5. CI 全绿 -> 你在本机试用（产品层面验收）
  6. 你觉得可以 -> 合并 PR

你负责的环节：
  - 步骤 1：定义需求（你最擅长的 UX 视角）
  - 步骤 5：产品验收（打开 app 试用，看体验是否符合预期）
  - 步骤 6：最终决策

机器负责的环节：
  - 步骤 4：全部自动化技术验证

AI 负责的环节：
  - 步骤 2-3：写代码、写测试、提 PR
```

macOS 特有的 CI 注意事项：

```
- macOS runner 比 Linux runner 贵（GitHub Actions 分钟数消耗 10 倍）
- Xcode 构建慢（你当前 timeout 20 分钟是合理的）
- UI 测试在 CI 环境中容易 flaky（无实际显示器）
- 签名问题需要在 CI 中跳过（你已经做了 CODE_SIGNING_ALLOWED=NO）
```

#### 二、iOS App

```
与 macOS App 的区别：
  1. CI 需要 iOS 模拟器（不是 macOS destination）
  2. 测试矩阵变成 iPhone 机型 + iOS 版本
  3. UI 测试更重要（触摸交互 vs 鼠标交互）

推荐 CI 配置：
  矩阵：

    - iPhone 16 + iOS 18
    - （可选）iPad + iPadOS

  必跑：
    - 编译
    - 单元测试
    - 集成测试

  选跑（PR 标签触发）：
    - UI 测试（耗时长，只在关键改动时跑）
    - 截图测试（检查 UI 是否变化）
```

iOS 特有的建议：

```
1. 使用 Fastlane 管理签名和发布流程
   你的 Vibe-Capture 已经有 fastlane/ 目录，说明你已具备基础

   对你特别有用——你关心的是 UI 层面，而不是代码层面
```

#### 三、网页产品

网页产品的 CI 通常更简单、更快、更便宜：

```
开发流程：
  1. 你提需求
  2. AI 在 feature 分支写代码 + 写测试
  3. AI 创建 PR

     - npm install / pnpm install

     - ESLint / Prettier 代码检查

     - 端到端测试（Playwright）

  6. 合并 PR -> 自动部署到生产

相比 macOS/iOS 的优势：
  - CI 速度快（通常 2-5 分钟，不是 15-20 分钟）
  - 不需要昂贵的 macOS runner（Linux runner 足够）
  - Preview 部署让你不用本地构建就能验收
  - 端到端测试（Playwright）比 Xcode UI 测试稳定得多
```

网页产品特有的建议：

```
1. 必须用 Preview 部署
   Vercel / Netlify 在每个 PR 上自动部署一个临时 URL
   你直接在浏览器里试用，不需要任何开发环境
   这对你来说是最友好的验收方式

2. Lighthouse CI
   自动检查页面性能、可访问性、SEO
   你不需要懂技术也能看懂分数

3. Visual Regression Testing（视觉回归测试）
   自动截图对比，发现 UI 的意外变化
   工具：Chromatic（配合 Storybook）、Percy、Playwright screenshots
```

### 9.5 不同规模的代码改动如何对应不同的 CI 范围

你的理解是对的。**不同规模的改动确实应该对应不同级别的 CI 检查。**

#### 一、为什么需要分级

```
如果每次改动都跑全量测试：
  改一行注释 -> 等 20 分钟 CI -> 浪费时间和资源
  开发者会觉得烦 -> 开始绕过流程

如果每次改动都只跑最小测试：
  重构核心模块 -> 只跑了单元测试 -> 集成问题没被发现
  上线后出 bug -> CI 形同虚设
```

所以需要的是：**小改动快检查，大改动深检查。**

#### 二、怎么定义"规模"

代码改动的规模不只是看行数，更要看**影响范围**：

```
维度 1：变更行数
  < 50 行：小
  50-300 行：中
  > 300 行：大

维度 2：影响范围
  只改 UI 文案/颜色 -> 影响范围小
  改业务逻辑 -> 影响范围中
  改核心架构/数据模型 -> 影响范围大

维度 3：文件类型
  .md / 文档 -> 几乎无风险
  .swift 业务代码 -> 中风险
  .xcodeproj / .entitlements / Info.plist -> 高风险（配置变更影响全局）
```

#### 三、分级规则（以 Vibe-Capture 为例）

```
Level 1 - 文档/配置类改动
  触发条件：只改了 .md、.txt、注释
  CI 范围：
    - 编译检查（确认没误改代码）
  预计耗时：2-3 分钟

Level 2 - 小型代码改动
  触发条件：改动 < 50 行，不涉及核心模块
  CI 范围：
    - 编译检查
    - 单元测试
    - SwiftLint
  预计耗时：5-8 分钟

Level 3 - 中型功能改动
  触发条件：改动 50-300 行，涉及业务逻辑
  CI 范围：
    - 编译检查（全矩阵：macOS 14/15/26）
    - 单元测试
    - 集成测试
    - SwiftLint
    - 覆盖率报告
  预计耗时：10-15 分钟

Level 4 - 大型改动 / 核心模块变更
  触发条件：改动 > 300 行，或涉及 .xcodeproj / 数据模型 / 核心架构
  CI 范围：
    - 全矩阵编译
    - 全量测试（单元 + 集成 + UI）
    - SwiftLint
    - 覆盖率报告 + 覆盖率门禁
    - （可选）性能测试
  预计耗时：15-25 分钟
```

#### 四、如何在 GitHub Actions 中实现分级

实现方式通常有两种：

**方式 1：基于路径过滤（推荐，最简单）**

```yaml
# 文档改动只跑编译检查
on:
  pull_request:
    paths:
      - '**.md'
      - '**.txt'
jobs:
  quick-check:
    runs-on: macos-14
    steps:
      - uses: actions/checkout@v4
      - run: xcodebuild build ...

# 代码改动跑完整测试
on:
  pull_request:
    paths:
      - '**.swift'
      - '**.xcodeproj/**'
jobs:
  full-test:
    runs-on: macos-14
    strategy:
      matrix: ...
    steps:
      - ... build + test + lint + coverage
```

**方式 2：基于 PR 标签（更灵活）**

```yaml
# AI 或你在 PR 上打标签来控制 CI 级别
jobs:
  full-test:
    if: contains(github.event.pull_request.labels.*.name, 'ci:full')
    ...

  quick-test:
    if: "!contains(github.event.pull_request.labels.*.name, 'ci:full')"
    ...
```

**方式 3：自动判断（最智能但最复杂）**

```yaml
jobs:
  determine-scope:
    runs-on: ubuntu-latest
    outputs:
      level: ${{ steps.check.outputs.level }}
    steps:
      - id: check
        run: |
          # 分析改动文件，自动判断 CI 级别
          FILES=$(gh pr diff ${{ github.event.number }} --name-only)
          if echo "$FILES" | grep -q '.xcodeproj\|.entitlements'; then
            echo "level=4" >> $GITHUB_OUTPUT
          elif [ $(echo "$FILES" | wc -l) -gt 20 ]; then
            echo "level=3" >> $GITHUB_OUTPUT
          else
            echo "level=2" >> $GITHUB_OUTPUT
          fi

  test:
    needs: determine-scope
    ...
```

#### 五、对你的实际建议

不要一开始就搞复杂的分级系统。推荐渐进式方案：

```
现在（立刻可做）：
  所有代码改动 -> 跑编译 + 单元测试（你现在已有的）
  纯文档改动 -> 加路径过滤，跳过 CI

短期（1-2 周）：
  给 CI 加上集成测试
  加上 SwiftLint
  移除 || true（让 CI 真正能报失败）

中期（有余力时）：
  基于路径过滤区分"核心代码改动"和"非核心改动"
  核心改动跑全矩阵 + 全量测试
  非核心改动只跑单矩阵 + 单元测试

长期（需求明确时）：
  引入 UI 测试到 CI（解决 flaky 问题后）
  覆盖率门禁（从 40% 起步，逐步提高）
```

关键原则：**先让 CI 真正能拦住问题（移除 || true），再考虑优化 CI 的速度和范围。一个能报红的慢 CI，远好过一个永远绿但实际什么都没检查的快 CI。**
