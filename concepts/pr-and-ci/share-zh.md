# 一个不懂代码的设计师，为什么要折腾 PR 和 CI

前几天，我打开自己 macOS App 的 GitHub 仓库，发现 CI 已经连续三天全部失败。原因是 GitHub Actions 的账单出了问题。

说实话，当时我的第一反应不是「赶紧修」，而是「这几天没有 CI，也没出什么事啊」。

然后我意识到，这个想法本身就是问题。

## 我为什么要学 PR 和 CI

我是一个 UX 设计师，做了二十多年设计。去年开始用 AI 做独立开发，目前上线了一款 macOS App 叫 Vibe Capture。

代码基本上是 AI 写的，我不写代码，也看不懂代码。

这意味着一个很现实的问题：**除了我能用肉眼看到的 UI 层面，代码的其他一切——逻辑对不对、边界情况有没有处理、会不会崩溃——我完全没有能力把控。**

所以我需要一种方式，让「机器」替我做技术层面的判断。

这就是我学 PR 和 CI 的原因。

## 这两个概念从哪来的

CI 的概念最早可以追溯到 1996 年。Kent Beck 在极限编程（Extreme Programming）中提出了一个想法：开发者应该每天把代码合并到一起，而不是各写各的、最后再拼。当时完全靠人的纪律，没有任何自动化工具。

2001 年，ThoughtWorks 发布了 CruiseControl——第一个 CI 服务器。从那以后，CI 从「靠人自觉」变成了「靠系统自动跑」。后来 Jenkins（2011）、Travis CI（2011）相继出现，直到 2019 年 GitHub Actions 正式发布，把 CI 直接内嵌到了代码托管平台里。

PR 的故事更有意思。2008 年，GitHub 把 Linux 社区里的 pull 模型产品化成了 Pull Request 功能。在这之前，开源社区的代码审查流程是通过邮件列表完成的——你把补丁发到邮件列表，维护者下载、审查、手动合并。GitHub 把这个过程变成了可视化的、可评论的、可追踪的 Web 界面。后来 GitLab 叫它 Merge Request，本质上是同一个东西。

所以这两个概念的年龄其实比我想的要大很多。CI 快 30 年了，PR 也快 20 年了。它们能活这么久，说明确实解决了真问题。

## PR 和 CI 的核心流程

抛开我个人的理解，客观来说，PR 和 CI 的标准流程是这样的：

```
开发者在 feature 分支上写代码
  -> 创建 PR（描述改了什么、为什么改）
  -> CI 自动触发：拉取代码 -> 编译构建 -> 运行测试 -> 生成报告
  -> CI 结果回写到 PR 页面（绿色通过 / 红色失败）
  -> 审查者查看代码 + CI 结果
  -> 全部通过 -> 合并到 main
  -> 任一失败 -> 修复后重新提交
```

这里面有几个关键的子概念：

1. **Branch Protection（分支保护）**：对 main 分支设限——必须通过 CI、必须有人审批、禁止直接推送。这是把流程从「建议」变成「强制」的机制。
2. **Status Check（状态检查）**：CI 跑完后向 GitHub 报告的结果标记，直接显示在 PR 页面上。绿勾或红叉，一目了然。
3. **Pipeline（流水线）**：CI 中定义的一系列按顺序执行的任务——安装依赖、编译、跑测试、生成覆盖率报告。

## 我理解的 PR 和 CI

用最简单的话来说（这是我目前粗浅的理解，不一定准确）：

**PR（Pull Request）**就是你改完代码后，不直接丢进主线，而是先「提交一个申请」，让系统检查一遍再决定要不要合并。

**CI（Continuous Integration）**就是每次代码变更后，自动跑一遍构建和测试，看看有没有搞坏什么东西。

如果用生活来打比方的话，PR 像给编辑部投稿——你写完交给编辑看，编辑确认没问题才发表。CI 像印刷前的自动校对机——稿子一入稿池，机器立刻检查错别字、格式规范，几分钟内告诉你通过还是不通过。

两者的关系是：**PR 触发 CI，CI 的结果反馈给 PR，PR 根据结果决定要不要放行。**

它们不是包含关系，而是合作关系。一个管流程，一个管验证。

## 在 Vibe Capture 里，我的实际情况

我的项目其实已经有了 CI 配置。`.github/workflows/ci.yml` 里跑着三个 macOS 版本的矩阵构建（macOS 14、15、26），每次改动都会自动编译和测试。

PR 也在用。从 git 历史可以看到，大部分功能是通过 PR 合并的，分支命名也很规范——`feature/`、`fix/`、`docs/`、`chore/`。

听起来还不错？

但仔细审查后，我发现了几个让我有点汗颜的问题：

1. **CI 里有 `|| true`**。这意味着即使构建或测试失败了，CI 照样显示绿色通过。换句话说，我的 CI 是个摆设，永远绿，但什么都没真正检查。
2. **有不少代码直接 push 到了 main**，绕过了 PR 流程。没有 branch protection，任何人（包括 AI）都可以直接推代码到主线。
3. **所有 18 个 PR 都是自己 merge 自己的**，没有任何 code review。

回头看，这些问题的本质都是一样的：**流程存在，但不是强制的。**

就好比你安了一道锁，但从来不上锁。

## 我的几个心得

1. **对于不懂代码的人，CI 几乎是唯一的技术质量把关者。** 我不能靠自己读代码来发现问题，也不能靠经验直觉来判断代码质量。CI 是唯一一个不需要我懂代码就能运作的安全网。所以让它失效（`|| true`）等于自毁城墙。

2. **PR 的价值不在于「我审查 AI 的代码」——我审查不了。** PR 对我的价值是：触发 CI 让机器替我做技术判断、记录每次改动的边界和目的、出问题时可以精准回退。

3. **流程必须是系统强制的，不能靠自觉。** 一个人开发，忙起来的时候最先跳过的就是流程。Branch protection 的意义就是让你想跳都跳不过去。

4. **你的用户视角本身就是测试标准的来源。** 我不懂代码，但我知道用户打开 App 时应该看到什么、点了按钮应该发生什么。这些判断可以让 AI 转化成自动化测试。这样，我的用户直觉就不再是一次性的手动验证，而是被固化成每次都会跑的检查。

5. **先让 CI 能真正报红，再谈别的。** 一个能报红的慢 CI，远好过一个永远绿但实际什么都没检查的快 CI。

## 最后

其实 PR 和 CI 这套东西，工程师们早就烂熟于心了。我作为设计师来聊这个话题，多少有点班门弄斧的感觉。

但或许，正是因为我不懂代码，反而更能体会到这套流程对于「非技术创作者」的意义——它让你在看不懂代码的情况下，依然能对产品质量有基本的信心。

在 AI 时代，越来越多像我这样的设计师开始自己做产品。代码可以让 AI 写，但质量不能让运气来保证。

再聊。
