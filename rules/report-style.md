# Report Style

## ASCII 规则

- 凡是表达流程、链路、逻辑关系、状态迁移、知识地图、因果链、输入输出结构时，统一使用 ASCII 表达。
- 优先使用以下形式：
  - `A -> B -> C`
  - `input -> process -> output`
  - `if / then / else`
  - 编号步骤 `1. 2. 3.`
  - Markdown 表格
- 不使用非 ASCII 箭头或流程符号，例如：
  - unicode right arrow
  - unicode left arrow
  - unicode bidirectional arrow
  - 视觉流程字符组合
- 中文正文可以正常使用；该规则只约束“流程 / 逻辑 / 结构表达”。

## 深度与篇幅

- 默认目标不是“简洁概述”，而是“足够细、足够能学”。
- 只要该概念有足够资料，完整报告默认应达到长文级别。
- 没有用户特别要求更短时，目标篇幅应**不低于 10000 字**。
- 如果可靠资料不足以支撑 10000 字，可以低于该目标，但必须优先保证真实性，不能为了凑字数编造。

## 论文部分要求

- 论文部分默认是全报告最细的一层，不能用 1 段泛泛带过。
- 每篇关键论文至少要覆盖：
  - 要解决的问题
  - 提出的方法
  - 为什么这样设计
  - 实验或验证思路
  - 最重要的结论
  - 局限性
  - 对后续工作的具体影响
- 当一个概念的论文脉络清晰时，要把多篇论文串成演化链，而不是孤立点评。

## 写作颗粒度

- 对定义，解释“是什么”之外，还要解释“为什么不是别的东西”。
- 对机制，不能只写模块名，要写模块之间怎样配合。
- 对实践，不能只写案例名，要写动作路径和适用边界。
- 对项目分析，不能只判断“有/没有”，要区分：
  - 在产品 runtime 中使用
  - 在研发工作流中使用
  - 在基础设施层中使用
